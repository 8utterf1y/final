# 代码-设计文档一致性审查工具面试资料

> 使用方式：先背“2 分钟项目介绍”和“30 秒压缩版”，再准备后面的追问。面试时不要一开始堆 MCP、子 Agent、Tree-sitter 等名词，先讲清楚业务问题、为什么普通 Agent 效果差、你如何把模型审查变成可控工程流程。

## 一、项目定位

### 30 秒概述

我在实习期间参与开发了一个面向 MR 场景的代码-设计文档一致性审查工具。部门希望在代码合入前自动检查 MR 修改是否符合需求设计文档，但直接让通用 Agent 审查时，容易受到长文档、代码上下文缺失和模型幻觉影响。

我的工作重点是把审查流程工程化：系统先调取内部需求文档和 MR 变更信息，基于 Git Diff 定位变更范围，再通过 AST/Tree-sitter 构建符号索引和双向调用链，为每条需求生成可追溯的证据上下文；随后用确定性状态机约束模型完成初判、反证、补证和收敛，最终输出对应需求条目、代码位置和问题原因的审查报告。

### 2 分钟项目介绍

背景上，部门希望在 MR 阶段引入 AI 审查能力，检查提交代码是否符合需求设计文档，提前发现需求遗漏、实现偏差和边界条件缺失等问题。最初尝试直接使用通用 Agent 读取需求文档和代码进行审查，但效果并不稳定，误报漏报都比较多，尤其容易出现模型凭印象判断、引用不到代码证据，或者把没有看到的实现误判成没有实现。

我分析后认为，问题核心不在于模型完全不会审查，而在于输入上下文和审查流程都不可控。需求文档较长时，如果一次性全部塞给模型，模型容易注意力分散，无法稳定维护对所有需求条目的覆盖；代码仓较大时，如果只看 MR Diff，会缺少调用方、被调用方、公共校验和状态流转等上下文；如果让模型自由搜索全仓，又容易引入大量无关代码，导致判断漂移和幻觉。也就是说，一次性 Prompt 很难同时保证“需求逐条覆盖”和“代码证据准确关联”。

所以我主要从两方面改造。第一是构建证据上下文：系统会锁定 MR 的 base/head 版本，解析 Git Diff 得到变更种子，再用 AST/Tree-sitter 提取类、函数、方法、常量和调用关系，将变更片段映射到具体符号，并沿 caller 和 callee 做有限扩展，形成需求、变更、代码之间的证据链。第二是约束模型审查过程：模型不能直接自由扫仓，而是按状态机推进，分阶段提交结构化结论；运行时会校验每条需求是否覆盖、Evidence ID 是否真实属于当前需求、consistent/inconsistent 是否有代码证据支撑。

成果上，工具已经完成工程化落地，并接入部门 MR 审查流程试用。相比直接使用通用 Agent，试点中审查结论的准确率从约 `X%` 提升到 `Y%`，误报率下降约 `Z%`，并且每个问题都能追溯到需求条目、代码文件和行号。它的定位不是替代 reviewer，而是作为 MR 辅助审查工具，提前把需求遗漏和高风险边界问题暴露出来。

> 说明：如果没有经过确认的真实数据，不要在面试中报具体数字。可以说“在内部回放样例和试点 MR 上，准确率、误报率和可追溯性相比通用 Agent 明显改善，具体指标按部门评估口径统计”。

## 三、技术方案拆解

### 1. 输入是什么

输入主要包括三类：内部需求文档、MR 变更信息、业务代码仓库。

需求文档用于提取待审查的需求声明；MR 信息用于锁定 base/head 版本并计算 Diff；仓库源码用于建立符号索引和调用链。只提供 Diff 不够，因为 Diff 只包含本次变化片段，无法说明未修改的调用方、公共方法和底层实现是否影响最终行为。

### 2. 需求如何处理

系统不是把整篇需求文档直接给模型，而是按章节、列表项和段落拆分为可审查的 claim。每个 claim 会记录来源章节、原文、规范化 statement、可验证类型和稳定 claim_id。这样后续审查可以做到“一条需求一个结论”，避免模型用“整体基本满足”掩盖具体遗漏。

文档信息、修订记录、负责人、版本号这类元数据会被识别为 not_applicable，不作为代码实现要求。

### 3. MR 如何处理

系统会锁定 base/head commit，计算 `base...head` 的 Git Diff，将每个 diff hunk 解析成文件路径、新旧行号、增删改类型和 diff 文本。随后根据 head 版本索引，将变更行映射到所在函数、方法或常量，形成 change seed。

change seed 的作用是把审查起点从“整仓代码”收敛到“本次 MR 影响的代码区域”，后续再通过调用链向上下游扩展。

### 4. AST/Tree-sitter 做什么

AST 是把代码解析成语法结构后得到的树，能识别函数定义、类定义、常量、调用表达式等结构。Tree-sitter 是多语言语法解析器，适合在不完整编译环境下解析多语言源码。

项目中 AST/Tree-sitter 主要做三件事：提取符号定义，记录每个符号的文件和起止行；提取函数调用，形成 caller 到 callee 的调用边；为 Diff 到代码符号的映射提供结构边界。它不是简单 grep，也不是完整编译器语义分析，目前主要是语法级索引。

### 5. 双向调用链为什么必要

单看变更函数通常不够。向下查 callee，可以看到底层状态迁移、仓储事务、网关调用和公共校验；向上查 caller，可以看到业务入口、后台任务和旁路调用。

例如费用支付场景中，正常付款入口可能通过原子 `claim_for_payment` 防止取消后付款，但后台任务如果直接把 `CANCELLED` 转为 `PAYING`，就会绕过并发保护。这个问题必须把需求、状态迁移和调用路径放在一起看，单看某个函数片段很容易漏掉。

### 6. 多阶段审查如何约束模型

流程不是靠模型自觉完成，而是由运行时状态机约束。模型必须按当前阶段获取上下文、提交结构化 JSON，再由后端校验后才能进入下一阶段。

阶段口径可以简化表达为：

- 初判：找出可能不一致或证据不足的需求。
- 反证：主动寻找替代实现、前置校验、其他入口等反例，降低误报。
- 补证：围绕证据缺口沿调用链定向补充上下文。
- 收敛：去除误报、合并同根因问题、给出最终结论。

面试中不要把这四步讲得过细，重点强调“状态机约束 + 证据校验 + 覆盖率门禁”，这是区别于普通 Prompt 的关键。

### 7. 大模型实际做了什么

大模型主要负责语义推理：理解自然语言需求，判断代码证据是否满足需求约束，发现实现偏差，提出需要补充取证的方向，并把最终结论组织成可读报告。

确定性的工程运行时负责 Git Diff、索引、调用图、分页上下文、证据持久化、状态推进和校验。也就是说，模型负责“判断”，运行时负责“给证据、控流程、防幻觉”。

### 8. 如何控制上下文

系统不会把所有需求和所有代码一次性塞给模型，而是按 claim 分页，每页只返回少量需求；每条需求只关联有限数量的 Diff、源码片段和调用图边；深度取证时可按 query、callers、callees 或 both 定向扩展。

这个设计解决两个问题：一是避免长文档导致上下文腐化；二是避免大仓库代码过多导致模型注意力分散。

### 9. 如何处理大仓库性能

当前实现会遍历受支持源码文件并计算哈希，未变化文件复用上一轮符号和调用事实，只重新解析变化文件。这个方案已经比每次全量重建好，但在超大仓库上仍有优化空间。

生产化更优方案是“主干基线索引 + MR 增量索引 + 按需调用链扩展”：主干定时构建全仓基线，MR 来了只解析变更文件，并复用基线中的未变符号和调用边。这样成本主要跟 MR 影响范围相关，而不是跟整个仓库规模线性相关。

## 四、真实面试官追问

### Q1：你这个项目和普通代码审查工具有什么区别？

普通代码审查工具多是固定规则扫描，比如空指针、SQL 注入、代码风格等。本项目的审查对象是“本次 MR 是否符合需求设计文档”，需求每次都可能变化，所以它需要先理解需求，再关联 MR Diff、源码实现和调用路径。核心不是扫固定规则，而是做需求与代码行为的语义对齐。

### Q2：为什么直接用 Agent 审查效果差？

主要有三个原因。第一，需求文档长，模型很难一次性稳定覆盖全部需求；第二，代码仓大，模型如果自由读代码会引入很多噪声，如果只看 Diff 又会缺少上下游；第三，普通 Agent 的审查流程缺少强约束，容易凭印象下结论。我的方案用 claim 拆分、证据分页、调用链取证和状态机校验来解决这些问题。

### Q3：Skill 不能解决吗？为什么还要做工具/Agent？

Skill 主要是提示词层面的流程规范，可以告诉模型应该怎么审查，但很难强制它必须覆盖每条需求、必须引用真实证据、必须按阶段推进。这个项目把约束放到运行时：后端知道当前有哪些 claim，证据是否真实存在，阶段是否允许推进，所以比单纯写 Skill 更可控。

### Q4：这是子 Agent、插件、MCP，还是普通工具？

面试里建议称为“代码-设计文档一致性审查工具”或“一致性审查 Agent”。子 Agent 是在 OpenCode 里的执行形态，插件是当前交付方式，MCP 是后续可以暴露给其他 Agent 或 IDE 的协议接口。项目核心不是这些包装名词，而是审查运行时和证据驱动流程。

### Q5：为什么必须提供仓库？

因为 MR Diff 只告诉我改了什么，不告诉我完整行为。需求一致性经常依赖未修改代码，例如公共校验、状态机、仓储方法、调用入口和异常处理。提供仓库后，系统才能建立符号索引和调用链，让模型看到与本次变更相关的完整证据，而不是只看孤立 Diff。

### Q6：把仓库给模型会不会泄露代码？

当前设计不是把整个仓库发给模型。仓库解析和索引在本地运行，模型只拿到与当前 claim 相关的有限证据包，包括少量 Diff、源码片段和调用边。真正企业落地时，还需要使用公司允许的模型通道、日志策略和权限隔离，保证数据边界可控。

### Q7：怎么防止模型漏掉需求？

需求先被拆成 claim，运行时记录当前阶段预期覆盖的 claim_id 集合。模型提交结果时必须逐条覆盖，不能缺失、重复，也不能伪造 UNKNOWN 之类占位 ID。覆盖率不满足，阶段就不能推进。

### Q8：怎么防止模型伪造证据？

证据由运行时生成 Evidence ID，并绑定 case、claim、文件路径、行号和版本。模型提交结论时只能引用已返回的 Evidence ID，后端会校验证据是否真实存在、是否属于当前 claim。consistent 或 inconsistent 没有代码证据会被拒绝。

### Q9：调用链是不是一定准确？

不是。当前调用链主要来自语法级解析，遇到动态调用、反射、同名函数、多态分发时可能不完整。因此调用图只作为取证导航，不能单独作为结论依据。最终定案必须回到源码或 Diff 证据；无法解析或存在歧义的边要记录为 gap。

### Q10：多阶段流程为什么能减少误报？

因为它强制模型不要停留在第一次判断。初判后必须做反证检查，主动找是否存在替代实现、前置校验或其他调用路径；证据不足时再定向补证，最后收敛时才形成最终结论。这样可以减少“没看到就判错”和“看到相似代码就判对”两类常见问题。

### Q11：效果怎么验证？

我会分离线样例和真实 MR 试点两类验证。离线样例用已知缺陷版本，看根因召回率、误报率、证据是否完整、是否能合并同根因；真实 MR 试点则看 reviewer 采纳率、人工复核耗时、误报反馈和发现问题的提前量。不要只用模型最终回答判断效果，要看结构化结果和人工/测试验证。

### Q12：你说准确率提升，怎么算？

可以按“工具输出的问题是否被 reviewer 确认为真实需求偏差”来算 precision，也可以按已知缺陷集中被成功发现的比例算 recall。如果项目报告中写“准确率从 X% 到 Y%”，必须准备样本数、标注口径、对照组配置和哪些 case 被新增命中，否则面试官追问时站不住。

### Q13：如果需求文档本身不清楚怎么办？

不能强行判代码错误。系统会把不可验证的文档元数据标记为 not_applicable，对语义模糊、边界缺失或证据不足的需求标记为 uncertain，并指出缺少什么信息。这样既避免误报，也能反向推动需求文档规范化。

### Q14：为什么不直接让它自动修代码？

需求一致性问题经常涉及业务取舍，不一定存在唯一正确修复。当前工具默认只读，最多生成建议 Patch，由人工确认后再创建修复变更。审查权限和写代码权限应该分开，否则很容易把 AI 审查变成新的风险源。

### Q15：如果主管问“这个工具有什么实际意义”，怎么答？

它的意义不是替代人工，而是把人工最容易漏掉的需求逐条对照和证据搜集前置化。对 reviewer 来说，它能快速指出“哪条需求没完成、代码证据在哪里、影响范围是什么”；对团队来说，它把需求实现情况沉淀为可追溯记录，后续也能服务测试生成、回归分析和质量度量。

### Q16：项目最大的难点是什么？

最大的难点是如何给模型提供“刚好足够”的上下文。上下文太少会漏掉跨函数逻辑，上下文太多会导致注意力分散和幻觉。我的做法是用 MR Diff 定位起点，用 AST/Tree-sitter 建立符号边界，用调用链做有限扩展，再通过分页和预算控制输入规模。

### Q17：如果 MR 只改几行，为什么还要看调用链？

因为代码行为不是由改动行单独决定的。几行改动可能调用了已有公共方法，也可能绕过了原有校验，还可能改变被多个入口复用的底层逻辑。调用链能帮助判断这几行代码在真实业务路径中的作用。

### Q18：如果大仓库每次索引很慢，怎么办？

当前实现已经做了文件哈希复用，只重新解析变化文件，但仍要遍历文件。更适合生产的方案是主干预建基线索引，MR 只构建增量索引，并把增量结果叠加到基线图上。再结合路径范围、语言过滤和按需 BFS，把成本控制在 MR 影响范围内。

### Q19：你个人具体做了什么？

可以回答：我主要负责需求、变更和代码之间的证据链设计与实现，包括需求 claim 拆分、Git Diff 到符号的映射、AST/Tree-sitter 索引、双向调用链取证，以及多阶段审查流程和证据校验机制。具体到代码层面，就是把模型自由审查改造成有输入范围、有阶段状态、有证据约束的审查运行时。

### Q20：这个项目还有哪些不足？

第一，静态调用图对动态分发、反射、运行时配置和跨服务调用覆盖不足；第二，当前检索主要依赖结构化索引和词项排序，语义召回还可以引入向量检索或代码搜索增强；第三，线上效果需要更多真实 MR 标注数据验证，不能只依赖少量演示样例。

## 五、被追问时的边界口径

### 关于“已部署”

可以说：工具已完成工程化落地，并接入部门 MR 审查流程试用。当前定位是辅助 reviewer 的建议工具，不是强制阻断门禁，也不会自动修改业务代码。

不要说：已经完全替代人工审查、已经全量覆盖所有仓库、已经自动修复业务代码。

### 关于“准确率”

推荐说：在内部回放样例和试点 MR 上，相比直接使用通用 Agent，准确率、误报率和可追溯性有明显改善；如果报具体数字，我会同时说明样本规模、标注口径和对照组。

不要说没有来源的固定数字。真实面试中，面试官很可能追问“样本多少、谁标注、怎么定义正确”。

### 关于“创新点”

推荐说：创新点不在于使用某个模型，而在于把需求一致性审查拆成可验证的工程流程：需求 claim 化、MR Diff 定位、符号索引和调用链取证、证据对象持久化、状态机约束模型推理、覆盖率和证据引用校验。

不要把“用了大模型”或“做成插件”当成主要创新。

### 关于“MCP”

可以说：MCP 更适合把代码索引、调用链查询、证据检索这些能力暴露给多个 Agent 或 IDE 复用；但本项目核心审查流程仍需要状态机、证据校验和报告生成。MCP 是能力接口，不等于完整审查系统。

### 关于“子 Agent”

可以说：子 Agent 是为了把审查任务从主对话中隔离出来，限制它只能调用 spec_review 相关工具，并按审查协议执行。它不是玩具概念，而是专用执行角色；但简历和面试中最好把项目主体称为“一致性审查工具/审查 Agent”，不要突出“子 Agent”。

## 六、面试收尾话术

如果让我总结这个项目，我认为核心价值是把大模型从“自由判断”变成“证据驱动的受控审查”。模型负责理解需求和代码语义，但它看到什么、什么时候能下结论、结论能否进入报告，都由运行时约束。这样才能在真实 MR 场景里降低误报漏报，并让 reviewer 能够快速复核每个结论。

## 七、原始方案素材保留

> 以下内容为原文档中的方案素材，保留用于后续提炼。部分表述偏“通用代码审查平台 / C/C++ 代码检视”，面试时应按前文的“代码-设计文档一致性审查工具”口径取用，不要整段照背。

| 能力 | 说明 |
| --- | --- |
| 项目管理 | 注册一个 C/C++ 代码仓库即可开始；平台自动完成初始化，并提供一键自检，包括模型连通性、环境就绪等。 |
| 发起检视 | 按整仓、指定文件、指定函数粒度建立检视任务，选择检视深度与规则范围；后台执行，支持实时进度与日志。 |
| 深度上下文 | 平台自动为代码建立索引，检视时按需注入跨函数、调用链上下文，让判断有据可依，而不是只看孤立片段。 |
| 多阶段推理 | 每条问题经历初判、质疑、跨函数取证、定级收敛的多阶段推理，可逐条回看推理过程与证据。 |
| 结果查看 | 问题列表多维过滤，包括严重级、规则、研判状态和关键词；支持翻页、文件行号定位、证据代码块和累计指标看板。 |
| 研判与导出 | 支持逐条研判，包括确认、误报和忽略；支持导出全字段结果，便于归档与跨部门评审。 |

### 跨函数取证：沿调用链补齐上下文

借助代码索引，AI 不只看眼前片段，还能顺着调用链查看被调函数的定义后再下结论。

只看孤立片段时，模型看不到被调函数的真实实现，拿不到调用链上下文，结论容易想当然。例如只盯着 `parse(buf)`，模型可能只提示“注意空指针”，但看不到 `fopen` 句柄泄漏，也无法判断 `read_all` 是否真的可能返回 `NULL`。

平台方案是索引到 `read_all` 定义后做跨函数取证，同时给出文件行号定位、证据代码块和完整推理过程。

### 大模型语义推理与多阶段链路

单轮提问难以自我纠错，LLM 自身也可能幻觉出不存在的问题。因此结论需要能逐条回看推理与证据，方便研判、复盘和跨团队协作。

一次性提问的问题在于不可靠、不可审计，也缺少协作沉淀。多阶段链路通过质疑和取证降低误判，并让每一步留痕、可回看。

### 痛点分析与方案设计决策

| 痛点 | 方案设计决策 |
| --- | --- |
| 缺少仓库级上下文 | 使用索引驱动的跨函数上下文，基于 Tree-sitter 建符号表和调用图，按需双向 BFS 取数。 |
| 语义审查弱、泛化弱、单轮不可靠 | 使用大模型语义推理和多阶段链路，完成初判、自我质疑、调工具取证和定级收敛。 |
| 不可审计、AI 幻觉 | 使用证据策略和全程留痕，强制可定位证据，逐条回看提示词、响应和工具观测。 |
| 缺少协作沉淀、未融入流程 | 平台化支持研判、归档、调度和实时日志，将审查嵌入研发流程。 |
| 可靠性和成本 | 使用确定性 L3/L4 流水线、token 预算裁剪、结果缓存、主备模型和排队机制。 |

### 适用场景

- 模块级或整仓级的周期性代码体检，配合定时任务闲时调度。
- 关键模块、变更热点的深度评审。
- 交付前的缺陷清单沉淀与跨部门评审。
- 叠加在既有静态分析和 CI 门禁之上的增量审查：传统工具守已知规则下限，AI 补充语义、逻辑和跨函数缺陷审查。
- 作为代码理解基础设施，代码上下文服务可以通过 MCP 被 IDE、Agent 或 CI 复用。

### 端到端数据流

一次审查任务的完整链路：

1. 登记项目：注册被审查的代码仓库，平台自动初始化配置。
2. 建立或更新索引：对整仓建立索引库，记录符号、引用、include 和调用关系；通过 SHA-256 增量识别，仅重建变更文件。
3. 按需取上下文：对每个审查目标沿调用链双向 BFS 取数，并按 token 预算裁剪。
4. 多阶段推理：按 L3 或 L4 编排大模型；L4 进入 Actor、Critic、ReAct、Refiner 链路，完成跨函数取证。
5. 落库与聚合：推理链、证据和用量写入运行数据库，平台侧聚合为可过滤、可研判、可导出的结果。
6. 研判与归档：用户逐条研判，按需导出归档。

### 组件职责边界

代码上下文模块只负责代码理解与取数，不调用 LLM，可独立作为 CLI、Python API 或 MCP 服务使用。

审查模块只负责推理编排与结果生产，把“给多少上下文”交给代码上下文模块，把“调度与展示”交给平台。

代码上下文模块相当于整条流水线的“代码理解层”：把整仓解析成符号表、调用图和 include 关系并落入 SQLite 索引，再按需把任意函数的相关上下文打包给模型，让大模型基于上下文判断，而不是只看孤立片段。它不是简单 grep 或正则，而是一套可复用的代码理解基础设施。

### 索引构建

- Tree-sitter 解析，不依赖项目一定能完整编译，容错强、跨平台；需要更精确时可结合 `compile_commands.json` 和编译器预处理，还原宏与 include。
- 增量和并行索引：通过 SHA-256 指纹比对，改了哪个文件只重建哪个文件；可通过线程池并行解析提升大仓索引速度。
- SQLite 单文件索引：符号、引用、include 和调用关系入库，只读查询和多读者并发较方便，适合被审查工具、CI、MCP 客户端共享。

### 按需取上下文

把“喂多少上下文”变成可控工程参数，而不是一股脑把代码全部塞给模型。

双向按需取数：沿调用链向下查看目标调用了谁，沿调用者方向向上查看谁调用了目标，通过 BFS 控制深度和 token 预算。

### MCP 能力

代码上下文服务可以通过 MCP 暴露一组只读工具，让兼容 MCP 的客户端直接接入并按需取数：

| MCP 工具 | 作用 |
| --- | --- |
| `get_function_context` | 取单函数上下文，支持 depth、caller_depth、max_tokens 裁剪，输出 Markdown 或 JSON。 |
| `search_symbols` | 按名称、类型、模块或通配过滤符号。 |
| `find_callers` / `find_callees` | 沿调用图向上或向下 BFS。 |
| `list_modules` / `module_map` | 返回模块表和文件清单。 |
| `tools/list` | 自描述列出全部工具与参数。 |

### L3：单次推理

L3 走单轮规则评审：把目标函数、上下文和规则一次性交给模型，快速产出问题清单。速度快、token 省，适合全量扫描和日常回归。

### L4：多阶段深审

L4 进入多阶段链路，逐级自我质疑与跨函数取证：

1. Actor 初判：基于上下文与规则给出初步问题判断。
2. Critic 质疑：对初判逐条提出反问，挑出证据不足或可能误报之处，并可发出 drop 信号，让弱证据 finding 被后续删除。
3. ReAct 取证：按需调用工具查定义、找调用者或读取片段，沿调用链补齐证据。
4. Refiner 收敛：综合证据定级、去误报、合并重复，产出最终结论。
