# 二、Coding Agent 项目

## 30 秒项目概述

我开发了一个面向软件开发任务的可控 Coding Agent CLI。它以大模型为决策核心，提供文件读取与修改、代码检索、Shell 执行、技能调用、知识检索和子任务委派等 13 个顶层工具，并支持只读探索、计划和通用执行三类子 Agent。我重点完成了工具编排、四层上下文治理、六种权限模式和混合 RAG，使 Agent 能够更稳定地执行长链路编程任务。

### 9. 这个项目解决什么问题？

普通大模型可以给出代码建议，但很难可靠地完成“理解仓库 - 修改文件 - 执行测试 - 根据结果继续修复”的闭环。这个工具把模型与代码库和执行环境连接起来，让模型能够调用受控工具完成任务，同时通过上下文治理和权限控制降低长任务失败与误操作风险。

### 10. 整体架构是什么？

核心是一个循环：模型读取系统提示和会话上下文，输出文本或工具调用；运行时进行权限判断并执行工具；工具结果回填给模型，直到任务收敛。外围包括会话持久化、上下文压缩、Skills、MCP、子 Agent、本地知识库和终端交互层。

### 11. 为什么选择 CLI？

编程任务天然依赖本地仓库、Shell、Git 和测试命令，CLI 与这些工具的集成成本最低，也便于流式展示执行过程和人工确认。项目目标是先验证 Agent 的执行闭环和控制机制，而不是投入大量成本做界面。

### 12. 13 个工具具体包括什么？

代码中的 13 个顶层工具包括文件读取、写入、精确编辑、文件列表、代码搜索、Shell 执行、Skill 调用、网页读取、知识库检索、进入计划模式、退出计划模式、子 Agent 和工具搜索。MCP 动态接入的外部工具不计入这 13 个，因为数量由配置的服务器决定。

### 13. 为什么要做工具延迟激活？

如果把所有工具的完整 Schema 一次性放入模型上下文，会占用 Token，并增加模型选错工具的概率。我将低频工具标记为 deferred，初始只暴露高频工具和工具搜索；模型需要时先检索并激活对应工具，从而减少提示开销。

### 14. 工具如何并发执行？

运行时先识别同一轮中的只读、无副作用工具，例如读文件、列目录、代码搜索和知识检索，再通过异步任务并发执行；写文件和 Shell 等可能产生状态变化的操作保持顺序执行。这样既降低代码探索耗时，也避免并发修改导致竞态。

### 15. 如何支持 Anthropic 和 OpenAI 兼容接口？

核心循环对两类消息格式分别做适配：Anthropic 使用 content block 和 tool_use，OpenAI 使用 tool_calls 和 tool role 消息。工具定义也会转换成对应格式，但权限判断、工具执行、压缩和会话管理共享同一套逻辑。

### 16. 四层上下文压缩是什么？

第一层在窗口利用率升高后限制单个超长工具结果的预算；第二层裁剪较旧的可恢复工具结果，仅保留近期结果；第三层在会话空闲或继续膨胀时清理过期内容；第四层在输入接近有效窗口上限时用模型生成会话摘要，保留关键决策、路径和任务状态。压缩是逐级触发的，避免过早丢失细节。

### 17. 为什么超长结果要保留可恢复副本？

直接截断会永久丢失信息，模型后续发现需要某段内容时无法恢复。因此运行时先把完整结果保存到本地，再把截断内容和恢复路径放回上下文；需要时可以通过读文件工具重新获取。这是在上下文成本和信息完整性之间的折中。

### 18. 为什么不能一开始就总结整个会话？

摘要会损失细粒度代码和工具结果，而且额外产生一次模型调用。项目采用分层压缩，优先处理体积最大、最容易恢复的旧工具输出，只有接近窗口上限时才做全局摘要。

### 19. 上下文体积降低 34% 是怎么测的？

我在同一组长会话任务上记录每轮发送给模型的上下文体积，对比启用和关闭分层治理后的平均值，得到约 34% 的下降。面试时要继续说明实际采用的是 Token 数还是序列化字符数、任务数量和统计区间，并展示原始日志；如果口径不是 Token，就不能称为 Token 降低 34%。

### 20. 六种权限模式是什么？

分别是 default、plan、acceptEdits、bypassPermissions、dontAsk 和 auto。default 对危险操作请求确认；plan 只允许读取和修改计划文件；acceptEdits 自动允许已有文件编辑；bypassPermissions 放宽交互确认但仍受显式 deny 规则约束；dontAsk 对需要确认的操作直接拒绝；auto 通过两阶段分类器判断非只读操作是否符合自动执行规则。

### 21. 如何识别危险命令？

运行时使用危险模式列表拦截删除、强制 Git 操作、提权、磁盘写入、终止进程和关机等命令，并结合用户级和项目级 allow/deny 规则判断。deny 规则优先级最高，即使在跳过确认模式下也不能绕过。

### 22. 如何降低错误修改文件的风险？

除了权限模式，我还实现了 read-before-edit：修改已有文件前必须先读取，并记录当时的 mtime；如果文件在读取后被外部修改，编辑会被拒绝，要求重新读取。复杂任务还可以先进入只读计划模式，用户确认计划后再执行。

### 23. Plan 模式如何工作？

进入 Plan 模式后，Shell 和业务文件写入被禁止，只允许读取仓库并维护专用计划文件。模型完成分析后调用退出计划模式，由用户选择继续规划或批准执行；批准后再恢复相应权限，确保分析和修改两个阶段分离。

### 24. 三类子 Agent 有什么区别？

Explore 子 Agent 只用于只读代码搜索，Plan 子 Agent 输出结构化方案但不修改代码，General 子 Agent可以使用除继续创建 Agent 之外的完整工具完成独立任务。它们拥有隔离上下文，主 Agent 只接收结果，能减少主会话噪声并支持任务分解。

### 25. 为什么子 Agent 不允许继续递归创建子 Agent？

无限递归会导致成本和执行范围失控，也会让责任链难以追踪。项目把任务委派控制在主 Agent 一层，子 Agent 在明确的工具范围和独立上下文中完成任务。

### 26. Skills 和普通 Prompt 有什么区别？

Skill 是带元数据、触发条件、允许工具范围和提示模板的可复用工作流，可以由用户调用或由 Agent 按条件调用。相比临时 Prompt，它能把稳定流程版本化，并限制执行权限；相比硬编码工具，它更容易扩展业务流程。

### 27. MCP 在系统中起什么作用？

MCP 用统一协议把外部工具接入 Agent。运行时从配置中启动 MCP Server，完成初始化和工具发现，再把工具转换为带服务器前缀的模型工具定义；调用时通过 JSON-RPC 转发。这样接入新系统时不需要修改 Agent 核心循环。

### 28. 本地知识库如何构建？

导入文档后先按格式解析，再依据标题层级、页码和 Token 预算进行结构感知切分；SQLite 保存文档、版本、分片元数据和向量。索引按内容、Embedding 模型和维度生成版本指纹，文档重复导入可保持幂等，配置变化时可以重建索引。

### 29. 为什么使用 SQLite？

这个项目是本地 CLI，SQLite 无需额外服务，支持事务、结构化元数据和 FTS5，部署成本低。对于单机知识库规模，它比引入独立向量数据库更合适；如果扩展到多人并发和大规模数据，再考虑服务化存储。

### 30. 混合检索流程是什么？

先根据高置信元数据选择是否缩小文档范围，再由 HNSW 或精确余弦检索召回语义相关分片，同时由 FTS5 召回关键词相关分片。两路结果使用 RRF 融合，再结合向量相似度、词项覆盖、标题标签匹配和精确短语进行本地二阶段重排，最后返回少量证据块。

### 31. 为什么不能只用向量检索？

向量检索擅长语义相似，但对函数名、配置项、缩写和精确编号可能不稳定；关键词检索恰好擅长这些精确匹配。混合召回可以提高覆盖率，RRF 又能在两路分数不可直接比较时稳定融合排序。

### 32. 为什么选择 HNSW？

HNSW 在较高召回率下具有较好的查询效率，适合本地中等规模向量索引。项目只在分片达到阈值且依赖可用时启用 HNSW；小规模或带复杂过滤的查询使用精确余弦，索引异常时也会安全回退。

### 33. Recall@5 从 68% 到 86% 怎么测？

我构建了带标准答案的检索集，每条问题标注预期文档、标题或关键词，并检查前 5 个结果是否覆盖目标证据。对照组是单路向量检索，实验组加入 FTS5、RRF 和二阶段重排，Recall@5 从 68% 提升到 86%。还应同步报告样本量、MRR 和 Precision@5，避免只展示单一指标。

### 34. 任务完成率从 73% 到 87% 怎么测？

简历口径是 30 组端到端编程任务，在模型、提示和环境一致的条件下对比改进前后版本，根据任务验收条件和测试结果判断是否完成。按 30 题换算，73% 和 87% 大约对应 22 题和 26 题，最终应以原始记录为准。需要能列出新增通过的任务类型，并说明失败是规划、检索、工具执行还是验证阶段造成的。

### 35. 这个项目最难的部分是什么？

最难的是在“保留足够上下文”和“控制 Token 与噪声”之间做平衡。过度压缩会让模型忘记代码细节，不压缩又会导致长任务溢出；我通过可恢复结果、分级阈值和只在高利用率下总结，把不可逆压缩推迟到最后。

### 36. 项目还有哪些不足？

第一，权限判断仍包含规则和模型分类器，无法形式化保证所有危险行为都被识别；第二，本地 SQLite 和 HNSW 更适合单机，暂不面向多人并发；第三，30 个任务的评估规模有限，还需要扩大任务类型并进行多次重复实验，降低模型随机性影响。

# 三、代码与设计文档一致性审查工具

## 30 秒项目概述

我在华为参与开发了一个需求设计文档与代码变更的一致性审查工具。系统先把文档拆成可验证的需求声明，再基于 Git Diff 确定变更范围，利用 AST 或 Tree-sitter 构建符号索引和调用关系，为每条需求生成有界的证据包；模型依次完成初判、反向质疑、定向取证和结论收敛。最终结论必须引用与当前需求绑定的源码或 Diff 证据，支持追溯。

### 37. 为什么需要这个工具？

人工审查通常更关注代码质量，但容易遗漏“实现是否覆盖设计要求”；直接把整份文档和整个仓库交给大模型，又会带来上下文过大、遗漏需求和无依据判断。这个工具把审查转化为逐条需求、逐条证据和有状态流程，提高覆盖率与可追溯性。

### 38. 系统整体流程是什么？

流程是：锁定仓库和审查范围，解析需求文档为 claims，解析 Git Diff 得到变更种子，构建或增量更新符号索引，然后为每个 claim 生成 Diff、源码和调用图上下文。模型提交结构化阶段结果，运行时校验证据归属和需求覆盖率，最后生成 Markdown、JSON 和 SARIF 报告。

### 39. 如何把文档转换为可审查的需求？

系统按文档章节和文本单元提取候选要求，为每条声明生成稳定 claim_id，并记录来源章节、原文、规范化 statement、可验证类型和顺序。关键是保持“一条需求一个 claim”，不能把多条要求合并成笼统结论。

### 40. 为什么使用 Git Diff？

Diff 能把审查范围收敛到本次改动，并保留新增、删除和修改的直接证据。系统将 diff hunk 映射到文件和符号，再沿调用关系扩展上下文，避免只看改动行而遗漏上下游影响。

### 41. AST 和 Tree-sitter 分别做什么？

它们用于抽取类、函数、方法、变量等符号，以及调用边。Python 可以使用标准 AST 获得稳定语法信息；多语言场景优先使用 Tree-sitter 的统一解析接口。解析后形成符号索引和调用图，用于从变更位置导航到相关实现。

### 42. 为什么不能只使用文本搜索？

需求描述和代码命名经常不一致，文本搜索很难识别别名、封装层和跨文件调用。符号索引能提供结构边界，调用图能沿 caller 和 callee 扩展；文本相关度仍可用于对候选证据排序，但不是唯一依据。

### 43. 双向调用链有什么作用？

向下查看 callee 可以确认关键逻辑最终如何实现，向上查看 caller 可以判断该逻辑是否真的从业务入口可达。两者结合有助于发现“底层函数写了但没有被调用”或“主入口正确但旁路绕过约束”的问题。

### 44. 调用图能直接证明需求实现了吗？

不能。调用图只用于导航，静态解析还可能存在动态调用、同名符号和解析歧义。最终 consistent 或 inconsistent 结论必须引用实际源码或 Diff 证据；解析不了的边应该标记 unresolved 或 ambiguous，而不是强行推断。

### 45. 多阶段审查为什么比一次 Prompt 更可靠？

一次判断容易受到首因偏差影响。系统先做 L3 全量初筛，再对不一致或不确定项执行 L4：初判提出假设，challenge 主动寻找反例，investigate 围绕证据缺口定向扩展 caller 或 callee，converge 去除误报并给出最终归因。各阶段结果持久化并校验，避免模型跳步。

### 46. fast、deep 和 auto 模式有什么区别？

fast 完成全量初筛后直接生成结果；deep 对目标声明完整执行深度审查；auto 先全量初筛，只把 inconsistent 和 uncertain 项送入 L4，从效果和成本之间取得平衡。

### 47. 如何防止模型遗漏需求？

运行时知道当前阶段预期的真实 claim_id 集合，提交结果必须逐条覆盖且不能重复，也不允许额外伪造 ID。缺失、重复或使用 UNKNOWN 等占位声明都会触发覆盖率门禁，阶段无法推进。

### 48. 如何防止模型伪造证据？

证据由运行时生成稳定 evidence_id，并绑定 case_id 和 claim_id。模型提交结论时，后端会检查每个 evidence_id 是否真实存在、是否属于当前案例和当前需求；consistent 或 inconsistent 没有代码证据也会被拒绝。

### 49. 如何控制上下文大小？

系统不会把“所有需求乘以所有代码”一次性返回，而是按 claim 分页，每页默认少量需求；每个 claim 只选择有限数量的 Diff 和源码证据，调用图也有节点、边和源码字符预算。深度取证时可按 query 和 callers、callees 或 both 定向扩展。

### 50. 如何做增量索引？

每次索引创建快照，对文件内容计算哈希。与上一快照哈希相同的文件直接复用符号和调用事实，只重新解析变化文件，再统一解析调用边；这样可以降低大仓库重复分析成本，并保留审查时对应的 revision。

### 51. 如何处理同名函数和无法解析的调用？

边解析会记录 resolver、confidence 和 resolution_status。唯一匹配时可以绑定目标符号；存在多个候选时标记 ambiguous，找不到时标记 unresolved，并把这些情况作为 gap 交给后续取证，而不是选择一个看似合理的目标。

### 52. 如何保证 PR 审查对象没有变化？

PR 模式会锁定 base 和 head SHA，并在隔离 worktree 中分析。真实发布前必须再次检查 expected head SHA；如果 PR 在审查后发生更新，发布会被拒绝，避免把旧结论发到新代码上。

### 53. 工具会自动修改业务代码吗？

默认不会。系统默认只生成审查报告；suggested patch 也只是建议。只有用户明确要求创建修复 PR，并提供完整确认条件时才允许进入发布路径，这是为了把审查和修改权限分离。

### 54. 如何评估这个审查工具？

仓库中构建了费用报销基准集，包括完整实现、并发幂等性不足、自审批校验缺失、重试策略错误和旁路绕过状态约束五类版本。合理指标包括根因召回率、精确率、证据完整度、重复问题合并能力和不确定性表达。注意：合规测试验证了基准样例与标准答案一致，不等于已经证明模型审查在五个版本上全部正确。

### 55. 你在这个项目中具体负责什么？

我主要围绕需求、变更和代码之间的证据链开展工作，包括利用 Git Diff 和语法索引确定相关代码、组织双向调用上下文，以及设计初判、质疑、取证和收敛的多阶段审查流程。回答时应进一步结合你实际提交过的模块说明，不要把团队整体工作全部描述成个人完成。

### 56. 这个项目最难的问题是什么？

最难的是区分“相关代码”与“足以支持结论的证据”。语义相关度高并不代表需求已实现，因此系统需要把检索、调用图导航、证据持久化、覆盖率校验和反向质疑组合起来，强制模型说明结论来自哪里。

### 57. 当前局限是什么？

静态调用图难以完整覆盖反射、动态分发和运行时配置；需求文档也可能存在歧义或不可验证描述。当前做法是显式记录解析精度和证据缺口，对证据不足的情况输出 uncertain，并建议结合动态测试、人工确认或更完整的运行时信息。

# 四、模型下载插件

### 58. 模型下载插件解决什么问题？

在中移动媒体插件化落地中，大模型包受存储中转限制，不能沿用普通安装链路，导致插件安装失败。我实现了独立的模型资源下载能力，使插件可以在运行前自动检查资源是否就绪，在需要时加载，并清理过期资源，保证模型能够可靠部署。

### 59. 为什么不把模型直接打进插件包？

大模型文件体积大，直接打包会增加分发、升级和存储成本，也容易触发平台传输限制。代码与模型资源解耦后，可以独立版本管理和按需获取，插件升级时不必重复传输完整模型。

### 60. 如何保证下载可靠性？

回答应围绕你真实实现的机制展开，例如完整性校验、临时文件与原子替换、失败重试、断点续传、并发锁和版本检查。简历目前只能确认自动就绪、按需加载和过期清理，不要主动声称未实际实现的机制。

### 61. 如何做过期清理？

核心是根据模型版本、最后使用时间或当前引用关系识别不再需要的资源，并避免删除正在加载或仍被业务引用的版本。具体淘汰规则和并发保护必须按真实代码回答。

# 五、科研一：SceneCom 场景理解图像合成

## 30 秒工作概述

这项工作提出 SceneCom，将图像合成拆为对象放置和对象插入两个阶段。放置阶段利用 VLM 判断适合承载前景对象的场景实体，再通过检测、分割和 Mask-guided Transformer 预测精确位置；插入阶段先验证对象是否出现在目标位置且身份是否保持，再利用 VLM 生成的外观差异描述指导颜色和亮度和谐化，从而提高合成图像的语义合理性和视觉协调性。

### 62. 为什么要统一对象放置和对象插入？

传统流程通常分别研究放在哪里和如何融合，但真实合成质量同时取决于空间合理性、对象身份保持和外观协调。统一框架可以让输出经过完整质量控制，而不是只优化某一个局部指标。

### 63. VLM 在其中承担什么作用？

VLM 不直接回归坐标，而是利用常识判断前景对象适合放在背景中的哪类实体或区域，例如把笔记本电脑与桌面关联；在和谐化阶段，它还分析前景与背景在白平衡、亮度和颜色等方面的差异，生成文本指导。精确定位和像素变换仍由专门视觉模型完成。

### 64. 为什么不让 VLM 直接输出坐标？

VLM 擅长全局语义和常识推理，但精确几何定位与连续坐标回归不是它的强项。因此我们让 VLM 输出语义实体，再由 Grounding DINO 定位、SAM 分割，最后通过 Mask-guided Transformer 预测具体放置框，发挥各类模型的优势。

### 65. MGPP 如何工作？

MGPP 先由 VLM 找到语义相关实体，Grounding DINO 和 SAM 将其转换为 ROI mask；随后提取前景和背景特征，在 Transformer 注意力中把 ROI mask 作为偏置，使模型重点关注合理区域；最后输出不同位置和尺度的放置热力图，并保持前景宽高比生成边界框。

### 66. MDCV 为什么需要两级验证？

扩散式插入具有随机性，可能出现对象缺失、位置偏移或身份变化。第一级用 Grounding DINO 检查目标对象是否存在并与预期框对齐，IoU 阈值为 0.8；第二级用 CLIP 比较生成区域与原始前景的身份相似度，阈值为 0.75。失败样本最多重试三次。

### 67. OCTGH 如何实现和谐化？

VLM 从五个维度描述前景和背景的外观差异，包括白平衡、亮度对比、颜色对比、整体亮度和整体颜色。视觉特征与 BERT 编码的文本特征融合后，网络预测像素级颜色变换矩阵，只对前景区域进行颜色和亮度调整，从而保留结构并改善视觉协调性。

### 68. 使用了哪些数据集和指标？

放置模块使用 OPA，和谐化模块使用扩展后的 T-HFlickr，整体插入测试使用 1000 对前景背景组成的 Pixabay-Pair。放置使用 Mean IoU、FID 和 LPIPS；插入使用质量分数、审美分数、DINO、CLIP-I 和 CLIP-T，分别衡量质量、身份一致性和文本对齐。

### 69. 主要实验结果是什么？

放置阶段 Mean IoU 为 0.301、LPIPS 为 0.245，优于论文中的对比方法；FID 为 21.93，略低于最优方法 IOPRE 的 20.86，因此应表述为在准确性和多样性上领先、整体取得较好平衡，而不是所有指标都最优。插入阶段在 Pixabay-Pair 上的 QS、AS、DINO、CLIP-I 和 CLIP-T 均优于列出的对比方法。

### 70. 消融实验说明了什么？

去掉 VLM 语义引导后，放置的 FID 从完整模型的 21.93 变差到 25.61；只加入固定中心区域 Mask 进一步变为 27.12，说明错误 ROI 反而会误导模型。OCTGH 提升了 QS 和 AS，但会使 DINO 与 CLIP-I 略降，因为颜色和亮度调整会让生成对象与原始前景特征产生一定差异。

### 71. 为什么 CLIP 阈值选择 0.75？

论文先分析未验证生成结果的 CLIP 分布，0.75 以下约占 16.5%，再人工检查不同区间样本。低于该阈值的样本通常出现明显伪影或身份偏差，因此把 0.75 作为质量与拒绝率之间的经验平衡。

### 72. 这项工作的局限是什么？

系统依赖 VLM、检测、分割、插入和和谐化等多个模型，推理链路较长、资源消耗较高；前级语义实体判断错误也会向后传播。未来可以通过模型蒸馏、缓存语义先验、减少串行调用和联合训练提升效率与鲁棒性。

# 六、科研二：GeoPlace 多对象放置

## 30 秒工作概述

GeoPlace 面向复杂场景中的多对象放置。方法为每个前景对象构造对象条件查询，将放置建模为对象在背景场景表示中的检索；同时把深度差与空间距离注入场景编码，增强尺度和位置的几何合理性；最后通过对象 Token 对比损失和交叉注意力重叠损失，减少同类别对象的身份混淆和放置冲突。

### 73. 多对象放置比单对象难在哪里？

除了每个对象与背景是否匹配，还要考虑对象之间的关系。同类对象的外观相似，查询容易收敛到相似表示并关注同一背景区域，导致预测框重叠、遮挡或身份对应错误。

### 74. 为什么叫对象驱动检索？

每个 decoder query 都由具体前景对象的 patch embedding、类别 embedding 和随机 latent 构成，不是与输入无关的通用查询。Decoder 用这些查询在几何增强的背景 Token 中检索适合该对象的放置线索，因此称为对象驱动检索。

### 75. 三类 Query 信息分别有什么作用？

Patch embedding 表示对象自身外观，类别 embedding 提供语义先验，随机 latent 提供候选多样性。消融中去掉类别信息下降更明显，说明类别先验对定位很重要；去掉随机 latent 后 Top-k 指标下降，说明它主要帮助覆盖多种合理放置。

### 76. DGSE 如何注入深度信息？

第一条路径根据 Token 两两之间的深度差和空间距离构造衰减矩阵，用它调制自注意力，使深度接近且空间连续的区域交互更强；第二条路径把深度图编码成与场景 Token 对齐的几何 embedding，通过残差加入场景表示。两条路径分别作用于注意力关系和 Token 内容。

### 77. 深度图从哪里来？会不会有误差？

深度图由 Depth Anything V2 离线估计，不依赖真实深度传感器。单目深度确实可能存在误差，因此论文把它作为软几何先验而非硬约束；实验还比较不同深度估计设置，以验证方法对深度质量变化的鲁棒性。

### 78. Relation-Consistent Regularization 包含什么？

第一项是对象 Token 对比损失，用 InfoNCE 把解码后的对象表示拉近其对应输入对象 Token，并推离其他对象，减少身份混淆；第二项是交叉注意力重叠损失，只对同类别对象中过度重叠的高响应区域进行惩罚，鼓励不同对象关注不同背景位置。

### 79. 为什么只约束同类别对象？

同类别对象外观和语义最相似，更容易出现 Query 混淆和竞争同一位置。只约束高风险对象对可以减少不必要的正则化；不同类别对象仍通过 Decoder 自注意力交换关系信息。

### 80. 为什么重叠损失要有门控和 warm-up？

合理放置并不要求注意力完全不重叠，直接惩罚所有重叠会过度约束。门控只惩罚超过阈值的高重叠；训练前期注意力尚未稳定，因此在前 25 个 epoch 逐步启用该损失，避免早期错误约束干扰基础定位学习。

### 81. 训练目标是什么？

总损失由 DETR 风格的检测框监督、对象 Token 对比损失和交叉注意力重叠损失组成。默认两项正则权重均为 0.2，对比温度为 0.07，注意力重叠采用阈值和门控温度控制。

### 82. 使用了哪些数据集和指标？

使用 Cityscapes 衍生放置数据和 OPA。准确性指标包括 Top-1、Top-5 的 IoU 与 IoU50；合理性使用 FID；多样性使用尺度、水平位置和垂直位置的变化范围。Top-5 更适合该任务，因为同一个对象在同一背景中可能有多个合理位置。

### 83. 主要结果是什么？

在 Cityscapes 上，GeoPlace 的 IOU50@1、IOU@1、IOU50@5 和 IOU@5 分别为 6.86、0.265、12.74 和 0.323，均优于对比方法；在 OPA 上除 IOU50@5 外，其余主要准确性指标领先。FID 在 Cityscapes 和 OPA 上分别为 39.76 和 21.71，也是表中最优。

### 84. 消融实验最能说明什么？

完整模型在 Cityscapes 上 IOU@1 为 0.265。去掉两条深度路径后降到 0.197，去掉两项关系正则后降到 0.145；仅保留 patch query、去掉类别与 latent 后降到 0.130。这说明对象条件查询、几何先验和关系约束分别解决身份、空间和多对象稳定性问题，三者具有互补性。

### 85. 为什么单对象任务也能从关系正则中受益？

这些正则虽然由多对象冲突提出，但训练时会让对象表示更可分、注意力分配更稳定，学到的编码与解码参数会迁移到单对象推理。因此它不只是测试时的对象间避碰规则，而是改善了整体表示学习。

### 86. GeoPlace 的局限是什么？

方法依赖估计深度和训练数据中的场景分布，对极端透视、严重遮挡或开放类别对象仍可能失效。当前关系约束主要针对同类别重叠，对更复杂的功能关系、支撑关系和物理碰撞还可以进一步显式建模。

### 87. 两项科研工作的区别是什么？

SceneCom 面向完整图像合成流程，强调 VLM 场景理解、插入质量控制和视觉和谐化；GeoPlace 聚焦放置子任务，强调深度几何和多对象关系。前者解决“从合理位置到高质量合成”的流程问题，后者深入解决“复杂场景中多个对象放在哪里”的建模问题。

# 七、技术基础追问

### 88. 什么是 ReAct？

ReAct 让模型在推理和行动之间循环：根据当前观察决定下一步工具，执行后再利用结果继续判断。Coding Agent 的核心工具循环属于这种范式，但工程实现还需要权限、错误处理、上下文管理和终止条件。

### 89. RAG 与微调有什么区别？

RAG 在推理时检索外部知识，更新快、证据可追溯，适合项目文档和代码知识；微调主要改变模型的行为模式或内化稳定知识，但更新成本更高，也不能天然提供来源。Agent 项目选择 RAG 是因为知识按项目变化且需要显示证据。

### 90. RRF 是什么？

RRF 根据结果在各检索列表中的排名进行融合，常用形式是对每一路累加 1/(k+rank)。它不要求向量相似度和 BM25 分数处于同一尺度，因此适合融合语义检索与关键词检索。

### 91. FTS5 的作用是什么？

FTS5 是 SQLite 的全文检索模块，擅长精确词项、标识符和短语匹配。在本项目中它与向量检索互补，尤其适合函数名、配置项、章节编号等不应只依赖语义相似度的内容。

### 92. AST 与正则解析代码的区别是什么？

AST 基于语言语法，能够识别嵌套结构、函数边界和调用表达式；正则只匹配文本，很容易被注释、字符串和复杂语法干扰。对于代码证据和调用关系，优先使用 AST 或 Tree-sitter，正则只适合简单辅助检索。

### 93. 什么是消融实验？

消融实验在其余设置尽量不变的情况下移除或替换某个模块，观察指标变化，用于判断该模块是否有效以及解决了什么问题。有效消融不仅要报告数字，还要解释变化是否符合模块设计预期。

### 94. 如何保证实验公平？

保持相同数据划分、模型骨干、训练轮数、优化器和评价脚本，只改变待验证因素；对随机性较强的实验应使用多个种子并报告均值和方差。引用他人论文结果时要明确标注，不能与自行复现结果混在一起。

### 95. 过拟合如何判断和处理？

通过训练与验证指标差距、不同数据分布上的泛化和消融稳定性判断。常见处理包括数据增强、正则化、早停、减小模型容量和扩大训练数据；具体选择要结合误差分析，而不是机械叠加手段。

# 八、行为题与压力题

### 96. 遇到过最棘手的问题是什么？

可以回答 Agent 长会话问题：工具输出不断累积，简单截断会丢失后续需要的代码，完全保留又会触发上下文上限。我先把完整结果持久化，再按窗口利用率逐层裁剪和总结，使信息可恢复，并通过长任务对比验证上下文体积和完成率。

### 97. 项目出现分歧时怎么处理？

我会先把分歧转成可验证的问题，例如评价目标是准确率、召回率、成本还是安全性，再设计最小对照实验。对于无法仅靠实验决定的架构问题，会明确约束、风险和维护成本，记录决策依据后推进。

### 98. 如何安排多个任务优先级？

我先区分阻塞主流程的问题、影响结果正确性的问题和体验优化。优先解决会导致任务无法完成或结论不可信的问题，再处理效率，最后完善易用性；每项任务都设置可验证的完成条件。

### 99. 失败经历是什么？

可以选择一次真实实验失败回答：最初方案只看二维外观或只使用单路检索，结果在复杂场景或精确术语上表现不稳定。通过错误样本分类，我确认问题来自几何信息缺失或召回方式单一，再引入针对性模块，并用消融而不是主观样例验证改进。

### 100. 如果入职后接到陌生任务，你会怎么做？

先明确业务目标、输入输出、评价指标和失败边界，再阅读现有代码和数据，建立最小可运行基线。之后通过误差分析确定主要瓶颈，小步迭代，并同步沉淀测试和可追溯记录，避免只做一次性 Demo。

### 101. 为什么我们要录用你？

我的特点不是只会训练模型或只会写业务代码，而是能够把问题建模、算法验证和系统实现连接起来。我有第一作者科研经历，也实现过 Agent 工具链和企业代码审查工具，能够较快进入需要模型能力与工程可靠性并重的任务。

### 102. 你未来三年的规划是什么？

希望继续深耕 AI 算法与 Agent 工程结合的方向，先建立对业务和工程体系的理解，能够独立负责一个完整模块；之后进一步提升模型评估、系统可靠性和复杂任务编排能力，承担从方案设计到上线验证的完整责任。

### 103. 如果模型输出不稳定，你怎么办？

先区分是输入、检索、模型推理还是工具执行导致，再建立可复现样例。可以通过结构化输出、证据约束、重试与回退、阶段校验和人工确认降低随机性；关键结论不能只依赖一次自由文本生成。

### 104. 你的项目是不是只是调用大模型 API？

模型调用只是决策入口，真正的工程工作包括工具协议、异步执行、权限系统、上下文生命周期、结果恢复、会话持久化、混合检索、子 Agent 隔离和测试评估。评价 Agent 项目不能只看是否调用模型，而要看它能否稳定、安全地完成可验证任务。

### 105. 使用了很多现有模型，你的创新在哪里？

使用预训练模型并不等于简单拼接，关键在于如何分配职责和建立新的训练或控制机制。SceneCom 把 VLM 的语义能力限制在场景实体和外观差异描述，把精确定位与像素变换交给专门模型；GeoPlace 则提出对象条件查询、深度双路径注入和关系一致性正则，并通过消融验证各自作用。

### 106. 论文还在投稿，如何证明工作有效？

投稿状态只说明尚未完成同行评审，不能当作成果已被认可。我能提供完整的方法定义、对比实验、消融、定量和定性分析，并如实说明非最优指标和局限；面试时重点讨论研究过程和证据，而不是用投稿去向替代技术价值。

# 九、面试前必须核对的口径

1. GeoPlace 的简历当前写法是 IEEE TMM 在投；SceneCom 的简历当前写法是 Elsevier KBS 在投。不要使用旧自我介绍里的“GeoPlace 投稿 ECCV 2026”或把两篇去向说反。
2. Agent 当前代码有 13 个顶层工具定义、6 种权限模式。部分 README 或文件头仍写“10 个工具、5 种模式”，面试以实际代码和简历为准，并解释版本演进。
3. “30 组任务完成率 73% 到 87%”应准备任务清单、通过标准和前后版本；按整数换算约为 22/30 到 26/30，但必须以原始记录确认。
4. “上下文体积降低 34%”必须确认度量单位、长会话数量、平均方式和是否包含 system prompt。
5. “Recall@5 从 68% 到 86%”必须准备 golden set 样本量、相关性定义、对照配置，以及 MRR/Precision@5 等辅助指标。
6. 一致性审查仓的 21 个运行时与 GitHub 集成测试已在当前环境通过；Agent 仓本次未完整运行，因为当前系统 Python 为 3.9 且缺少项目要求的 Python 3.11 与 SDK/pytest 依赖。
7. 费用报销基准中的合规测试全部符合预设 oracle，只能证明测试样例构造正确；除非有真实盲测输出，不要声称审查模型已经在五个版本上达到 100% 召回。
8. 模型下载插件只回答真实实现。当前简历可确认自动就绪、按需加载和过期清理，断点续传、校验、原子替换等机制需查看真实代码后再说。
