# 朱子墨 AI 面试问答：Coding Agent 项目强追问版

> 适配当前简历项目：**面向企业研发场景的可控 Coding Agent**。  
> 目标不是把项目说成通用 Claude Code 替代品，而是把它讲成“企业私有研发知识 + 可控工具执行 + 上下文治理 + 评测闭环”的 Agent 工程项目。  
> 答案按真实面试节奏组织：先直接回答，再说明评测口径和边界。不要上来讲太多实现细节，除非面试官追问。

---

## 一、项目总述

### 1. 请介绍一下你这个 Coding Agent 项目。

面试官您好，我这个项目是一个面向企业研发场景的可控 Coding Agent。在企业开发中，很多代码任务需要同时参考当前代码仓、项目规范、接口文档和历史问题处理经验，所以我围绕这个场景实现了一个本地 Agent，让它能够在代码仓中读代码、改代码、执行命令，并结合私有知识检索和经验沉淀完成更可控的研发任务处理。

具体来说，在工具执行方面，我设计了文件操作、代码检索、Shell 执行、技能调用和子 Agent 委派等 13 个核心工具，并支持流式调用、并发执行和延迟激活；在上下文和安全控制方面，通过四层压缩机制处理长会话和超长工具结果，并结合六种权限模式、危险命令检测和 read-before-edit 控制修改风险；在经验沉淀与知识库检索增强方面，我把历史问题处理过程提炼成结构化经验文档，同时接入代码规范、设计文档和接口文档，使 Agent 在相似任务中复用排查路径、修改策略和验证方式，并在当前任务中参考项目约束和接口定义。

从效果上看，在多组端到端编程任务中，系统能够稳定完成代码检索、文件修改和命令验证等完整流程；在涉及历史相似问题或规范约束的任务中，能够减少重复探索，并提高任务处理的一致性和可控性。

### 2. 这个项目解决了什么实际问题？

它解决的是企业研发任务里“代码仓、私有知识和执行控制割裂”的问题。比如修一个接口问题，开发者通常要同时看现有代码、接口定义、错误码规范、测试要求和类似历史问题；如果这些信息不能稳定进入 Agent 的执行过程，模型就容易重复搜索、漏掉约束，或者只完成局部修改。

所以我把代码检索、文件修改、命令验证、私有知识检索和经验沉淀放到同一条任务链路里，并用权限模式和上下文治理限制风险。这样 Agent 处理的不只是单个代码片段，而是带有项目约束和验证闭环的研发任务。

### 3. 你这个项目和普通聊天大模型有什么区别？

普通聊天模型主要依赖对话上下文回答问题，而这个项目的核心是任务执行。Agent 会根据任务动态读取文件、搜索代码、修改内容、运行命令，并把工具结果继续回填到后续推理中。

我重点处理的是执行过程中的工程问题：工具怎么编排，错误怎么回填，长上下文怎么治理，写文件和 Shell 怎么做权限控制，以及相似任务经验怎么复用。换句话说，这个项目的重点是把模型能力放进一个可控的代码任务执行框架里。

### 4. 你这个项目和 Claude Code 有什么不同？

我主要从定位上区分。Claude Code 是成熟的通用 Coding Agent 产品，我这个项目更侧重企业研发场景下的可控原型和定向增强，重点围绕私有知识接入、任务经验沉淀、权限控制和离线评测来做。

具体来说，我关心的是企业内部资料怎么进入 Agent 的执行链路，历史任务经验怎么沉淀和复用，长会话中工具结果怎么压缩和恢复，以及代码修改、Shell 执行这些高风险动作怎么通过权限策略控制。

所以我不会把它包装成和 Claude Code 正面竞争的产品，而是强调我完整实现了 Coding Agent 的关键运行链路，并围绕企业研发约束做了可解释、可评测的扩展。

### 5. 如果面试官继续问：Claude Code 也能读文档和调用工具，这算什么创新？

这个问题要落到工程实现和闭环上。文档能被读取是一层能力，文档能被结构化管理、稳定检索、进入任务执行，并在评测里证明有效，是另一层能力。

我的知识库做了结构感知切分、文档和分片元数据管理、向量与关键词双路召回、RRF 融合和二阶段重排；经验沉淀也不是保存聊天记录，而是从任务轨迹中提炼适用场景、排查路径、修改策略和验证方式。检索出来的内容还会进入代码修改、权限控制和命令验证流程，所以重点是“知识接入到研发任务闭环”，而不是单纯把资料放进上下文。

### 5A. 面试官问：你说系统能稳定完成代码检索、修改和验证，这个结论怎么验证？

这个结论来自 30 组固定端到端编程任务的离线评测，而不是单次演示。任务覆盖 bug 修复、测试失败修复、接口字段调整、代码规范修复和小范围重构。每个任务都固定初始代码仓、输入描述、模型、权限模式和最大轮次，并提前写好验收标准。

评测时看四件事：是否检索到关键文件，是否修改了正确文件，是否执行了对应测试或验证命令，最终代码状态是否满足验收。30 组任务里优化后 26 组通过，失败的 4 组主要集中在测试覆盖不足、需求约束不明确和工具路径选择错误。判断依据来自 tool call 轨迹、文件 diff、命令返回码和验收脚本，不以模型最后说“我完成了”为准。

### 5B. 面试官问：你说历史相似任务能减少重复探索，怎么证明？

我把任务分成“历史相似任务”和“全新任务”两类单独统计。历史相似任务里，我用 10 组任务做了经验库开关对照，固定模型、仓库版本、输入和最大轮次，只改变是否启用经验检索。

关闭经验库时，平均 tool call 约 20 次，首次命中关键文件通常在第 5 到第 7 次工具调用；开启经验库后，平均 tool call 降到 15 次左右，首次命中关键文件提前到第 3 到第 4 次工具调用，验证命令复用率从 60% 左右提升到 80% 以上。这个结果说明经验库的收益主要体现在少走重复搜索路径，而不是让模型凭空变强。

### 5C. 面试官问：你说规范约束任务的一致性和可控性提高，怎么测？

这类任务不能只看代码能不能跑，还要看是否满足规范。我在评测里把规范约束单独列成检查项，比如是否使用指定目录结构、是否遵守接口字段定义、是否补充异常处理、日志格式是否符合规范、是否执行指定测试命令。

在 30 组任务中，涉及规范或接口约束的任务有 11 组。开启知识库后，明显减少的是“改了代码但漏掉文档约束”的情况，比如日志格式、错误码处理、接口字段同步这类问题。自动化部分看测试、lint、类型检查；非自动化部分用结构化 checklist 复核。所以这里的一致性和可控性是由检查项和执行轨迹支撑的，不是主观评价。

### 5D. 面试官问：为什么项目介绍里不直接强调具体数值？

项目总述阶段我通常先讲场景和能力，再讲指标。因为这个项目不是单点算法，指标涉及端到端完成率、上下文体积、检索 Recall 和经验采用率，如果一开始直接堆数字，面试官不一定知道这些数字对应哪条链路。

如果追问效果，具体实验口径是：30 组端到端任务里完成率从 73% 到 87%；长会话平均上下文体积下降 34%；知识库 50 条 golden query 上，混合检索 Recall@5 从 68% 到 86%。这样能把数字和验证方法对应起来。

### 5E. 面试官问：这个项目最大的难点是什么？

最大的难点是把模型能力变成一个稳定的工程执行链路。单次让模型回答问题并不难，难的是它在真实代码仓里要反复读取文件、搜索代码、修改文件、运行命令、根据错误继续调整，而且这个过程还要受权限、上下文长度和项目规范约束。

所以我当时重点解决了三类问题：第一，工具调用要可控，不能让模型随意执行高风险操作；第二，长任务上下文要可治理，不能被源码、日志和搜索结果撑爆；第三，私有知识和历史经验要能真正影响执行路径，而不是检索出来之后模型不用。

### 5F. 面试官问：你具体是怎么解决这个难点的？

我把问题拆成了运行时链路来做。工具层面，把读文件、代码搜索、文件编辑、Shell 执行、知识检索、技能调用和子 Agent 委派拆成边界清晰的结构化工具，并在工具执行前做权限判断，执行后把结果结构化回填。

上下文层面，我做了四层压缩和大结果落盘，对长日志和大文件只把预览放进上下文，完整内容保留在本地可恢复。知识层面，我把代码规范、设计文档、接口文档和历史经验做结构化切分，通过向量检索和关键词检索融合召回，再让召回内容进入任务执行过程。最后通过任务轨迹记录和端到端评测去验证这些设计有没有真正改善任务过程。

### 5F-1. 面试官追问：工具执行出错怎么办？

工具错误不能只打印日志，也不能直接让主循环崩掉。我这里的处理方式是把错误转成模型可理解的工具结果回填，比如文件不存在、正则非法、命令失败、权限拒绝、未读先写、文件被外部修改等，都会以明确结果返回给 Agent。

这样模型下一轮可以基于错误继续修正，而不是假设工具成功了。比如 `grep` 正则写错，就返回正则错误；编辑文件前没读过，就返回“先 read_file”；测试命令失败，就把 exit code 和关键 stdout/stderr 返回。任务轨迹里也会记录这次失败，后续可以用于评测和经验沉淀。

### 5F-2. 面试官追问：模型会不会因为工具失败一直重复调用？

这个风险存在，所以我从三层控制。第一，Prompt 层要求模型失败后先诊断原因，不能机械重复同一个动作。第二，工具层返回具体错误原因，让模型有信息调整路径，比如换关键词、重新读取文件、修改命令或请求确认。第三，运行时有硬边界，包括最大轮次、最大成本、Goal 迭代上限、Loop tick 上限和 Auto Mode 拒绝次数上限。

所以我的设计不是靠“模型自觉别重试”，而是错误原因回填加外层停止条件。模型可以恢复，但不能无限消耗。

### 5F-3. 面试官追问：你说有最大次数，具体有哪些？

模型接口的临时错误，比如 `429`、`503`、`529` 或网络抖动，会做指数退避重试，最多重试 3 次，也就是总共最多 4 次尝试。

任务层面可以通过 `--max-turns` 限制 agentic turn，通过 `--max-cost` 限制成本；`/goal` 有 25 次迭代上限，`/loop` 有 100 个 tick 上限；Auto Mode 如果连续拒绝 3 次或累计拒绝 20 次，会回退到人工确认或在无交互环境直接拒绝。这样每个可能循环的地方都有刹车。

### 5F-4. 面试官追问：如果上下文某一次真的超过限制怎么办？

我在设计上尽量把压缩放在接近上限之前触发，而不是等真正溢出之后再处理。系统会根据上下文窗口利用率分级处理：先对超长工具结果做预算裁剪，再把历史工具结果 snip 掉，只保留最近关键结果；更大的结果会提前落盘，只把预览和路径放进上下文；如果仍然接近高水位，再做会话级 compact。

如果某次请求还是因为上下文过长被模型服务拒绝，系统会把它作为可恢复错误处理：先触发更激进的压缩，把旧工具结果和低价值历史内容进一步裁剪，再重试一次请求。当前设计的重点是事前控制上下文体积，尽量避免走到服务端报错；真的报错时也不能直接崩掉，而是进入强制压缩和有限重试。

### 5F-5. 面试官追问：如果预算或轮次到了，但模型已经发出了工具调用，怎么保证消息历史不坏？

这是工具协议里很容易忽略的点。模型一旦发出 tool call，后面必须有对应的 tool result，否则下一轮消息历史可能不合法。

所以预算超限或轮次到达时，我不会直接丢掉这些 tool call，而是给每个未执行工具补一个“未执行，原因是预算或轮次限制”的结果，再停止当前任务。这样用户知道为什么停，模型历史也是完整的，后续恢复和调试不会出现半截工具调用。

### 5F-6. 面试官追问：如果权限拒绝了，闭环在哪里？

权限拒绝会作为工具结果返回给模型，而不是静默失败。比如危险 Shell、越权写入或 plan 模式下试图修改文件，都会返回拒绝原因，并记录到任务轨迹里。

闭环体现在两点：第一，模型不能假装执行成功，它必须根据拒绝原因改方案；第二，评测时可以看到失败是权限策略导致、工具参数导致，还是模型规划错误导致。这样错误不是黑盒，而是可定位、可统计、可改进的。

### 5G. 面试官问：你在做的过程中遇到过什么具体问题？

一个比较典型的问题是工具结果太长。比如一次 `grep` 或测试命令可能返回大量日志，如果原样放进上下文，后续模型很容易被无关内容干扰，也会快速接近上下文窗口上限。

我的解决方式不是简单截断，而是先把超长结果落盘保存，再把摘要、前若干行预览和文件路径放回上下文。这样上下文里保留当前判断需要的信息，同时完整结果没有丢，后续模型需要时可以再读取。

### 5H. 面试官问：还有没有和代码修改相关的问题？

有。早期如果只让模型直接调用编辑工具，可能出现基于过期上下文改文件的问题。比如模型上一轮看到的文件内容已经被用户或其他进程改过，它继续按旧内容生成 patch，就可能覆盖别人的修改。

所以我加了 read-before-edit 和 mtime 检查。系统要求编辑已有文件前必须先读取当前文件，并记录当时的修改时间；如果执行编辑时发现文件 mtime 已变化，就要求重新读取。这样可以把“盲改”和“覆盖外部修改”这类风险在写入前拦住。

### 5I. 面试官问：知识库这块你遇到的难点是什么？

难点是企业资料不是同一种形态，不能都按固定长度切分。代码规范通常依赖标题层级，接口文档可能有表格和字段名，设计文档偏自然语言，历史经验又包含问题现象、排查步骤和验证命令。

我的处理方式是做结构感知切分和元数据管理。Markdown 保留标题路径，PDF/Word 保留页码或章节，CSV 保留表头和行范围，JSON 保留 path；同时给分片保存 heading、tags、source、chunk 序号和 content hash。这样检索命中后，模型拿到的不只是文本片段，还能知道它来自哪份文档、哪个章节、适用于什么约束。

### 5J. 面试官问：经验沉淀这块最容易出问题的地方是什么？

最容易出问题的是把“模型总结”误当成“真实经验”。如果让模型自由总结，它可能把没验证过的步骤写成经验，或者把一次失败尝试也沉淀下来，后面反而误导任务。

所以我采用显式保存和证据校验。用户通过 `/experience save` 触发保存，系统从结构化任务轨迹中提取候选事件，模型只负责把轨迹提炼成经验文档；程序侧会校验引用的事件是否真实存在、是否有成功验证命令、是否包含实质性工程活动。证据不足的经验会标记为 unverified，质量太低的直接 skip。

### 5K. 面试官问：权限控制这块遇到的主要问题是什么？

主要问题是安全和效率之间的取舍。如果所有操作都让用户确认，Agent 会变得很笨重；如果全部自动放行，写文件、Shell 命令和外部工具调用又有风险。

我的做法是按操作风险分层。只读工具尽量自动允许，写文件要求 read-before-edit，危险 Shell 命令进入确认或拒绝，plan 模式只允许探索和规划，auto 模式也有拒绝次数上限和人工回退。这样不是简单“一刀切”，而是让不同风险级别的任务对应不同执行策略。

### 5L. 面试官问：如果让你用 STAR 法讲一个项目难点，你会怎么讲？

在做这个项目时，我发现长任务里工具结果会迅速挤占上下文，尤其是代码搜索、文件读取和测试日志，导致模型后续容易丢失关键目标或重复探索。我的任务是让 Agent 在长会话中仍然能继续执行，并且不丢掉必要证据。

我采取的做法是把上下文治理拆成几层：超长结果先落盘保留完整副本，只把预览放进上下文；旧工具结果按时间和利用率逐步裁剪；必要时再做会话摘要压缩。最后在长任务评测中，Agent 能更稳定地完成读代码、改文件和运行验证的流程，同时上下文占用明显降低。这个难点让我意识到 Coding Agent 的核心不只是模型推理，还包括运行时状态管理。

## 二、指标与评测总口径

### 6A. 面试官问：你这个项目效果怎么样？

我的评估主要分两类：一类是运行效率指标，一类是任务质量指标。

运行效率上，我记录平均 token 消耗、tool call 次数、任务耗时和上下文压缩触发次数。中等复杂度代码任务一般会读取 5 到 8 个文件、修改 1 到 3 个文件、运行 1 到 2 次测试，基础链路通常需要 12 到 25 次工具调用，input token 大概 2 万到 5 万。在 10 组历史相似任务的小规模消融里，开启经验检索后平均 tool call 从 20 次左右降到 15 次左右，input token 从约 4.1 万降到约 3.0 万。

任务质量上，我主要看任务是否完成、是否遵守项目规范、是否执行了正确验证命令、是否出现重复探索。30 组端到端任务里，系统优化后完成率从 73% 提升到 87%。这个提升是系统级结果；经验库的收益主要出现在接口改动、测试失败、规范修复这类历史相似任务上，对完全全新的开放问题提升不明显。

### 6. 你简历里写完成率从 73% 提升到 87%，这个指标怎么来的？

这是在 30 组端到端编程任务上做的对照实验。每个任务都有固定输入、固定代码仓状态和明确验收标准，例如目标功能是否实现、相关测试是否通过、是否满足指定约束。73% 大约是 22/30 个任务通过，87% 大约是 26/30 个任务通过。

对照时我尽量固定模型、任务集、权限模式和最大轮次，只比较优化前后的系统能力。这里的优化不是单一模块，而是工具编排、上下文治理、知识检索和执行控制共同作用后的系统级提升。

具体判通过时，能用测试判定的任务优先看测试、lint、类型检查或指定验证脚本；不能完全自动判定的任务，提前列出验收项，比如是否改到目标模块、是否符合接口约束、是否补充异常分支。任务完成不是由模型自己宣布，而是由外部验收条件决定。

### 7. 面试官问：30 组任务是不是太少，能说明什么？

30 组任务不能证明通用泛化能力，我把它定义为阶段性离线评测。它的价值在于验证系统设计是否有效，并帮助发现失败类型，比如检索失败、上下文丢失、工具调用不合理、测试没有覆盖等。

如果要更严谨地上线评估，需要扩展到更多仓库和任务类型，并对同一任务重复运行多次，报告成功率、工具调用次数、Token、耗时和置信区间。所以我不会把 87% 说成线上生产指标，只说它是在固定任务集上的对照结果。

### 8. 面试官问：这个 14 个百分点到底是谁带来的？

这个提升是系统级结果，不能全部归因给某一个模块。知识库检索提升有 Recall@5 单独证明，上下文治理有平均上下文体积单独证明，但端到端完成率是工具执行、检索、上下文和权限控制共同作用的结果。

我做过较小规模的局部消融：知识库主要改善规范和接口约束类任务，经验库主要减少历史相似任务的重复搜索，上下文治理主要改善长会话稳定性。由于完整消融样本还不够大，我不会把 14 个百分点拆成每个模块各自贡献多少，只把它作为系统级对照结果。

### 9. 面试官问：怎么定义任务完成？

我不以模型最后说“完成了”为准，而是以任务验收条件为准。优先使用可执行验证，比如单测、lint、类型检查、指定脚本或命令返回码；如果任务没有自动化测试，就用事先定义的检查项，例如目标文件是否被正确修改、接口行为是否符合需求、是否满足代码规范。

所以完成率不是主观打分，而是“任务输出是否通过预设验收”。这也是我设计 Shell 执行、权限控制和任务轨迹记录的原因，Agent 的完成状态必须能被外部证据验证。

### 10. 面试官问：怎么证明提升不是模型随机性？

我的对照方式是控制变量。固定同一个模型、同一个代码仓初始状态、同一批任务、同样的权限模式和最大轮次，只改变系统能力是否启用，比如是否开启知识库、是否启用上下文治理。

单次运行确实存在随机性，所以我没有用某一个案例证明效果，而是看一组任务的分布。提升主要集中在历史相似任务、规范约束任务和长上下文任务上；全新任务提升较小。这个分布和系统设计目标一致，更能说明收益来自知识、经验和上下文机制，而不是模型随机变好。

### 10A. 面试官问：你说经验库有用，怎么证明不是知识库或模型本身带来的？

我用三组对照区分这个问题。第一组是基础 Agent，只能看代码仓；第二组开启普通知识库，可以检索规范和设计文档；第三组在普通知识库基础上再开启经验库。这样可以区分“外部文档带来的提升”和“历史处理流程带来的提升”。

在历史相似任务上，普通知识库主要提高规范遵循和接口约束引用，经验库进一步减少了重复搜索和无关文件读取，并提高历史验证命令的复用率。也就是说，知识库解决“当前任务应遵守什么约束”，经验库解决“类似问题以前怎么排查和验证”。

### 10B. 面试官问：你会怎么设计完整实验表？

实验表按任务维度记录：任务 id、任务类型、是否历史相似、初始仓库版本、模型、权限模式、最大轮次、是否开启知识库、是否开启经验库、是否开启上下文治理、最终是否通过、失败原因、tool call 次数、input/output token、耗时、验证命令是否执行。

最后不是只汇总一个成功率，而是分组看结果：相似任务和全新任务分别看，短任务和长任务分别看，有规范约束和无规范约束分别看。这样面试官问“好在哪里”时，我能回答是效率提升、质量提升，还是上下文稳定性提升。

### 10C. 面试官问：如果让我看一个最关键指标，你选哪个？

我选“相似任务的端到端成功率”和“平均工具调用次数”。成功率说明它有没有真的解决问题，工具调用次数说明它有没有减少重复探索。

单独看 token 可能受模型输出风格影响，单独看耗时会受机器和网络影响；tool call 更能反映 Agent 执行路径是否更有效。比较理想的结果是，相似任务成功率提升，同时平均工具调用从 20 次左右下降到 14 到 16 次，input token 从 4 万左右下降到 3 万左右。

## 三、工具编排与任务执行

### 11. 你说有 13 个核心工具，分别解决什么？

简历里的 13 个指基础运行时工具：`read_file`、`write_file`、`edit_file`、`list_files`、`grep_search`、`run_shell`、`web_fetch`、`knowledge_search`、`skill`、`agent`、`enter_plan_mode`、`exit_plan_mode` 和 `tool_search`。这次又增加了 `experience_search` 与 `experience_show` 两个领域检索工具，所以当前内置 schema 实际是 15 个；MCP 工具由外部服务动态发现，不计入这 13 个核心工具。

我不是为了堆工具数量，而是把编程任务拆成权限边界清晰的原子能力。比如读文件和改文件必须分开，代码搜索和 Shell 也必须分开，这样才能做权限控制、日志追踪和后续评测。

### 12. 面试官问：为什么不直接给 Shell？Shell 什么都能做。

只给 Shell 确实功能最强，但权限和可追踪性最差。模型通过 Shell 可以绕过很多安全策略，比如直接覆盖文件、删除文件或执行危险命令，系统也很难结构化记录它到底是在搜索、读取还是修改。

所以我把常见动作拆成独立工具。读文件、检索、编辑和执行命令分别有不同权限策略，后续也能统计每类工具的调用次数、失败率和耗时。

### 13. 延迟激活是什么？为什么需要？

如果把所有工具 Schema 一次性塞给模型，会增加首轮上下文成本，也会干扰模型选择。延迟激活的思路是：高频基础工具直接可见，低频或外部工具先只暴露简要索引，模型需要时通过 tool search 激活完整 Schema。

它的价值主要是减少工具定义占用和降低选择噪声。这是工程优化，不是端到端完成率提升的主要来源。

### 14. 流式调用和并发执行带来了什么实际收益？

流式调用主要改善交互体验和调试可见性，用户可以更早看到模型输出和工具调用趋势。并发执行主要优化探索阶段，例如多个只读文件读取、代码搜索、知识检索可以并发进行，减少等待时间。

但我只对无副作用工具并发，例如 read、list、grep、knowledge search。写文件和 Shell 这类可能改变状态的操作按顺序执行，避免并发修改导致状态不一致。

### 15. 三类 Sub-Agent 是做什么的？

Explore 负责只读探索，适合搜索代码和理解项目结构；Plan 负责生成结构化方案，不直接修改代码；General 负责相对独立的执行任务。

这样做的好处是隔离上下文和权限。主 Agent 不需要承载所有搜索细节，只接收子 Agent 的结论；同时只读探索和可修改执行可以分开控制，降低错误修改风险。

### 16. 面试官问：Sub-Agent 对完成率提升多少？

我不会单独声称 Sub-Agent 提升了多少，因为当前 73% 到 87% 是系统级优化结果。Sub-Agent 的确定价值是上下文隔离和任务分工，尤其适合大仓库探索和多模块并行分析。

单独评估它需要固定任务集，对比单 Agent 和启用 Sub-Agent 的完成率、Token、耗时、主上下文增长量和失败类型。在当前项目里，我把它作为可解释的工程设计，不单独夸大成主要提升来源。

## 三A、工具编排与任务执行强追问

### 16A. 面试官问：工具编排这部分，你到底做的难点是什么？

难点不是把几个函数包装成工具，而是让模型调用工具这件事变得可控、可追踪、可恢复。Coding Agent 在一次任务里会经历多轮“模型决策、工具执行、结果回填、继续决策”，任何一环设计不好都会导致任务跑偏。

所以我重点做了三件事：第一，把文件读写、代码检索、Shell、Skill、Sub-Agent 等能力拆成边界清晰的工具；第二，在运行时加入权限判断、并发调度、流式执行和失败回填；第三，记录工具调用轨迹，用于后续评测和经验沉淀。这样工具系统不是一次性调用，而是一个任务执行框架。

### 16B. 面试官问：模型是怎么决定调用哪个工具的？

模型会根据系统提示中的工具说明和当前任务上下文选择工具。比如需要了解代码结构时，它会优先使用 list 或 grep；需要确认文件内容时使用 read；需要修改时使用 edit/write；需要验证时使用 Shell。

但系统不会完全放任模型。工具被拆成不同权限等级，调用前会经过权限检查；低频工具还做了延迟激活，模型需要时先搜索工具，再拿到完整 Schema。这样既保留模型的动态决策能力，也避免一次性暴露过多工具造成选择干扰。

### 16C. 面试官问：你如何判断模型工具调用是好是坏？

我主要看过程指标和结果指标。过程指标包括 tool call 次数、重复搜索次数、无效工具调用比例、工具失败率、读文件和编辑文件的顺序是否合理；结果指标包括任务是否完成、测试是否通过、是否满足验收条件。

比如一个相似任务，如果开启经验库后 tool call 从 20 次降到 15 次，同时仍然通过测试，说明工具路径更有效；如果 tool call 下降但任务失败，就说明模型可能跳过了必要探索。因此工具调用质量必须和最终任务结果一起看。

### 16D. 面试官问：什么叫无效工具调用？你怎么统计？

无效工具调用可以分几类：重复读取同一信息、grep 查询过宽导致大量无关结果、Shell 命令失败且没有后续修正、编辑前没有读取文件、调用了和当前任务无关的外部工具。

统计上可以从任务轨迹里做规则分析，比如相同 query 的重复 grep、同一文件反复读取但没有后续编辑、失败命令后没有调整参数再次验证。这个指标能帮助判断 Agent 是在有效探索，还是在消耗 token 试错。

### 16E. 面试官问：工具调用失败了怎么办？

工具失败不会直接中断整个任务，而是作为 tool result 回填给模型，让模型基于错误信息调整下一步。比如命令执行失败会返回 exit code、stdout/stderr 摘要；编辑失败会返回找不到字符串或未读文件等原因；权限被拒会明确告诉模型动作没有执行。

关键是不能把失败隐藏掉。如果模型以为工具成功了，后续推理会建立在错误状态上。所以我把失败也作为任务轨迹的一部分，后续既能用于调试，也能用于经验沉淀里的 pitfall。

### 16F. 面试官问：为什么需要 Skill？直接让 Agent 自己规划不行吗？

Skill 适合沉淀稳定流程，比如提交前检查、固定格式生成、项目内特定构建步骤。Agent 动态规划适合路径不确定的问题，比如不知道 bug 在哪里，需要先搜索和判断。

企业落地时，两者应该结合：能流程化的部分做成 Skill，减少模型每次重新规划；开放性定位和决策交给 Agent。这样既保留灵活性，也能降低重复推理成本。

### 16G. 面试官问：Skill 和经验库有什么区别？

Skill 更像可执行流程，适合步骤稳定、输入输出明确的任务；经验库更像可检索的方法论，适合描述某类问题如何排查、有哪些坑、验证方式是什么。

举例来说，“提交前运行哪些命令”可以做成 Skill；“某类接口字段变更通常要查哪些位置、为什么 fixture 容易漏改”更适合作为经验。经验被召回后可以指导模型选择工具，Skill 则可以被模型直接调用执行。

### 16H. 面试官问：Sub-Agent 为什么分 Explore、Plan、General，而不是都用一个？

因为不同子任务的风险和上下文需求不同。Explore 只需要读和搜，不应该有修改权限；Plan 负责产出方案，也不应该直接执行；General 才适合处理相对独立的完整任务。

这个区分本质上是权限隔离和上下文隔离。只读探索可以大胆并行，不会破坏仓库；计划可以让用户确认；真正修改时再进入可执行路径。企业场景里这种分层比一个全权限 Agent 更可控。

### 16I. 面试官问：Sub-Agent 会不会带来成本上升？

会，所以不能滥用。Sub-Agent 会额外产生模型调用和 token 消耗，如果任务很小，直接由主 Agent 完成更合适。

它适合两类情况：第一，大仓库探索，子 Agent 可以隔离大量搜索结果；第二，多条相对独立线索并行排查。评测时要看它是否降低主上下文体积、减少主 Agent 重复搜索、提高成功率，而不是只看有没有用了子 Agent。

### 16J. 面试官问：MCP 外部工具接入解决什么问题？

MCP 主要解决工具生态扩展问题。内置工具覆盖本地文件和 Shell，但企业环境里可能还需要接 Jira、GitLab、内部文档、CI、监控平台等外部系统。如果每个都写死在 Agent 里，扩展和权限管理会很混乱。

通过 MCP，外部工具可以按统一协议暴露给 Agent，系统只需要负责发现工具、转发调用和接收结果。这样 Agent 运行时和工具生态解耦，后续更容易接入企业内部平台。

### 16K. 面试官问：工具并发如何保证正确性？

我只对无副作用工具并发，比如读文件、列目录、代码搜索、知识检索。这些工具不会修改外部状态，即使并发执行，结果之间也不会互相覆盖。

对写文件、Shell、计划模式切换、外部状态修改这类有副作用动作，我按顺序执行，并且先做权限判断。这个原则是：探索阶段可以并发，修改和验证阶段要保守。

### 16L. 面试官问：Shell 命令为什么不并发？测试并发不是更快吗？

Shell 的副作用很难判断，它可能改文件、启动服务、占用端口、写缓存或依赖当前工作目录状态。即使看起来是测试命令，并发也可能造成资源竞争或日志混乱。

所以我默认把 Shell 当成高风险工具顺序执行。如果未来要支持 Shell 并发，需要先做命令分类和隔离，比如只允许明确只读的命令并发，或者在临时目录/容器里执行。

### 16M. 面试官问：流式工具调用有没有一致性问题？

有这个风险，所以流式执行只能在工具参数完整、工具属于并发安全集合、权限判断通过后才启动。不能在模型还没生成完整参数时就执行，也不能让需要权限确认的工具提前跑。

我把流式主要用于提升交互可见性和缩短安全只读工具的等待时间，不会为了速度牺牲权限检查和状态一致性。

### 16M-1. 面试官问：流式输出具体是怎么做的？

流式输出本质上是把一次完整模型响应拆成事件流来消费，而不是等模型整轮生成结束后一次性展示。实现上，系统会持续监听模型返回的流式事件，比如文本增量、thinking 增量，以及 tool call 的 partial JSON。

当文本增量到来时，直接实时打印到终端；当 tool call 还在生成参数时，系统先在内存里拼接参数 JSON；只有当这个 tool block 完整结束后，才会把它解析成真正的工具调用。这样既能给用户实时反馈，也能避免半截参数就触发工具执行。

### 16M-2. 面试官问：那工具是等模型说完再执行，还是边输出边执行？

两种情况都有。对于普通情况，模型输出完一轮后再统一执行工具；但对于只读、无副作用、权限已经自动允许的工具，我支持在流式过程中提前启动执行。

比如模型正在继续生成后半段内容时，如果前面一个 `read_file` 或 `grep_search` 的 tool block 已经完整闭合，系统可以立刻启动这个工具，让工具执行时间和模型剩余输出时间重叠。这样能缩短等待时间，但只对并发安全工具开放。

### 16M-3. 面试官问：为什么不对所有工具都提前执行？

因为很多工具有副作用，提前执行风险很高。比如写文件、运行 Shell、调用外部系统，如果在权限判断前或参数还不稳定时就启动，可能造成错误修改或越权操作。

所以我把“流式提前执行”限制在无副作用工具和自动允许场景里。写操作、Shell、需要确认的动作仍然要等参数完整、权限确认通过后再执行。

### 16M-4. 面试官问：用户在界面上具体会看到什么？

这是一个终端 REPL 界面，不是图形化网页。正常交互里，用户会先看到输入提示符；提交任务后，如果模型还没开始吐字，会先看到一个 spinner；一旦模型开始流式输出，终端会像聊天一样逐字或逐段显示文本。

如果模型触发工具调用，界面会打印工具名和参数摘要；工具执行完成后，会继续显示工具结果摘要。也就是说，用户看到的是“模型文本输出 + 工具调用提示 + 工具结果提示”交替出现，而不是最后一次性给一个完整答案。

### 16M-5. 面试官问：这个界面长什么样，能不能用一句话描述？

可以把它理解成开发者终端里的 Agent 对话界面。左侧是连续的文本输出流，中间会穿插工具调用和结果提示，底部是下一轮输入提示。它更像一个带工具执行日志的对话式命令行，而不是单纯 shell，也不是网页聊天框。

### 16M-6. 面试官问：流式输出里如果有 thinking，会不会直接暴露给用户？

取决于模型和配置。实现上，thinking 也是流式事件的一种，可以单独显示，也可以在最终存储时过滤掉。我的设计更偏工程可控：如果开启 thinking，终端可以显示一个 `[thinking]` 段落，便于调试；但真正保存到最终消息历史时，不会把这类不稳定内容当成长期上下文的一部分。

这样做的原因是 thinking 对调试有帮助，但如果直接长期保留，会影响缓存稳定性，也可能污染后续上下文。

### 16M-7. 面试官问：流式输出对用户价值是什么？

第一是等待感更低。用户不用等完整一轮结束，能尽早看到模型是在读代码、解释问题，还是准备调用工具。第二是可观察性更好，如果模型明显跑偏，用户可以更早中断。第三是对只读工具可以和模型剩余生成并行，缩短任务总等待时间。

所以流式输出的主要价值不是提高正确率，而是提升交互体验、可调试性和部分场景下的响应效率。

### 16M-8. 面试官问：流式输出怎么和会话保存、上下文管理配合？

流式只是展示和调度方式，不改变最终进入会话历史的结构。最终保存到消息历史里的，仍然是完整的 assistant message 和完整的 tool result，而不是零散的字符流。

这样做有两个好处。第一，用户看到的是实时输出，但系统内部仍然保留结构化消息；第二，上下文压缩、任务轨迹记录和经验提炼处理的都是最终结构，而不是中间的流式碎片。

### 16M-9. 面试官问：如果流式过程中用户中断，会发生什么？

如果用户中断，系统会停止当前任务，并尽量在安全边界内取消尚未完成的执行。对于主 Agent 来说，中断首先作用在当前处理任务上；对于循环任务或目标驱动任务，也会触发相应 stop 标志。

这个场景下流式输出的好处也比较明显，因为用户通常能更早发现模型跑偏，而不是等整轮结束后才发现问题。

### 16N. 面试官问：如果模型工具参数写错，比如路径错了，系统怎么处理？

路径错、命令错或 edit 匹配失败，工具会返回明确错误，而不是静默失败。模型下一轮可以根据错误重新 list、grep 或 read，修正路径和参数。

这类错误也会进入任务轨迹。评测时可以统计工具参数错误率，如果某类错误频繁出现，说明工具描述、Schema 或提示需要优化。

### 16O. 面试官问：为什么强调 13 个核心工具，而不是更多工具？

因为工具不是越多越好。工具太少会导致 Shell 滥用，工具太多会增加 Schema 成本和选择噪声。我选择的是覆盖编程任务闭环的最小核心集合：读、搜、改、执行、知识检索、工作流复用和任务委派。

企业真正落地时，其他工具应该通过 MCP 或 Skill 扩展，而不是全部塞进核心工具集。核心工具保持稳定，业务工具按需接入。

### 16P. 面试官问：任务执行的停止条件是什么？

正常情况下，当模型不再产生 tool call，而是输出最终回复时，当前任务收敛。但我不会仅凭这一点判断任务成功，成功还要看外部验收条件，比如测试通过、指定文件修改完成、需求约束满足。

这也是为什么经验保存不能用“最后没有 tool call”自动触发。停止调用工具只代表模型结束当前轮执行，不等于任务一定正确完成。

### 16Q. 面试官问：工具编排对 73% 到 87% 的提升贡献多少？

我不会单独给工具编排一个夸大的百分比，因为 73% 到 87% 是系统级结果。工具编排的贡献主要体现在减少无效调用、提升错误恢复能力和让任务执行可验证。

如果要单独测，可以做消融：关闭延迟激活、关闭并发、禁用 Sub-Agent、禁用 Skill，分别看完成率、tool call、token 和耗时变化。没有单独消融前，我只会说工具编排是系统完成率提升的基础组件之一。

### 16R. 面试官问：如果工具执行结果很长，怎么避免模型被干扰？

这和上下文治理配合处理。工具层会返回结果，Agent 层会对超过阈值的结果做持久化和预览，只把当前必要部分放进上下文，完整内容保留在本地可恢复。

这样模型不会被长日志或大文件淹没，但如果后面需要完整结果，可以根据路径重新读取。这比简单截断更可靠。

### 16S. 面试官问：你这个东西为什么是 CLI，而不是网页？

我把它做成 CLI，主要是因为 Coding Agent 的核心工作对象就是本地代码仓、文件系统和 Shell。CLI 形态更贴近开发者真实工作流，也更容易直接接入读文件、改文件、运行命令、查看日志这些动作。

另外，CLI 更适合做原型验证。它能让我先把模型循环、工具调用、权限控制、上下文治理和知识库打通，而不用过早把精力花在前端交互上。对这个项目来说，核心价值在运行时和评测链路，不在界面包装。

### 16T. 面试官问：CLI 具体怎么用？

它支持 one-shot 和交互两种方式。one-shot 是直接给一个 prompt 执行一次任务；交互模式下是一个 REPL，用户可以持续提任务，也可以用命令管理会话和知识库。

比如用户可以用 `/kb add` 导入知识文档，`/kb search` 测试检索，`/experience save` 保存经验，`/experience show` 和 `/experience delete` 管理经验，`/plan` 进入只读规划模式，`/cost` 查看 token 和成本。这个设计说明它不只是“调一次 API”，而是一个可操作的开发工具。

### 16U. 面试官问：为什么可以叫 code harness？

这里的 harness 不是指测试框架，而是指“把模型、工具、权限、上下文和评测组织起来的运行底座”。模型本身只负责推理，真正让它能稳定处理代码任务的是外层执行框架。

所以叫 code harness，强调的是它把代码相关的文件操作、命令执行、知识检索、权限判断和结果回填串成一条可控链路。也就是说，harness 体现的不是某个单独功能，而是把模型约束在一个可执行、可验证的代码任务环境里。

### 16V. 面试官问：这个项目里哪里体现了 harness？

主要体现在四个地方。第一，工具层把读、搜、改、执行拆成结构化接口，而不是让模型直接输出随意命令。第二，运行时负责权限判断、流式执行、并发调度和失败回填。第三，上下文治理和任务轨迹记录负责维持长任务状态。第四，知识库和经验库让模型能用企业资料和历史流程完成任务。

换句话说，模型不是直接面对代码仓裸跑，而是运行在我搭建的这套执行和控制框架里，这就是 harness 的含义。

### 16W. 面试官问：系统 prompt 是怎么设计和组织的？

我把 Prompt 做了分层组织。基础层是静态系统 prompt，放通用行为约束、工具使用规则、安全边界和输出风格；动态层是和当前项目相关的环境信息，以及 Memory、Knowledge、Experience、Skills 等轻量索引；`CLAUDE.md`、rules 和日期通过首条 user reminder 注入。知识正文和完整经验不常驻 System Prompt，而是在相关工具命中后作为 tool result 进入当前消息历史。

这样做有两个好处。第一，静态部分稳定，便于缓存和复用；第二，动态部分可以随着项目状态变化刷新，比如导入新知识文档后，只更新动态上下文，而不必重写整段系统提示。

### 16X. 面试官问：为什么要把系统 prompt 分成静态和动态两层？

一方面是工程可维护性。静态规则比如工具使用规范、权限原则、交互风格相对稳定；动态内容比如知识库清单、项目环境、日期、技能列表会变化，如果全写在一起，维护成本高，也不利于调试。

另一方面是为了提高缓存命中和减少无谓重传。静态部分长期不变，更适合放在可缓存前缀里；动态部分只在需要时更新。对于长会话和频繁交互来说，这样更合理。

### 16Y. 面试官问：系统 prompt 里主要约束模型什么？

主要约束三类东西。第一是任务行为，比如优先使用专用工具而不是滥用 Shell、并行只用于独立只读操作、复杂任务要先规划；第二是安全边界，比如权限被拒后不能假装执行成功、不能绕过工具规则；第三是交互规范，比如回答风格、何时继续调用工具、何时结束。

这些约束的目标不是把模型写死，而是减少明显错误路径，让模型在代码任务里更像一个受控执行体，而不是单纯聊天模型。

### 16Z. 面试官问：知识库、Skills、日期这些为什么也要进 prompt？

因为模型需要知道当前有哪些外部能力和项目知识可用。比如不知道知识库里有什么，它就不会主动用 `knowledge_search`；不知道有哪些 Skills，它就不会把稳定流程委派出去；不知道日期和环境信息，某些路径或时效性判断也会偏。

但我不会把全文资料直接塞进系统 prompt，而是只放索引和能力说明。真正需要某份文档内容时，再通过检索或工具读取。这也是 prompt 和知识库分工的边界。

### 16AS. 面试官问：如果工具执行出错，系统是怎么处理的？

我的原则不是让异常把主循环打崩，而是尽量把错误收敛成结构化结果回填给模型。大部分工具失败不会直接抛到最外层，而是返回明确的错误字符串，比如路径不存在、命令失败、正则非法、URL 请求失败、文件未先读取等。

这样模型下一轮可以根据真实错误继续修正参数、改走其他路径，任务轨迹里也会留下对应的 `tool_result` 或 `permission_denied` 证据。也就是说，错误会进入执行闭环，而不是只停留在日志里。

### 16AT. 面试官问：工具失败后，模型会不会无限重试？

我没有把“无限重试”当成正常恢复策略。系统层面做的是把失败原因明确返回，比如 `Command failed`、`Action denied`、`read_file first`、`modified externally`，让模型必须基于新证据调整方案，而不是盲目重复同一个动作。

另外，预算、最大轮次、goal/loop 上限和 Auto Mode denial limit 都会作为外层刹车，防止模型在错误路径上无休止消耗 token。Prompt 里也明确约束了“失败后先诊断，不要机械重试相同行为”。

### 16AU. 面试官问：网络或模型接口出错时，最大重试次数是多少？

流式模型请求这一层有统一重试包装。当前对 `429`、`503`、`529` 以及部分网络错误会做指数退避重试，最大是 3 次重试，也就是总共最多 4 次尝试。

这里的目的是处理临时性故障，比如限流和短暂网络抖动；如果超过上限或者错误类型不可重试，就直接向上返回，不会一直卡住。这样既有基本韧性，也有明确边界。

### 16AV. 面试官问：为什么你只对一部分错误做自动重试？

因为不是所有错误都适合重试。像参数错误、路径错误、权限拒绝、非法正则、读写前置条件不满足，这些本质上是逻辑错误或约束错误，重复执行不会自己变对。

所以我只对典型瞬时错误做自动重试，把可恢复性和可解释性分开处理。瞬时错误靠重试吸收，逻辑错误回填给模型修正。

### 16AW. 面试官问：如果流式过程中失败并重试，会不会有副作用重复执行？

会有这个风险，所以我把流式提前执行严格限制在并发安全、无副作用、权限已自动允许的工具上，比如读文件、列目录、代码搜索这类只读工具。

写文件、危险 Shell、外部写操作这类有副作用的工具，不会因为流式块提前闭合就马上执行，而是要等参数完整、权限通过后再执行。这样即使流请求重试，也不会把高风险操作重复触发。

### 16AX. 面试官问：权限拒绝后系统怎么闭环，而不是直接卡死？

权限拒绝不是静默吞掉，而是会作为工具结果回填给模型，同时在任务轨迹里记录 `permission_denied`。模型下一轮必须基于这个事实调整方案，比如改成只读解释、请求用户确认，或者换用低风险替代路径。

这点很关键。真正的闭环不是“拦住了就结束”，而是“拦住了以后系统状态仍然一致，模型知道为什么没执行，并能选择下一步”。

### 16AY. 面试官问：Auto Mode 如果分类器一直拒绝，怎么防止陷入拒绝循环？

这里专门做了 denial limit。当前阈值是连续 3 次拒绝，或者累计 20 次拒绝，一旦达到上限，就认为分类器可能陷入了 refusal loop。

这时系统不会继续把动作交给分类器反复判，而是回退到人工确认；如果是无交互环境，就直接 deny。也就是说，Auto Mode 不是无限相信分类器，而是把它放在一个有上限、有回退的框架里。

### 16AZ. 面试官问：除了 Auto Mode，你还有哪些“最大次数”或“停止条件”设计？

主要有四类。第一，模型接口重试最多 3 次。第二，`/goal` 有硬上限，最多 25 次迭代，避免 no-tool 场景一直兜圈。第三，`/loop` 有硬上限，最多 100 个 tick，同时也受 `--max-turns` 和 `--max-cost` 约束。第四，普通任务执行也受最大轮次和预算控制。

这些上限的目标不是保守，而是防止系统在错误路径上无限放大成本。

### 16BA. 面试官问：预算超了之后系统怎么处理，为什么说这是闭环的一部分？

预算超限时，我不会简单中断而破坏消息结构。因为在工具调用协议里，已经发出的 `tool_use` 或 `tool_call` 必须收到配对的结果，否则下一轮历史会失效。

所以预算超限后，系统会给尚未执行的工具补一个“未执行，原因是预算超限”的结果，再停止当前任务。这样消息历史仍然合法，模型和后续调试都能知道停在哪、为什么停。

### 16BB. 面试官问：如果用户中断任务，系统怎么保证状态不乱？

中断不是直接把进程杀掉，而是通过 `_aborted`、`goal_stop`、`loop_stop` 这些标志去停止当前执行路径。这样主循环、goal 和 loop 都有各自的退出判断，不会出现某一层已经停止、另一层还继续跑的情况。

所以中断处理本质上也是一种闭环设计：有统一信号，有各层检查点，有明确的退出分支。

### 16BC. 面试官问：read-before-edit 算不算错误预防机制？

算，而且它比事后补救更重要。系统要求模型在写文件或编辑文件前，必须先读过当前文件；如果文件在读取后又被外部修改过，还要因为 mtime 变化而重新读取。

这解决的是两类高频问题：第一，模型凭猜测盲改；第二，覆盖用户或其他进程刚改过的内容。它不是在错误发生后恢复，而是在错误发生前阻断。

### 16BD. 面试官问：长工具结果会不会本身造成错误，比如把上下文冲爆？

会，所以我把这也当成运行时错误预防。超过阈值的大结果不会原样塞进上下文，而是先持久化到本地文件，再把预览和路径放回上下文。

后续如果模型真需要完整内容，可以再通过 `read_file` 回读。这比直接截断更稳，因为完整证据没有丢，只是从“内联上下文”转成了“可恢复外部引用”。

### 16BE. 面试官问：Sub-Agent 或 Skill 执行失败会不会把主 Agent 一起带崩？

不会直接带崩。无论是 `agent` 工具创建的 Sub-Agent，还是 `skill` 的 fork 模式，外层都有异常捕获，失败后会返回 `Sub-agent error: ...` 或 `Skill fork error: ...` 这样的结果字符串。

这样主 Agent 仍然能接住结果，决定是否改走主链路、换一个技能、或者把失败信息反馈给用户。也就是说，子任务失败被收敛成主任务可消费的结果，而不是未处理异常。

### 16BF. 面试官问：Session、Knowledge Base 这些外围模块出错时怎么办？

这些模块我更偏向降级而不是拖垮主流程。比如 Session 文件损坏或读取失败时，`load_session()` 会直接返回 `None`，表示本次不恢复，但 CLI 仍可继续启动；Session 自动保存失败也会被吞掉，避免会话因为持久化问题崩掉。

知识库文档导入则会把文档状态标成 `FAILED` 并记录 error，而不是让整个知识库不可用。也就是说，外围模块出问题时优先局部失效、主流程继续。

### 16BG. 面试官问：你怎么判断一个错误处理设计是不是“工程闭环”？

我主要看四个问题。第一，错误能不能被检测到，而不是静默失败。第二，错误能不能被结构化返回给上层，而不是只留一条日志。第三，系统有没有停止条件和回退路径，避免无限重试或状态失配。第四，后续有没有证据可追踪，比如轨迹、状态字段、失败原因。

如果一个设计只做到 try/except，不记录、不回填、不限流、不留证据，那不算工程闭环，只算防崩。

### 16BH. 面试官问：如果要评测错误处理能力，你会怎么测？

异常场景需要单独评测，不能只看正常任务完成率。我覆盖的典型场景包括非法路径、未读先写、文件被外部修改、危险 Shell、工具参数错误、网络 429、知识库文档解析失败、Auto Mode 连续拒绝、流式中断和预算超限。

指标上至少看四类：错误拦截率、错误后恢复成功率、无限重试占比、失败原因可解释率。这样才能证明系统不只是“跑得通”，而是在出错时也有可控行为。

### 16AA. 面试官问：如果面试官问“你这个 prompt 有什么特别创新的地方”怎么答？

我不会把创新点夸到 prompt 本身。我的说法会是：prompt 的价值在于把工具使用规则、权限边界、项目动态上下文和知识入口组织清楚，让模型在一个稳定的执行框架里工作。

真正有工程价值的不是一句神奇提示词，而是 prompt、工具、权限、上下文治理和知识库一起组成的运行时。这样回答更稳，也更像真实工程项目。

## 四、上下文治理与安全控制

### 17. 你为什么要做上下文压缩？

Coding Agent 的上下文增长主要来自工具结果，而不是模型回复。一次中等复杂度任务可能要读 5 到 8 个文件、grep 多次、运行测试并读取错误日志；这些内容如果全部保留，很快会占满上下文，也会让模型在旧信息里迷失。

但直接截断又有风险，因为后续可能需要恢复某个日志或代码片段。所以我的目标不是简单压缩，而是优先移除可恢复信息，保留任务状态、最近证据和恢复路径。

### 18. 四层压缩机制具体怎么做？

第一层是工具结果预算控制：当窗口利用率超过 50% 时开始限制工具结果体积，超过 70% 后进一步收紧。第二层是过期结果裁剪：超过 60% 后对旧的 read、grep、list、shell 结果做 snip，默认保留最近 3 个完整结果。第三层是空闲清理：会话空闲超过 5 分钟后做微压缩。第四层是全局摘要：超过 85% 时才对会话做摘要压缩。

另外，单个工具结果超过 30KB 时，会先把完整结果保存到本地，再返回预览和恢复路径。这样模型当前能继续工作，必要时也可以重新读取完整结果。

### 19. 面试官问：这是 KV Cache 压缩吗？

不是。我的压缩是应用层上下文治理，处理的是每次请求前发送给模型的消息历史和工具结果，不修改模型内部 KV Cache。

同时要考虑 Prompt Cache 的命中问题。缓存仍然有效时，不轻易改写历史前缀；只有上下文利用率进一步升高时，才优先保证不溢出。这也是我没有简单每轮都摘要的原因。

### 20. 平均上下文体积降低 34% 是怎么测出来的？

我的测法是固定一组长链路任务，对比开启上下文治理前后，每轮请求进入模型的上下文估算 token，记录任务过程中的平均上下文体积和峰值上下文体积。34% 指的是这组长会话任务中，开启治理后平均输入上下文体积相比基线下降的比例。

基线是保留完整工具结果和完整历史；实验组开启结果预算、旧结果裁剪、大结果持久化和摘要。这个指标说明系统减少了无效历史和超长工具输出的占用，但不代表模型内部计算被压缩，也不等于耗时一定下降 34%。

### 21. 面试官问：上下文体积降低会不会导致信息丢失，影响任务完成？

会有这个风险，所以我把压缩顺序设计成从可恢复信息开始。超长结果会先落盘，模型拿到的是预览和路径；旧工具结果会被裁剪，但最近 3 个结果保留完整；只有上下文接近高水位时才做全局摘要。

评测时不能只看 token 下降，还要看任务完成率是否下降、是否出现“需要的信息被压掉”的失败。如果压缩后 token 降了但完成率明显下降，那就是失败设计。

### 22. 你做了哪些安全控制？

我做了六种权限模式，用来控制不同场景下工具是否自动执行、是否需要确认、是否只允许规划。对于危险 Shell 命令会单独检测；对代码修改做 read-before-edit，要求修改前必须读过文件，并检查文件 mtime 是否变化。

这样可以避免模型在没看当前文件内容时盲改，也能防止用户或其他进程改了文件后，模型基于过期上下文继续写入。

### 23. read-before-edit 的价值怎么评估？

它主要提升可靠性，不一定提升速度。可以统计三类指标：未读文件编辑拦截次数、文件被外部修改后的拦截次数、以及因此避免的覆盖风险。

这个机制的价值不是让模型更聪明，而是把工程修改风险前置拦截，尤其适合多人协作或本地文件状态频繁变化的场景。

## 四A、上下文治理与安全控制强追问

### 23A. 面试官问：上下文治理这部分最核心的设计目标是什么？

核心目标是让长任务不因为上下文膨胀而失控，同时尽量不丢掉后续排查需要的信息。Coding Agent 的上下文里最大的问题通常不是模型回复，而是工具结果，包括源码、grep 输出、测试日志和文档片段。

所以我不是简单做摘要，而是做分层治理：先限制新结果体积，再处理旧的可恢复结果，再做空闲清理，最后才做全局摘要。设计原则是优先压缩可恢复信息，尽量保留任务状态和最近证据。

### 23B. 面试官问：你怎么判断哪些内容可以压缩，哪些不能压缩？

可以压缩的是可恢复、过期、重复或者低价值的工具结果，比如旧的 read_file、grep_search、list_files、run_shell 输出。不能轻易压缩的是用户最新需求、当前计划、最近的工具结果、错误原因和验证结论。

对于超过 30KB 的大结果，系统会先把完整内容保存到本地，再返回预览和恢复路径。这样模型上下文里只保留摘要，但信息没有真正丢失。

### 23C. 面试官问：为什么保留最近 3 个工具结果？

这是一个工程折中。最近几次工具调用通常和当前决策最相关，比如刚读的文件、刚失败的测试、刚修改后的验证结果。如果全部裁剪，模型容易丢掉当前状态。

保留 3 个不是理论最优值，而是为了在信息保留和上下文占用之间取平衡。更严谨可以通过实验调参，比如比较保留 1、3、5 个结果时的任务成功率和上下文体积。

### 23D. 面试官问：你这些阈值 50%、60%、75%、85% 是怎么来的？

这些阈值是按上下文风险阶段设计的工程参数。50% 时风险还不高，先控制单次工具结果；60% 时开始处理旧内容；75% 时说明接近高水位，即使会影响缓存，也要优先避免溢出；85% 时才做全局摘要，因为摘要信息损失最大。

我不会说这些阈值是理论最优。它们是可调参数，应该通过长任务评测继续优化，比如看不同阈值下的上下文体积、compact 次数、任务成功率和缓存命中。

### 23E. 面试官问：你怎么证明上下文压缩没有伤害效果？

不能只看上下文体积降低，还要同时看任务完成率和失败原因。我的评测会对比开启和关闭上下文治理，在同一批长链路任务上统计平均上下文 token、峰值 token、完整 compact 次数、任务成功率和“信息被压掉导致失败”的次数。

如果上下文降低 34%，但成功率明显下降，那说明压缩过激。理想结果是上下文体积下降，同时任务成功率不下降，甚至因为减少旧噪声而略有提升。

### 23F. 面试官问：如果压缩掉的信息后面又需要，怎么办？

大结果会保存完整副本，返回给模型的是预览和本地路径；旧工具结果被 snip 后，模型可以重新 read 或 grep 获取当前需要的信息。也就是说，我尽量把压缩设计成可恢复，而不是永久删除。

只有全局摘要属于信息损失更大的操作，所以它放在 85% 高水位才触发。这样可以降低关键细节过早丢失的风险。

### 23G. 面试官问：上下文压缩和知识库/经验库有什么关系？

知识库和经验库会增加额外上下文，因为模型需要读规范、设计文档和历史经验。如果没有上下文治理，私有知识增强反而可能挤占代码和测试日志空间。

所以这几个模块是配套的：知识库负责提供外部依据，上下文治理负责控制这些依据和工具结果的生命周期，经验持久化则避免把已完成任务完全依赖短期上下文记忆。

### 23H. 面试官问：Prompt Cache 和上下文压缩会冲突吗？

会有一定冲突。Prompt Cache 依赖稳定的前缀，如果频繁改写历史消息或每轮都摘要，会降低缓存命中。所以上下文没有接近高水位时，我尽量不改写稳定历史，只控制新工具结果和旧的可恢复内容。

当上下文利用率到 75% 或 85% 以上时，避免溢出的优先级高于缓存命中。这是成本和可靠性的权衡，不是单纯追求压缩率。

### 23I. 面试官问：你说平均上下文体积降低 34%，具体怎么采样？

每个任务运行过程中，系统记录每轮发给模型前的上下文估算 token，包括消息历史、工具结果和知识注入内容。对一组长任务求平均，比较开启治理和关闭治理两种配置。

这里的 34% 是平均上下文体积下降，不是总 token 成本一定下降 34%。因为总成本还受任务轮数、模型输出长度、缓存命中和是否额外调用经验提炼模型影响。

### 23J. 面试官问：有没有统计压缩触发次数？

这是应该统计的指标。一次长任务里可以记录各层压缩触发次数，比如结果预算收紧次数、旧结果 snip 次数、大结果落盘次数、microcompact 次数、full compact 次数。

这些指标能帮助判断策略是否健康。如果 full compact 频繁触发，说明前面几层治理不够；如果 snip 太多导致任务失败，说明阈值或保留策略过激。

### 23K. 面试官问：安全控制为什么需要六种权限模式？

因为不同使用场景对自动化和风险的要求不同。个人本地快速实验可以更激进，企业代码仓修改就必须保守；CI 场景可能需要自动拒绝交互确认；规划阶段则应该只读不改。

六种权限模式的价值是让同一个 Agent 运行时适配不同风险级别，而不是所有场景都用一套权限策略。

### 23L. 面试官问：六种权限模式分别怎么解释？

可以简化成这样说：默认模式会对风险操作请求确认；plan 模式只允许规划和只读探索；accept-edits 可以自动接受文件编辑但仍控制危险命令；bypassPermissions 用于可信本地快速实验；dontAsk 适合 CI 或非交互场景，遇到需要确认的动作直接拒绝；auto 模式会用模型分类器判断工具调用风险。

面试中不需要死背每个内部细节，重点说清楚它们覆盖了从只读规划到快速执行、从人工确认到自动拒绝的不同安全级别。

### 23M. 面试官问：auto 权限模式让模型判断风险，会不会不可靠？

会有风险，所以 auto 模式不能无限信任分类器。我的设计里，高风险或不确定操作仍然可以回退到人工确认或拒绝；同时会统计连续拒绝次数，避免模型不断尝试被拒动作。

如果在企业场景上线，auto 只能作为辅助分类，而不是最终安全边界。最终还需要确定性规则，比如危险命令黑名单、路径白名单、写权限范围和人工审批。

### 23N. 面试官问：危险命令怎么判断？

危险命令主要看是否会造成不可逆破坏、越权访问或影响外部状态，比如删除文件、修改权限、清理仓库、推送代码、安装未知脚本、访问敏感路径等。系统会对 Shell 命令做静态检测，命中高风险模式时要求确认或拒绝。

但静态规则不可能覆盖所有情况，所以 Shell 默认比 read/grep 更保守。企业落地时还应结合路径限制、容器隔离和命令白名单。

### 23O. 面试官问：read-before-edit 为什么必要？

因为模型可能基于过期上下文或猜测直接修改文件，这在真实代码仓里风险很高。read-before-edit 要求编辑前必须读取当前文件内容，并记录文件 mtime；如果文件被外部修改过，就要求重新读取。

这个机制解决的是“盲改”和“覆盖用户改动”的问题。它不一定提高速度，但能提高工程可靠性。

### 23P. 面试官问：read-before-edit 会不会降低效率？

会增加一次读取成本，但这是值得的。代码修改是高风险动作，先读取文件可以让模型基于当前内容生成 patch，也能让系统检查文件是否被外部改动。

如果任务很小，这个成本可能显得明显；但在企业代码仓里，避免一次错误覆盖比省一次 read_file 更重要。

### 23Q. 面试官问：如何评测安全控制有效？

可以构造一组安全测试任务，包括未读文件直接编辑、读取后文件被外部修改、危险 Shell 命令、越权路径写入、计划模式下尝试修改等。指标看拦截率、误拦截率和绕过率。

比如 read-before-edit 应该拦截 100% 未读文件编辑；危险命令检测要尽量提高召回，但也要关注误报。安全评测不能只看功能任务完成率，还要看高风险动作有没有被正确拦截。

### 23R. 面试官问：安全控制会不会影响任务完成率？

会有可能，尤其是权限过严时，模型可能无法执行必要验证或修改。所以安全控制需要和任务完成率一起评估。

我的原则是：只读探索尽量放开，写入和外部副作用严格控制。这样可以让 Agent 充分收集信息，同时在真正改变代码或环境前进入确认和校验流程。

### 23S. 面试官问：如果用户拒绝了工具调用，Agent 怎么办？

拒绝结果会作为工具结果返回给模型，模型不能假设动作已经执行。它应该调整方案，比如改用只读方式解释、请求用户手动执行，或者选择更低风险的替代路径。

这个拒绝事件也会进入任务轨迹，用于分析任务失败原因。如果很多任务因为权限拒绝失败，说明权限策略或任务提示需要调整。

### 23T. 面试官问：计划—确认—执行机制怎么发挥作用？

复杂或高风险任务先进入 Plan，模型只读探索并产出修改方案；用户确认后，系统再按权限切换到执行模式进行修改。这样可以把“想清楚怎么做”和“真正改代码”分开。

企业场景里这很重要，因为开发者通常希望先看到影响范围、修改点和验证方式，再决定是否允许 Agent 执行。

### 23U. 面试官问：上下文治理和安全控制哪个更重要？

它们解决的问题不同。上下文治理解决长任务能不能持续推进，安全控制解决推进过程中能不能限制风险。

如果没有上下文治理，Agent 容易在长任务中溢出或丢状态；如果没有安全控制，Agent 可能错误修改文件或执行危险命令。企业落地需要两者同时存在。

### 23V. 面试官问：如果只能保留一个安全机制，你选哪个？

我优先保留 read-before-edit 加危险命令拦截。因为这两个直接对应最常见的高风险动作：错误写代码和错误执行 Shell。

权限模式和计划确认可以进一步提高可控性，但 read-before-edit 是代码修改可靠性的基础线。

### 23W. 面试官问：这套安全机制和公司已有权限系统如何结合？

我的权限模式可以作为 Agent 内部第一层控制，公司已有的代码仓权限、CI 权限、身份认证和审批系统作为外部第二层控制。Agent 不应该绕过企业权限，而是把企业权限作为工具可用性的边界。

比如某些目录只读、某些命令需要审批、某些外部系统只允许查询不允许写入，这些都可以映射成工具权限和 MCP 工具策略。

## 五、知识库与经验沉淀

### 24. 你的知识库具体存什么？

它可以存代码规范、需求设计文档、接口说明、架构文档、论文资料和历史问题处理经验。对企业研发来说，很多关键约束不在代码里，而在这些文档中。

比如接口新增任务需要看需求字段、异常码、日志规范和测试规范；论文或技术资料则可以用于算法类任务的实现参考。

### 25. 知识库和记忆系统有什么区别？

记忆更偏长期偏好和简单事实，例如用户习惯、项目背景、常用命令。知识库更偏结构化资料和工程资产，例如需求文档、代码规范、接口说明、历史故障处理流程。

经验沉淀是一条独立于普通知识库的过程知识链。完整 Markdown 分成 Description 和 Content：Description 保存用于匹配的短描述，Content 保存适用场景、问题现象、排查步骤、修改策略、验证方式和踩坑点。后续任务先检索 Description，再按 ID 读取完整经验。

### 26. 结构感知文档切分是什么意思？

不同文档不能都按固定字符数切。Markdown 要保留标题层级，PDF 要保留页码，CSV/JSON 要保留表头、行范围或 JSON path，否则检索命中后很难定位来源。

所以我在切分时会尽量保留 heading、page、row、chapter、tags 等元数据。这样召回的不只是文本片段，还有可追溯的文档结构信息。

### 26A. 面试官问：结构感知切分具体是怎么做的？

整体流程是“先解析成统一文档对象，再按文档结构选择切分策略，最后把分片和元数据一起写入索引”。系统先通过文档解析器把 Markdown、txt、CSV、JSON、PDF、docx 等资料转换成统一的 `ParsedKnowledgeDocument`，里面包括正文、标题、mime type、parser、是否 Markdown、source suffix 等元数据。

然后根据文档类型采用不同切分方法。Markdown 会按标题层级切，保留类似 `Context > Truncation` 这种 heading path；PDF 会按页切，分片里保留 page number；CSV 会把表头重复到每个 chunk，并记录 row_start、row_end；JSON/JSONL 会按 JSON path、数组区间或记录范围切，而不是直接按字符截断。这样检索结果能告诉模型“命中了哪一节、哪一页、哪几行、哪个 JSON path”。

### 26B. 面试官问：为什么不能直接固定 500 token 一个 chunk？

固定长度切分实现简单，但会破坏文档语义结构。比如代码规范里一个标题下面的规则被切到两个 chunk，模型可能只看到规则内容但不知道适用范围；CSV 如果不重复表头，命中某几行时模型不知道每列含义；JSON 如果不保留 path，模型不知道字段来自哪个结构层级。

我的做法不是完全放弃 token budget，而是在结构边界内控制 chunk 大小。默认目标大概是 500 token，重叠大概 60 token，但切分时会尽量尊重标题、页码、表头、行范围和 JSON path。这样兼顾检索粒度和语义完整性。

### 26C. 面试官问：Markdown 或代码规范类文档怎么切？

Markdown 会先识别 `#` 到 `######` 的标题层级，维护一个 heading stack。每当遇到新标题，就把前一节内容 flush 成分片，并把当前分片的 heading 设置成完整标题路径。

比如文档里有 `# 后端规范`、`## 日志规范`、`### 错误日志`，对应 chunk 的 heading 会保存成“后端规范 > 日志规范 > 错误日志”。这样后续检索到这段内容时，模型不只看到正文，还能知道它属于哪条规范和哪个章节。

### 26D. 面试官问：PDF、Word 或论文资料怎么处理？

PDF、Word 这类非纯文本格式会先通过解析器转换成文本或 Markdown。对于 PDF，系统尽量保留页码信息，把每一页作为结构边界之一，再在页内按标题和 token budget 切分。

论文资料通常章节结构很重要，比如方法、实验、消融、限制。如果切分时保留标题层级和页码，检索到某个方法细节后，模型能更容易判断它来自方法部分还是实验部分，也方便用户追溯原文位置。

### 26E. 面试官问：CSV 和 JSON 为什么要特殊处理？

CSV 和 JSON 是结构化数据，如果按普通文本切，很容易丢失字段含义。CSV 里某个 chunk 只包含几行数据但没有表头，模型就不知道每列是什么；JSON 里某段数组或对象如果没有 path，模型不知道它在原始结构中的位置。

所以 CSV 分片会重复 header，并记录 row_start 和 row_end；JSON 会记录 json_path、数组 item_start/item_end 或 JSONL record_start/record_end。这样检索结果既能被模型理解，也能被程序追溯。

### 26F. 面试官问：分片里具体存了哪些元数据？

分片级元数据主要包括 document_id、index_version、ordinal、heading、page_number、chapter_number、tags、token_count、metadata、content、content_hash 和 embedding。文档级元数据包括 document id、name、source_path、stored_path、content_hash、status、active_version、embedding_model、chunk_count、mime_type、parser、title、source_dir、description、tags、chapter_numbers 和 updated_at。

这些元数据有两个作用：第一是检索时做过滤和重排，比如按 tag、章节、source_dir、parser 过滤；第二是结果展示和证据追溯，比如告诉模型命中的是哪个文档、哪个章节、哪一页或哪几行。

### 26G. 面试官问：索引管理是怎么做的？

导入文档时，系统先计算原文件内容哈希。如果内容完全一样，就直接复用已有文档，避免重复索引；如果是新文档，就把原文件复制到知识库 sources 目录，并在 SQLite 的 documents 表里记录 PENDING 状态。

真正索引时会生成一个新的 index_version，先把文档状态改成 PROCESSING，然后解析、清洗、切分、生成 embedding，把分片写入 chunks 表和 FTS 表。全部成功后，才把 documents 表的 active_version 指向新版本，并把状态改成 COMPLETED。这样用户检索时只会看到 active_version 对应的完整索引。

### 26H. 面试官问：为什么需要版本化索引？

因为索引构建可能失败，也可能中途被打断。如果直接覆盖旧索引，就可能出现文档一半是旧分片、一半是新分片，检索结果不一致。

版本化索引的好处是原子切换：新版本的 chunks 和 FTS 都写完后，再更新 active_version；如果中间失败，就把这次 index_version 对应的临时分片删掉，并把文档标记为 FAILED。这样不会污染旧的可用索引。

### 26I. 面试官问：SQLite 里怎么同时存向量和关键词索引？

SQLite 负责文档元数据和分片元数据，chunks 表里会保存分片正文、metadata、content_hash 和 embedding。embedding 会被打包成二进制向量存储；关键词检索则通过 FTS5 表保存 heading 和 content，用于全文检索。

这样一个本地数据库就能同时完成文档管理、分片管理、向量检索候选、关键词检索候选和版本控制。对于本地 CLI Agent 来说，比引入多个外部服务更轻量。

### 26J. 面试官问：HNSW 索引和 SQLite 里的向量是什么关系？

SQLite 里存的是权威数据，包括每个 chunk 的 embedding。HNSW 是在 chunk 数量较大时构建的近似向量索引，用于加速查询。小规模数据或者有明确 metadata filter 的场景直接走精确余弦检索，因为这时精确检索更简单、可靠。

当 chunk 数量超过阈值后，系统可以从 SQLite 中读取 active chunks 的向量构建 HNSW 索引。查询时 HNSW 返回候选，再回到 SQLite 取对应 chunk 元数据和正文。

### 26J-1. 面试官问：embedding 用的是什么模型？

我这里用的是 `Qwen` 系列的 `text-embedding-v4`，通过 OpenAI-compatible 的 embedding 接口接入，而不是把 embedding provider 写死成某一家专用 SDK。

这样做的好处是 embedding 这一层和聊天模型一样，保留了 provider 可替换性。后面如果企业内部有自己的兼容网关，或者需要切换 embedding 服务，只要接口协议兼容，迁移成本会比较低。

### 26J-2. 面试官问：为什么选 `text-embedding-v4`？

我主要考虑四点。第一，我的知识库文本是中文、英文技术词、代码符号和错误信息混合的，中英混合技术文本比较多，`text-embedding-v4` 在这个分布下更合适。第二，它在效果、成本和接入复杂度之间比较平衡，适合作为本地 Coding Agent 的知识检索底座。第三，它和我现有的 OpenAI-compatible 适配层一致，不会把系统绑死在某一个 provider 上。第四，我本身用的是混合检索，所以 embedding 主要承担语义召回，不需要单独承担全部精确匹配责任。

所以我选它不是因为它在所有 benchmark 上绝对最好，而是因为它更符合我这套系统的文本分布和工程约束。

### 26J-3. 面试官问：为什么不是只用关键词检索，非得上 embedding？

因为企业知识里有很多同义表达和语义近邻问题。比如“接口字段变更”“返回参数调整”“schema 改动”，本质上是同类问题，但关键词未必完全一致。

embedding 的价值主要在语义泛化，能把这类表达不同但语义相近的查询召回出来；而 FTS5 负责错误码、字段名、接口名、文件名、命令参数这些精确符号。两者结合比单一路径更稳。

### 26J-4. 面试官问：为什么不直接说某个 embedding 模型更强？

我不会把回答讲成“这个模型绝对最好”，因为最终检索效果取决于整条链路，不是只取决于 embedding 本身。我的系统里还有结构感知切分、元数据过滤、HNSW、FTS5、RRF 融合和二阶段重排，这些都会影响最终 Recall 和可用性。

所以更准确的说法是：我选了一个对中英混合技术文本效果稳定、成本可控、且和现有 OpenAI-compatible 架构一致的 embedding 模型，再通过混合检索把系统级效果做上去。

### 26J-5. 面试官问：如果面试官追问“为什么不是 BGE、Jina、Voyage 或 OpenAI embedding”呢？

我的目标不是做 embedding 模型横评，而是做本地 Coding Agent 的知识增强闭环，所以我更看重和现有架构的一致性、中文技术文本适配性以及整体成本。`text-embedding-v4` 能满足这几个条件。

如果后续要做更严格的 provider 选型，需要在固定 chunk 策略、固定 query set 和固定 rerank 配置下，比较不同 embedding 的 Recall@k、MRR、延迟和单位成本，而不是凭主观感觉选型。

### 26K. 面试官问：结构感知切分对检索准确率有什么帮助？

它主要提升两点：语义完整性和可追溯性。语义完整性是指一个 chunk 尽量保留完整章节、表头或 JSON path，模型不容易误解片段含义；可追溯性是指命中后能知道来源位置，方便模型引用和用户检查。

如果用固定长度切分，很多命中片段可能缺标题、缺表头、缺字段路径，Recall 可能看起来还可以，但模型实际使用时容易出错。结构感知切分能提高检索结果的可用性，而不仅是提高相似度分数。

### 26L. 面试官问：索引更新或删除怎么保证一致性？

更新时通过新的 index_version 构建新索引，成功后切换 active_version，再删除旧版本 chunks 和 FTS 记录。删除时会从 documents、chunks_fts 和 sources 目录同步移除，并清空 HNSW 缓存，避免后续检索到已经删除的文档。

这套逻辑是为了保证知识库在增删改过程中始终处于一致状态。Agent 检索到的内容必须来自当前有效版本，不能混入构建失败或已经删除的分片。

### 26M. 面试官问：如果文档很大，会不会索引很慢？

会，所以我做了几个控制。首先解析后的文本有最大长度限制，避免超大文件直接拖垮本地索引；其次 chunk 有 token budget，避免单个 chunk 过大；再次小规模走精确向量检索，大规模再启用 HNSW。

如果企业级资料规模继续扩大，embedding 生成、向量索引和全文检索可以拆成异步任务或服务化后端，比如用 OpenSearch、Milvus 或 Qdrant。但在本地 Agent 原型里，SQLite + FTS5 + HNSW 更容易部署和验证。

### 27. 为什么要混合检索，而不是只用向量？

企业文档里有大量专有名词、接口名、错误码、字段名和文件名。向量检索擅长语义相似，但对精确符号可能不稳定；关键词检索擅长精确匹配，但对同义表达不够好。

所以我用了 HNSW 向量检索和 FTS5 关键词检索双路召回，再用 RRF 做融合排序，并结合元数据进行二阶段重排。这样既能找语义相近内容，也能保留接口名和错误码这种精确命中。

### 28. Recall@5 从 68% 到 86% 是怎么测的？

我构造了 50 条 Knowledge golden query，每条样本包含 query、期望命中的文档或 chunk，以及对应的资料类型。样本覆盖三类：设计文档 18 条、代码规范 16 条、接口文档 16 条。Recall@5 表示前 5 个检索结果里是否包含标注的目标片段。

结果上，单路向量检索 Recall@5 是 68%，混合检索加 RRF 和二阶段重排后是 86%。拆开看，设计文档大约 83%，代码规范大约 88%，接口文档大约 87%。这个指标只评估“能不能把相关资料召回”，不直接等价于端到端任务成功率，但它能证明知识库检索质量确实提升了。

### 29. 面试官问：为什么不和 BM25、纯 FTS、纯向量都比？

我做了基础对照，只是简历里只放了最直接的单路向量 baseline。50 条 query 上，纯向量 Recall@5 是 68%；纯 FTS5 在精确符号类问题上表现好，但整体大约 62%；向量和 FTS5 双路召回后到 82%；再加 RRF 融合和二阶段重排后到 86%。

从类型上看，设计文档这种表达差异大的问题更依赖向量；代码规范和接口文档里有大量规则名、字段名、接口名，FTS5 能补足向量漏召回。所以混合检索不是为了堆组件，而是因为企业研发资料同时有语义问题和精确符号问题。

### 为什么用 FTS5？

因为我的知识库底层就是 SQLite，FTS5 是 SQLite 原生的全文检索能力，不需要额外部署 Elasticsearch 或 OpenSearch，适合本地 CLI Agent 这种轻量化场景。它可以很好地处理函数名、配置项、错误码、命令参数这类精确关键词，对向量检索是一个补充。  
如果是企业级大规模、多租户、高并发场景，可以考虑 Elasticsearch / OpenSearch；但我这个项目重点是本地私有知识库和 Agent 原型验证，SQLite + FTS5 的部署成本更低，也更容易做版本化存储和测试。

### 为什么用 HNSW？
向量检索如果全量计算余弦相似度，数据量上来以后查询成本会线性增长。HNSW 是比较成熟的 ANN 近似最近邻算法，查询速度快，召回效果也比较稳定，适合做本地向量索引加速。  
我这里做了一个自适应策略：小规模数据或有明确 metadata filter 的时候直接精确余弦检索，因为数据少时精确检索更简单可靠；当 chunk 数量达到阈值后，再启用 HNSW 索引来降低检索延迟。这样避免为了小数据量过早引入近似索引的复杂度。

### 为什么不用 Elasticsearch？

Elasticsearch 更适合服务端、多用户、高并发、大规模检索系统，但我的项目是本地 Coding Agent CLI，核心诉求是轻量、可嵌入、低部署成本。SQLite 可以同时承载文档元数据、chunk、向量和 FTS5 索引，单机环境下更容易落地，也更方便做原子写入、版本化和回归测试。  
如果后续要扩展成团队级服务，检索层可以抽象出来，把 FTS5 替换成 Elasticsearch / OpenSearch，把本地 HNSW 替换成 Milvus、Qdrant 或 ES dense vector。

### 为什么不用 Milvus / Faiss？

Faiss 和 Milvus 都更偏专门的向量检索组件。Faiss 本地性能强，但它主要解决向量索引，不负责文档元数据、关键词检索和版本管理；Milvus 更适合服务端向量数据库，但部署成本更高。  
我的项目不是单独做向量数据库，而是做 Agent 的本地知识增强，所以我优先选择 SQLite 管元数据和关键词索引，再用 HNSW 作为大规模 chunk 下的向量加速。这能让系统保持单机可运行，同时保留后续替换向量后端的空间。

### 为什么需要 FTS5 + HNSW 双路召回？

因为代码和研发文档里同时存在两类查询。一类是语义型问题，比如“上下文压缩为什么会丢信息”；另一类是精确标识符问题，比如函数名、配置项、错误码、MD5、HNSW 这种词。  
纯向量检索对语义相似问题更好，但可能漏掉短关键词和符号；关键词检索对精确匹配更稳，但不理解同义表达。所以我采用双路召回：HNSW 负责语义候选，FTS5 负责关键词候选，再通过 RRF 融合候选排序，最后交给二阶段重排进一步调整顺序。

### 如果被追问 RRF 是什么

RRF 是 Reciprocal Rank Fusion，核心思想是基于排名做融合，而不是直接比较原始分数。因为向量相似度和 FTS5/BM25 分数不在同一个尺度上，直接加权不稳定。RRF 根据候选在各路检索结果中的名次给分，排名越靠前贡献越大，多路都命中的候选会自然排得更靠前。

### 30. 经验沉淀是怎么实现的？

Agent 在执行任务时会持续记录结构化任务轨迹，包括用户需求、读取过哪些文件、调用过哪些工具、是否发生代码编辑、Shell 验证结果、权限拒绝和失败信息。任务收敛后，用户通过 `/experience save` 显式触发保存。

保存时，系统调用一个独立模型把轨迹提炼成结构化经验文档，包括用于召回的 Description，以及包含适用场景、问题现象、处理步骤、验证方法和相关文件模式的 Content；然后程序做证据校验、脱敏和质量评分。完整流程保存为 Markdown，同时把 Description、经验 ID 和路径写入独立 SQLite 索引。后续先通过 `experience_search` 召回描述卡片，再通过 `experience_show(id)` 读取完整经验。

### 31. 面试官问：为什么不是完全自动保存？

因为“模型停止调用工具”不等于任务真正成功。可能是测试失败后停止了，可能是权限被拒后停止了，也可能只是等待用户确认。如果完全自动保存，很容易把错误流程写进知识库，污染后续任务。

所以我采用的是显式触发、自动提炼。用户用 `/experience save` 表达保存意图，后续的提炼、结构化、校验、脱敏和索引由系统自动完成。这个方案在人机成本和可靠性之间更平衡。

### 32. 面试官问：如何控制模型保存的对错？

我不完全信任模型总结，所以保存链路分成模型提炼和程序校验两层。模型负责把任务轨迹整理成 JSON；程序负责硬校验，例如引用的 event id 必须真实存在，验证方法必须对应真实成功的 `run_shell` 事件，相关路径必须来自真实工具输入，敏感信息必须脱敏。

如果模型编造了测试通过，程序找不到对应成功事件，就不会标记为 verified；如果没有实质性工程活动，系统会直接 skip；如果信息不足但仍有参考价值，会标记为 unverified。这样可以降低错误经验进入经验索引并影响后续任务的风险。

更自然的说法是：我没有让模型“想存什么就存什么”。模型只是一个提炼器，真正决定经验是否可信的是任务轨迹里的证据。比如它说“运行 pytest 通过”，那必须能在轨迹里找到一条成功的 Shell 事件；它说“修改了某个文件”，这个路径也必须出现在真实工具调用里。这样能把模型总结从主观文本变成有证据约束的结构化产物。

### 33. 面试官问：经验保存错了怎么办？

我做了可审计和可删除。系统提供 `/experience show <id>` 查看经验内容，`/experience delete <id>` 删除经验文件，并在同一操作中移除对应经验卡片，不会影响普通知识库。

同时经验本身有质量分和 verified/unverified 状态。后续还可以做评分衰减：如果某条经验多次被召回但没有被采用或验证失败，就降低它的权重。

如果错误经验已经影响模型，处理方式有三层：首先经验不会自动高优先级覆盖当前代码证据，模型仍然要读取当前文件和错误信息确认适用性；其次经验文档里包含 applies_when 和 not_applies_when，明确适用边界；最后可以通过 show/delete 删除错误经验，并同步移除卡片索引。长期来看，还可以引入采用率和验证通过率作为经验权重。

### 34. 经验库比不存经验好在哪里？

主要好在减少重复探索和稳定复用企业流程。企业项目里很多任务有固定处理路径，比如同类接口迁移、测试失败、配置问题、规范修复。没有经验库时，Agent 每次都要重新搜索、读文件、试命令；有经验库后，可以先召回历史处理范式，再结合当前代码验证是否适用。

收益主要体现在相似任务上，例如 tool call 次数下降、input token 下降、验证命令覆盖率提升、遗漏规范的概率降低。对完全新问题，经验库收益不会特别大，这个边界要说清楚。

更具体一点，比如第一次处理某类接口字段变更时，Agent 可能需要从接口定义、DTO、schema、测试 fixture、调用方一路摸索；如果这次流程被保存成经验，下一次类似字段变更就可以直接提示“先查接口定义，再查 DTO/schema，再查测试 fixture，最后跑对应模块测试”。它不是替代模型推理，而是让模型少走重复探索的路。

### 35. 面试官问：怎么评测经验库到底有没有用？

我做的是 A/B 对照。固定模型、代码仓、任务输入和最大轮次，设置两组：一组关闭经验检索，只能看当前代码和普通知识库；另一组开启经验检索。任务集里单独抽了 10 组历史相似任务，另外保留全新任务作为参照。

指标包括成功率、平均 tool call、平均 input token、平均耗时、验证命令覆盖率和经验采用率。在这 10 组历史相似任务上，开启经验检索后，平均 tool call 从约 20 次降到约 15 次，input token 从约 4.1 万降到约 3.0 万，验证命令覆盖率从 70% 左右提升到 90% 左右，任务通过数从 7 组提升到 9 组。

全新任务上的收益不明显，这也符合经验库定位。经验库主要复用历史排查路径、修改策略和验证方式，不是解决所有新问题的通用增强。

### 35A. 面试官问：你怎么判断“模型采用了经验”？

我看任务轨迹，而不是只看最终回答。经验被召回后，如果后续工具调用和经验建议一致，比如读取了经验里提到的关键文件类型、执行了经验中的验证命令、避免了之前记录的坑点，就认为发生了采用。

在小规模评测里，我把采用率定义为：经验被召回后，后续执行路径至少命中关键文件模式、关键排查步骤或验证命令中的两类。10 组历史相似任务里，经验卡片 top-3 召回命中 8 组，其中 7 组出现了明确采用，采用后的任务通过 6 组。这样可以区分“检索到了”和“真的影响了执行过程”。

### 35B. 面试官问：经验库带来的提升怎么量化到“好多少”？

我把指标拆开说。效率方面，看平均 tool call、input token 和耗时；质量方面，看任务完成率、验证命令覆盖率、规范遵循率和错误采用率。

在 10 组历史相似任务的小规模消融里，开启经验库后，平均 tool call 从约 20 次下降到约 15 次，input token 从约 4.1 万下降到约 3.0 万，耗时下降约 15%，验证命令覆盖率从 70% 左右提升到 90% 左右，任务通过数从 7 组提升到 9 组。这个结论只针对历史相似任务，不外推到所有开放任务。

### 35C. 面试官问：如果经验库没有提升，可能是什么原因？

我从三个环节排查。第一是召回问题，相关经验没有进入 top-k；第二是采用问题，经验召回了但模型没有按它调整执行路径；第三是适用性问题，历史经验和当前任务表面相似但约束不同，导致错误迁移。

对应的优化也不同：召回问题要调检索和重排，采用问题要改提示和经验结构，适用性问题要补充 not_applies_when 和反例。这样回答可以体现我不是只看最终成败，而是能定位 Agent 链路中的问题。

### 36. 面试官问：你怎么证明模型真的用了经验，而不是检索出来没用？

我看过程指标，而不只看最终结果。比如经验被召回后，后续工具调用是否减少重复搜索，是否按经验推荐读取关键文件，是否执行了经验里记录的验证命令，修改位置是否和经验的文件模式匹配。

如果只是检索命中但执行路径没有变化，就不能算有效采用。我的评测里记录了召回率、采用率、采用后成功率和错误采用率：10 组历史相似任务中，top-3 召回命中 8 组，明确采用 7 组，采用后通过 6 组，出现 1 次表面相似但实际不适用的错误采用。

### 37. 面试官问：如果经验召回错了，会不会误导模型？

会有风险，所以经验文档必须包含适用条件和不适用条件，而不是只保存结论。模型不能直接照搬经验，仍然要读取当前代码和错误信息来确认症状是否匹配。

在系统层面，可以通过二阶段重排、标签过滤和证据检查降低误召回；在评测层面，需要统计错误采用率。如果错误采用率高，就说明经验文档质量或检索排序需要优化。

## 五A、任务轨迹与经验持久化强追问

### 37A. 面试官问：任务轨迹记录是怎么做的？

我没有直接依赖聊天上下文来保存经验，因为聊天上下文可能被压缩或摘要，里面的信息不一定完整。我的做法是在 Agent 运行时单独维护一个 `TaskJournal` 对象，它属于程序侧的结构化事件流，不参与模型上下文压缩。

具体实现上，Agent 初始化时会创建 `self.experience_journal = TaskJournal(self.session_id)`，同时创建 `ExperienceManager` 负责后续保存。每一轮用户输入进入 `chat()` 时，系统会调用 `start_turn(user_message)`，生成新的 `turn_id` 并记录一条 `user_message` 事件。

之后模型如果调用工具，Agent 会在工具执行前记录 `tool_call`，在工具执行后记录 `tool_result`；如果权限被拒绝，会记录 `permission_denied`；如果模型最后输出自然语言结论，也会记录 `assistant_message`。所以 `/experience save` 读取的是这份程序侧轨迹，而不是被压缩后的聊天文本。

### 37B. 面试官问：任务轨迹具体记录什么？

每条事件会有一组固定字段，包括 `event_id`、`turn_id`、`event_type`、`timestamp`、`summary`、`tool_name`、`tool_input`、`status` 和 `duration_ms`。其中 `event_id` 是后续经验校验的证据 id，`turn_id` 用来确定任务范围，`status` 用来区分工具成功还是失败。

内容上主要记录四类信息。第一是用户目标和模型阶段性结论；第二是工具调用，包括工具名、参数摘要、涉及的文件路径或 Shell 命令；第三是工具结果，包括成功、失败、错误信息和耗时；第四是关键控制事件，比如权限拒绝、read-before-edit 拦截、验证命令是否成功。

我不会把所有长日志原样塞进轨迹，而是保存摘要、状态、路径、命令和 event id。这样既能保留后续经验提炼需要的证据，又不会让轨迹本身无限膨胀。

可以给面试官举一个例子：用户说“修复测试失败”会产生一条 `user_message`；模型读取 `app.py` 会产生 `tool_call/read_file` 和 `tool_result/success`；模型编辑文件会产生 `tool_call/edit_file` 和 `tool_result/success`；最后运行 `pytest` 成功，会产生 `tool_result/run_shell/success`。后面经验里如果写“通过 pytest 验证”，就必须引用这条真实事件。

### 37C. 面试官问：怎么保证任务轨迹记录正确？

轨迹记录不是让模型自己写日志，而是在工具执行框架里由程序自动记录。也就是说，只要模型调用工具，系统会在执行前记录工具请求，在执行后记录结果状态和摘要；权限拒绝、命令失败、文件修改这些状态也来自真实执行结果。

所以它比模型自然语言总结更可信。模型可以说“我跑了测试”，但轨迹里如果没有对应的成功 Shell 事件，系统就不会认为测试真的通过。

更具体地说，记录点是在 Agent 的工具执行链路里，而不是在 Prompt 里要求模型自觉记录。工具调用参数来自模型输出的结构化 tool call，工具结果来自实际执行返回值，失败状态由程序根据返回内容和权限判断生成。保存经验时，程序还会反查 event id、工具名和 status，避免模型在经验总结阶段编造证据。

### 37D. 面试官问：经验持久化是怎么做的？

经验持久化采用“显式触发、自动提炼、程序校验”的方式。用户执行 `/experience save` 后，系统从任务轨迹里取出候选范围，调用独立模型提炼结构化经验，再由程序完成证据校验、脱敏和质量评分。通过门控后，一份带 Description 和 Content 的完整 Markdown 落到项目经验目录，同时只把 Description、经验 ID 和路径写入独立索引。

它把一次任务处理过程转成可复用的工程流程。保存后的经验可以被 `/experience show <id>` 查看，也可以用 `/experience delete <id>` 删除并同步移除卡片索引。

实现上，原始轨迹先保存在本次 Agent 进程内的 `TaskJournal.events` 列表中；执行保存后，`ExperienceManager` 把轨迹提炼成 Markdown，保存到 `~/.mini-claude/projects/<project_hash>/experiences/`。Markdown 里明确分成 `Description` 和 `Content`：`Description` 是用于召回的短描述，包含适用场景、问题信号、文件模式和验证命令；`Content` 保存完整排查、修改和验证流程。`ExperienceIndex` 只对 `Description` 生成 embedding 和 FTS5 索引，并记录经验 ID 与 Markdown 路径。这里不再调用知识库的 `add_document()`，完整经验也不会按 500 token 分块。

所以原始轨迹是运行时证据流，完整 Markdown 是经过提炼和校验后的事实源，经验卡片是用于发现这份事实源的索引。`Description` 负责回答“这条经验是否可能相关”，`Content` 负责回答“完整过程具体怎么做”。

### 37E. 面试官问：持久化的经验内容是什么？

经验文档主要分成两部分。第一部分是 `Description`，用于检索召回，写得短而聚焦，主要包含适用场景、问题信号、相关文件模式和验证命令。第二部分是 `Content`，用于真正复用，包含适用/非适用场景、问题现象、约束条件、诊断依据、处理步骤、容易踩坑的点、验证方法、相关文件模式和检索关键词。

比如一次接口字段迁移经验，不会只写“修改 DTO”，而是会写适用于什么接口变更场景，通常要检查接口定义、DTO/schema、测试 fixture 和调用方，修改后应该跑哪个模块测试。这样后续模型检索到时，拿到的是一个可迁移的流程，而不是一句结论。

### 37F. 面试官问：用户如何让经验被保存？

我没有设计成完全自动保存，而是让用户通过 `/experience save` 显式触发。原因是任务是否真正完成很难仅靠“最后没有 tool call”判断，可能是测试失败后停止了，也可能是权限被拒后停止了。

同时我也支持 `/experience save --from <turn-id>`，用户可以指定从某一轮开始保存，避免把前面无关讨论也写进去。保存后可以用 `/experience list` 看已有经验，用 `/experience show <id>` 查看内容，用 `/experience delete <id>` 删除错误经验。

### 37G. 面试官问：如何保证持久化范围正确？

默认情况下，系统会从上一次成功保存后的 checkpoint 开始，到用户执行 `/experience save` 前为止，作为候选范围。这样可以避免重复保存已经沉淀过的经验。

如果用户认为当前任务从更晚的某一轮才开始，可以用 `--from <turn-id>` 手动指定范围。模型会基于候选轨迹提炼经验，但程序会校验它选择的 turn id 是否真实存在、是否连续、是否在候选范围内。如果范围里没有代码编辑、验证命令或失败恢复等实质性工程活动，系统会 skip 或标记为 unverified。

### 37H. 面试官问：为什么不让模型自己决定从哪里开始保存？

模型可以辅助判断，但不能完全交给模型。因为模型可能把无关上下文也纳入经验，或者漏掉关键验证步骤。

所以我的设计是程序先给出硬边界：只能从候选轨迹里选，不能越过 checkpoint，不能引用不存在的 turn 或 event。模型负责在这个范围内提炼结构，程序负责验证边界和证据。这样既利用模型的语义理解，又避免它随意扩大或编造范围。

### 37I. 面试官问：经验冲突如何处理？

目前比较保守：如果新经验和已有经验标题或 slug 相近，会作为相关版本保存，而不是直接覆盖旧经验。每个版本有独立 ID、Markdown 路径和卡片记录，删除时文件与卡片同步移除。

如果真正上线，需要进一步按场景和适用条件做冲突处理。例如同一个错误现象有两条不同处理方案，就不能简单覆盖，而是保留不同版本，并记录适用项目、适用分支、验证命令和最后成功时间。后续检索时根据项目、文件模式和任务类型做过滤。

### 37J. 面试官问：之后什么情况下经验会被检索到？

当用户的新任务和某条经验的 `Description` 相似时，经验就有机会被 `experience_search` 召回。这个描述会概括适用场景、问题信号、文件模式和验证命令。比如用户说“接口字段变更导致测试失败”，系统可能召回之前的接口迁移经验；如果用户说“某个 lint 规则失败”，可能召回对应规范修复经验。

匹配不只靠标题。保存经验时，模型会生成一段专门用于检索的 `description`；如果模型没有给出，程序会从 applies_when、signals、文件模式和验证方法中兜底生成。向量和 FTS5 都只围绕这段 description 建索引，命中后返回经验 ID、路径和描述，模型再用 `experience_show` 读取完整 Content。

### 37K. 面试官问：经验靠什么匹配？向量还是关键词？

我采用混合检索。向量检索适合匹配语义相似的任务描述，比如“接口字段变更”和“API 参数调整”这种表达不同但含义接近的情况；关键词检索适合匹配精确符号，比如错误码、接口名、文件名、测试命令和 lint 规则。

经验卡片的核心检索字段是 `description`。这段描述同时包含自然语言场景和精确工程信号：前者由向量检索匹配，错误码、接口名、路径、测试命令和规则名由 FTS5 匹配。两路结果通过 RRF 融合，再结合向量分、词覆盖和精确短语做轻量重排。当前经验量较小，向量分支使用精确余弦检索，没有直接套用知识库的大规模 HNSW 路径。

### 37L. 面试官问：设计文档、代码规范和任务经验，用同一种检索策略合理吗？

不合理，所以我把存储粒度和消费方式分开了。设计文档、接口文档和代码规范属于事实型资料，按标题、章节、页码或结构路径切块，`knowledge_search` 直接返回相关片段；任务经验属于过程型知识，完整性比局部命中更重要，因此只检索经验 Description，命中后再读取整篇 Markdown Content。

两条链可以共用向量、FTS5 和 RRF 等基础能力，但索引对象、重排特征、top-k 和返回格式不同。Knowledge 更关注章节证据和精确术语，Experience 更关注 description 中的场景、signals、文件模式和 validation。

### 37L-1. 面试官问：为什么经验搜索只返回卡片，不直接把完整经验给模型？

因为搜索阶段的目标是判断“哪条经验可能适用”，不需要一次读取所有候选全文。卡片主要返回标题、路径和 description，适合做高召回筛选；如果把前三篇完整经验都返回，会明显占用上下文，也容易让不同经验的步骤互相干扰。

所以系统先返回最多 3 张候选卡片。模型结合当前错误和代码模块选择候选后，再调用 `experience_show(id)` 读取一篇完整经验。这样既控制 token，也保留了经验内部的顺序关系。

### 37L-2. 面试官问：检索和读取结果究竟怎么进入 Prompt？

动态 System Context 只披露经验索引入口、ID、标题和少量 description 摘要。`experience_search` 和 `experience_show` 的实际结果不改写 System Prompt，而是作为 tool result 写入当前消息历史，下一轮模型请求自然能看到。Knowledge 也是同样的工具回填机制，只是它一次返回命中的局部 chunk；Experience 会先返回 description 卡片，再返回选中经验的完整 Content。

### 37M. 面试官问：不同类型资料的检索准确率有没有测过？

测过，但不同资料类型用的指标不一样。Knowledge 部分用了 50 条 golden query，覆盖设计文档 18 条、代码规范 16 条、接口文档 16 条。混合检索整体 Recall@5 是 86%，其中设计文档约 83%，代码规范约 88%，接口文档约 87%。单路向量整体是 68%，纯 FTS5 整体大约 62%。

Experience 部分没有沿用 Knowledge 的 Recall@5，而是用 10 组历史相似任务测 Description top-3 命中。结果是 8/10 命中正确经验，7/10 被执行路径明确采用，1 次出现表面相似但约束不匹配的错误采用。所以我不会把知识库 86% 直接套到经验库上，两者是分开评测的。

### 37N. 面试官问：你觉得各种资料更适合什么检索方法？

需求设计文档适合结构感知切分加向量召回，因为查询表达和原文可能不同；代码规范更依赖关键词、标题和标签，因为常有固定规则名、目录名和格式要求；接口文档适合关键词与 metadata 过滤结合语义召回。

历史经验适合“description 混合检索 + Content 全文读取”。向量判断是否属于同类问题，关键词匹配错误信息、命令、文件路径和测试名；召回阶段保持 description 短小，使用阶段保持完整步骤连续。

### 37O. 面试官问：检索到经验后，对任务有提升吗？测过吗？

测过一个小规模消融。当前简历里的 73% 到 87% 是系统整体完成率提升，不能全部归因给经验库；但经验库单独在 10 组历史相似任务上做过开关对照。

固定模型、仓库、任务和最大轮次后，关闭经验库时 10 组通过 7 组，开启经验库后通过 9 组；平均 tool call 从约 20 次降到约 15 次，input token 从约 4.1 万降到约 3.0 万，验证命令覆盖率从 70% 左右提升到 90% 左右。全新任务没有明显提升，所以经验库的价值主要在历史相似问题和固定研发流程复用上。

### 37P. 面试官问：经验库提升多少比较合理？

目前小规模测试里，历史相似任务上的量级是：tool call 下降约 25%，input token 下降约 27%，耗时下降约 15%，验证命令覆盖率提升约 20 个百分点。比如原来一个相似任务需要 20 次左右工具调用，开启经验后大概降到 15 次左右。

这个收益主要来自减少重复探索和更快复用验证路径。对全新任务，经验库最多帮助规范遵循和检索路径，完成率提升不明显。

### 37Q. 面试官问：如何证明检索到经验真的影响了任务过程？

只看检索命中不够，我用任务轨迹看采用证据。比如经验建议先看 DTO/schema 和测试 fixture，实际轨迹里是否确实少做泛化 grep，而是直接读取这些关键文件；经验建议运行某个模块测试，实际是否执行了这个命令；经验记录某个坑点，模型是否避免了同样错误。

所以经验评测分三层：recall、adoption、post-adoption success。10 组历史相似任务里，top-3 recall 是 8/10，adoption 是 7/10，post-adoption success 是 6/7。召回说明找到了，采用说明影响了执行路径，采用后成功率才说明它真的有业务价值。

### 37R. 面试官问：如果经验和当前代码冲突，模型该听谁的？

当前代码和当前验证结果优先。经验只是历史流程建议，不是事实来源的最高优先级。模型必须先读取当前文件和错误信息，确认经验的适用条件是否满足，再决定是否采用。

如果经验说的文件结构已经变化，或者验证命令不适用，就应该放弃这条经验，重新探索，并且可以在任务结束后保存一个新版本经验。这样经验库不会变成僵化规则，而是可更新的工程资产。

## 六、Token、耗时与成本

### 38. 一个通用编程任务大概消耗多少 Token？

中等复杂度任务，比如定位一个 bug、读取 5 到 8 个文件、修改 1 到 3 个文件、运行 1 到 2 次测试，通常 input token 大概 2 万到 5 万，output token 大概 2 千到 6 千，tool call 大概 12 到 25 次，耗时大概 3 到 8 分钟。

如果任务涉及大范围重构、长日志、多轮测试失败，input token 可能到 8 万以上；如果只是小修复，可能 1 万到 2 万就够。所以这个指标要按任务复杂度给区间，不能给一个绝对值。

### 39. 上下文治理后 Token 降低多少？

在长会话任务上，我统计的是平均上下文体积降低 34%。具体到单个任务，收益取决于工具结果有多大。如果任务包含大量 grep、长测试日志和多文件读取，下降会更明显；如果任务很短，收益就不明显。

我把它定义为“长任务里的上下文占用优化”，不是“所有任务成本都下降 34%”。

### 40. 经验保存会额外消耗多少？

经验保存只在用户显式执行 `/experience save` 时触发，不是每轮都调用。因为传给提炼模型的是结构化任务轨迹摘要，不是完整上下文，所以额外输入大概 6k 到 12k token，输出大概 1k 到 2k token。

这个成本是否值得取决于复用次数。如果一条经验后续能帮助 2 到 3 个相似任务减少重复探索，基本就能覆盖保存成本；如果是一次性任务，就没有必要保存。

### 41. 面试官问：你怎么估算这些 Token 数值？

Token 主要从三个来源估算：第一是模型 API 返回的 input/output token；第二是工具结果的文本长度估算；第三是任务轨迹中每轮消息和工具调用的累计统计。

例如完成率评测里，每个任务会记录总 input token、output token、tool call 次数和耗时。上下文治理评测则记录每轮请求前估算上下文 token，用开启/关闭治理的平均值做对比。

### 42. 面试官问：Prompt Cache 你怎么考虑？

Prompt Cache 可以降低重复前缀的计费和延迟，但它不是无限制的。如果频繁改写历史消息，比如每轮都摘要，会破坏缓存命中。

所以我的策略是在低风险阶段尽量保留稳定前缀，只控制新工具结果和旧的可恢复内容；当上下文利用率达到高水位时，才牺牲部分缓存稳定性来避免溢出。评估成本时也要区分普通 input token、cache read token 和 cache creation token。

## 七、业务落地与 HR 可听懂版本

### 43. 如果面试官不懂 Agent，只问这东西有什么业务价值，怎么说？

可以理解为一个能读公司内部资料、能改代码、能跑测试、还知道权限边界的 AI 开发助手。它的价值不是替代程序员，而是把重复性的排查流程、代码规范和历史经验沉淀下来，让 AI 在处理相似问题时更快、更稳定。

比如团队以前处理过某类测试失败，系统可以把当时的排查步骤、修改位置和验证命令保存为经验。以后再遇到类似问题，AI 不用从零摸索，可以先参考历史流程，再由开发者确认最终修改。

### 44. 如果 HR 问：这个项目最难的地方是什么？

最难的是让模型输出从“看起来合理”变成“过程可控、结果可验证”。代码 Agent 不是只生成一段代码，真正难的是长任务中怎么保留关键信息、怎么限制危险操作、怎么让私有知识真正影响执行路径，以及怎么用指标证明它有效。

所以我做了上下文治理、权限控制、知识库评测和经验沉淀，而不是只停留在 Prompt 调优。

### 45. 如果技术面问：你觉得这个项目最有价值的设计是什么？

我选经验的“Description 召回、Content 全文读取”闭环。企业开发里有很多可复用的排查和验证流程，通过任务轨迹记录、显式保存、模型提炼和程序校验，可以把一次成功处理过程变成完整 Markdown；独立卡片索引只负责发现相似经验，按 ID 读取全文则保留步骤连续性。

这个设计也比较符合企业落地，因为它不是要求模型一次性变强，而是让团队的规范、文档和历史经验持续进入 Agent。

### 46. 如果问：这个项目现在还有什么不足？

第一，30 组任务规模还不够大，更多是阶段性离线评估。第二，端到端完成率提升还没有做非常细的模块消融，不能把系统级提升完全归因到某个模块。第三，经验库目前以显式保存为主，还没有做长期的自动质量衰减和线上反馈闭环。

如果继续做，优先补批量任务 Runner、统一 Trace、失败分类报告和经验采用率评测，让指标更接近真实企业使用。

## 八、针对简历三条 Bullet 的高频追问

### 47. 简历写“工具编排与任务执行”，你具体负责了什么？

我主要实现了 Agent 的核心执行循环和工具系统。模型每轮输出工具调用，系统负责解析参数、权限判断、执行工具、回填结果，并根据结果继续下一轮推理。

在这个基础上，我做了延迟激活、流式调用、只读工具并发和三类 Sub-Agent，目的是让复杂任务既能拆解执行，又不会让主上下文被大量搜索结果污染。

### 48. 简历写“完成率 73% 到 87%”，面试官质疑数据怎么办？

这是固定 30 组任务上的离线对照，不是线上大规模指标。73% 对应约 22 个任务完成，87% 对应约 26 个任务完成。每个任务都有预设验收标准，优先以测试、lint、类型检查或明确的文件修改检查作为通过条件。

这个指标是系统级效果，用来证明整体链路有效；如果要做论文级或生产级结论，还需要扩大样本、重复运行和做模块消融。

### 49. 简历写“四层压缩机制”，面试官问为什么叫四层？

因为它不是单一摘要，而是按上下文风险逐级触发。第一层控制单次工具结果预算，第二层裁剪旧的可恢复工具输出，第三层在空闲时做微压缩，第四层在高水位时做全局摘要。

这样设计的原因是摘要有信息损失，所以不能一开始就摘要。先处理最占空间、最容易恢复的工具结果，最后才处理不可逆的会话摘要。

### 50. 简历写“长会话平均上下文体积降低 34%”，怎么说更严谨？

这是在长链路编程任务中，对比开启和关闭上下文治理后，每轮请求前的平均上下文估算 token 得到的下降比例。它衡量的是上下文占用，不等于任务耗时下降，也不等于模型内部 KV Cache 被压缩。

压缩效果必须和任务完成率一起看。如果上下文降低但任务成功率下降，就说明压缩策略过激。

### 51. 简历写“六种权限模式”，分别有什么意义？

不同场景对自动化程度要求不同。普通交互下需要用户确认危险操作；计划模式只允许读和规划；accept-edits 可以自动接受文件编辑但仍限制危险命令；bypass 更适合可信本地快速实验；dontAsk 适合 CI 里自动拒绝；auto 则通过模型分类器判断工具风险。

本质上，权限模式是把 Agent 从 Demo 变成可控工具的基础。企业环境中不能让模型无限制执行所有命令。

### 52. 简历写“HNSW + FTS5 + RRF + 重排”，为什么这么设计？

HNSW 负责高效向量召回，解决语义相似问题；FTS5 负责关键词和符号精确匹配，适合接口名、错误码、字段名；RRF 用来融合两路排序，避免单一路径漏召回；二阶段重排再结合标题、标签、章节等元数据优化结果顺序。

这个组合适合企业文档，因为企业文档既有自然语言描述，也有大量精确符号。

### 53. 简历写“Recall@5 68% 到 86%”，面试官问样本怎么构造？

样本来自项目知识库常见查询类型，一共 50 条 query，包括 18 条设计文档、16 条代码规范和 16 条接口说明。每条样本有 query 和期望命中的文档或片段，评估前 5 个结果中是否包含期望答案。历史问题经验已经拆到独立经验索引，我用 10 组历史相似任务单独测 Description top-3 命中和采用情况。

这个指标评估的是检索召回质量，不直接代表代码任务完成率。它证明的是知识库能更稳定地把相关资料放进模型上下文。

### 54. 简历写“任务轨迹自动提炼为经验文档”，自动体现在哪里？

自动体现在提炼和结构化过程。任务执行时系统自动记录轨迹；用户显式执行 `/experience save` 后，系统自动选择候选范围、调用模型生成带 Description 和 Content 的结构化经验、做证据校验、脱敏和质量评分，随后保存完整 Markdown 并建立独立 Description 索引。

我没有做完全无确认的自动保存，因为那样容易污染知识库。这个设计是“显式触发，自动提炼”。

## 九、最容易被连续追问的一组问答

### 54A. 面试官：先别讲模块，你整体效果到底怎么样？

整体效果主要从三个维度看：端到端任务质量、运行效率和检索质量。

端到端质量上，在 30 组固定编程任务中，完成率从 73% 提升到 87%，也就是大约从 22 个任务完成提升到 26 个任务完成。运行效率上，在 10 组历史相似任务里，经验库把平均 tool call 从约 20 次降到约 15 次，input token 从约 4.1 万降到约 3.0 万。检索质量上，50 条 Knowledge golden query 中，混合检索相比单路向量检索，Recall@5 从 68% 提升到 86%。

这些是本地离线评测结果，不是线上大规模生产数据。

### 54B. 面试官：你怎么证明不是你挑了容易的任务？

任务集需要提前固定，而不是根据结果挑选。我的口径是：任务覆盖 bug 修复、接口改动、测试失败、规范修复和小范围重构，每个任务都有初始仓库状态、输入 prompt 和验收条件。

更严谨的做法是把任务分层统计，比如简单任务、中等任务、长上下文任务、历史相似任务和全新任务分别报告结果。如果只在简单任务上提升，那说服力不强；如果提升集中在长上下文和历史相似任务上，反而符合这个系统的设计目标。

### 54C. 面试官：你说相似任务提升明显，相似任务怎么定义？

相似任务不是指 prompt 长得像，而是指问题处理流程相似。比如同一类接口字段迁移、同一类测试 fixture 更新、同一类配置错误、同一类代码规范修复，它们可能涉及不同文件，但排查路径和验证方式类似。

我用经验文档里的 applies_when、signals、related_file_patterns 和 validation method 来定义相似性。评测时也可以人工标注任务是否属于历史经验的相似变体，再比较开启经验库前后的表现。

### 55. 面试官：你说效果提升，能不能一句话讲清楚怎么测的？

可以。端到端效果用 30 组固定编程任务 A/B 对照，指标是任务完成率、tool call、token、耗时和验证覆盖；知识库效果用 golden set 测 Recall@5、MRR 和 Precision@k；上下文效果用长任务每轮请求上下文 token 的平均值和峰值做对比。

### 56. 面试官：为什么完成率提升和知识库 Recall 提升不是同一个指标？

因为它们衡量的是链路的不同环节。Recall@5 只说明相关知识有没有被召回；端到端完成率还取决于模型是否采用知识、是否正确修改代码、是否跑对测试、是否通过权限控制。

所以需要同时报告检索指标和任务指标，不能用 Recall@5 直接替代完成率。

### 57. 面试官：如果召回率高但任务没完成，问题在哪里？

可能有几类原因。第一，召回的知识相关但不够精确；第二，模型没有正确采用知识；第三，代码修改能力或工具调用出了问题；第四，验证命令没有覆盖真实需求。

所以要看任务轨迹，分析检索命中后是否影响了后续文件选择、修改位置和验证命令。这个项目记录任务轨迹，就是为了能做这种失败归因。

### 58. 面试官：如果没有知识库，模型也可能自己搜代码完成，为什么还要知识库？

代码仓只能提供“现在代码怎么写”，不一定提供“为什么这么写”和“需求要求怎么写”。企业里很多约束在外部文档中，比如设计方案、接口协议、异常码规范、日志规范、测试要求。

知识库的作用是把这些外部约束纳入执行依据，减少模型只根据局部代码做错误推断。尤其是需求驱动开发和规范修复场景，知识库价值更明显。

### 59. 面试官：你如何防止经验库越存越乱？

第一，显式触发保存，不让所有对话自动进入经验库。第二，保存时做结构校验和证据校验，没有成功验证的经验会标记 unverified 或 skip。第三，提供 show/delete，错误经验可以被审计和删除。

后续可以进一步加经验版本、采用率统计和评分衰减，让长期不用或被验证失败的经验降低优先级。

### 60. 面试官：如果让我复现实验，你需要给我什么？

需要给出任务集、初始仓库版本、模型配置、权限模式、最大轮次、验收命令和评测脚本。每个任务运行后输出任务是否通过、总 token、tool call 次数、耗时、压缩事件和失败原因。

这样别人可以在同样条件下复现 73% 到 87% 的端到端结果，也可以替换模型或模块做消融。

### 61. 面试官：如果你说经验库有效，实验表里最应该出现哪些字段？

实验表至少记录这些字段：任务 id、任务类型、是否历史相似任务、是否开启经验库、召回的经验 id、经验是否被采用、最终是否通过、tool call 次数、input token、output token、耗时、验证命令是否执行、失败原因。

为了证明经验库的作用，实验表还记录采用路径，比如经验建议读取哪些文件、实际是否读取；经验建议运行什么测试、实际是否执行。这样可以证明经验库不只是被召回，而是真的影响了 Agent 的执行过程。

### 62. 面试官：如果公司让我上线这个方案，你会怎么做评估？

上线评估会先选一个低风险、高重复的研发场景，比如测试失败修复、接口字段迁移或代码规范修复，而不是一开始就让它处理大范围重构。然后用公司历史 issue 或 MR 构造离线任务集，固定仓库版本和验收脚本，先做离线 A/B。

离线评估通过后，再做开发者辅助模式，只让 Agent 生成修改建议和 patch，由人确认合并。线上阶段重点看人工采纳率、回滚率、Review 修改意见、任务耗时和验证通过率。这样比较符合企业落地节奏。

### 63. 面试官：你怎么回答“这些指标有没有水分”？

这些是原型阶段的离线评测，不是生产环境的真实收益，不能包装成线上指标。但离线指标仍然有价值，因为它固定了任务、模型、环境和验收标准，可以验证设计方向是否有效。

真正上线前，需要扩大任务集、重复运行、加入人工 review 结果和线上采纳率。这个回答比硬说“完全没水分”更可信。

## 十、推荐现场回答模板

### 项目一句话

我做的是一个面向企业研发场景的可控 Coding Agent，重点不是简单让模型写代码，而是让它结合企业私有文档和历史经验，在权限控制和上下文治理下完成代码修改与验证。

### 业务价值一句话

企业开发中很多问题有固定规范和处理流程，我希望把这些需求文档、代码规范和历史解决经验变成 Agent 可检索、可复用、可验证的工程资产，减少重复探索和规范遗漏。

### 效果一句话

我主要从端到端任务完成率、上下文 token 占用和知识库 Recall@5 三个角度评估：30 组任务完成率从 73% 到 87%，长会话平均上下文体积降低 34%，混合检索 Recall@5 从 68% 到 86%。

### 评测口径一句话

这些指标都是在固定模型、固定任务、固定仓库初始状态下做 A/B 对照得到的；完成率看预设验收条件，检索看 golden set，压缩看每轮请求前上下文估算 token。

### 被质疑数据时的一句话

这些数据定义为本地原型阶段的离线评测结果，而不是线上生产指标；它能证明设计方向有效，但如果要上线，还需要扩大任务集、重复运行并做更细的模块消融。

### 经验保存一句话

经验保存采用显式触发、自动提炼：Agent 自动记录任务轨迹，用户执行 `/experience save` 后，模型提炼带 Description 和 Content 的完整经验，程序做证据校验、脱敏和质量评分，同时只对 Description 建立独立索引；后续先召回描述卡片，再按 ID 读取全文。

### 和 Claude Code 对比一句话

我不把它定位成 Claude Code 的替代品，而是围绕企业私有知识、研发流程和权限评测做可控原型，重点验证通用 Coding Agent 如何在企业场景中被定制和评估。

## 十一、数值口径速记

- 端到端任务：30 组固定编程任务。
- 完成率：73% 到 87%，约 22/30 到 26/30。
- 中等任务消耗：input 2 万到 5 万 token，output 2 千到 6 千 token。
- 中等任务工具调用：12 到 25 次。
- 中等任务耗时：3 到 8 分钟。
- 工具编排核心价值：把读、搜、改、执行、知识检索、Skill、Sub-Agent 拆成权限边界清晰的原子工具。
- 工具质量指标：tool call 次数、重复搜索次数、无效调用比例、工具失败率、任务完成率、验证通过率。
- 并发原则：只读无副作用工具可以并发；写文件、Shell、外部状态修改必须保守顺序执行。
- 流式输出实现：消费文本增量、thinking 增量和 tool call partial JSON；tool block 完整后才解析和执行。
- 流式提前执行边界：只对无副作用、权限已自动允许的工具开放，不对写文件、Shell、外部写操作开放。
- 终端界面形态：spinner + 实时文本输出 + 工具调用提示 + 工具结果提示的 REPL 界面。
- Skill 与经验区别：Skill 是可执行稳定流程；经验是可检索的问题处理范式。
- Sub-Agent 价值：上下文隔离、权限隔离、并行探索；不能单独声称提升多少，除非做消融。
- CLI 形态原因：更贴近代码仓、文件系统和 Shell 的真实开发流，也更适合先验证运行时而不是前端。
- Harness 含义：不是单指 prompt，而是把模型、工具、权限、上下文、评测组织成可控代码执行底座。
- Prompt 组织：静态系统规则 + 动态项目上下文分层；动态部分只放 Memory、Knowledge、Experience 等轻量索引及环境、Skills、日期，正文通过工具结果按需进入。
- 长任务上下文：平均上下文体积降低 34%。
- 经验保存额外成本：input 6k 到 12k token，output 1k 到 2k token。
- 经验库小规模消融：10 组历史相似任务中，tool call 约 20 次降到约 15 次，input token 约 4.1 万降到约 3.0 万，验证覆盖率约 70% 到 90%，通过数 7/10 到 9/10。
- 知识库检索：单路向量 Recall@5 68%，混合检索 Recall@5 86%。
- 结构感知切分：Markdown 保留标题路径；PDF 保留页码；CSV 保留表头和行范围；JSON/JSONL 保留 json_path、数组区间或 record 范围。
- Chunk 设计：默认目标约 500 token，重叠约 60 token，但优先尊重章节、页、表头、行范围和 JSON path。
- 索引版本化：导入先算 content_hash；索引时生成 index_version；全部 chunks、FTS、embedding 写完后再切 active_version；失败则清理临时版本并标记 FAILED。
- 分片元数据：heading、page_number、chapter_number、tags、token_count、metadata、content_hash、embedding。
- 文档元数据：source_path、stored_path、status、active_version、embedding_model、chunk_count、mime_type、parser、title、source_dir、description、tags。
- 经验持久化内容：Description 用于召回，Content 保存适用场景、非适用场景、问题现象、处理步骤、验证方法、相关文件模式、检索关键词。
- 经验可信控制：真实 event id、真实成功 Shell 验证、路径来自工具输入、敏感信息脱敏、低质量 skip、证据不足 unverified。
- 经验范围控制：默认从上次 checkpoint 到 `/experience save` 前；支持 `/experience save --from <turn-id>` 手动指定。
- 经验检索匹配：只对经验 Description 做精确向量与 FTS5 双路召回，RRF 融合并轻量重排；命中后通过 `experience_show(id)` 读取完整 Markdown Content。
- 文档检索差异：需求设计偏向量和章节；代码规范偏关键词、标题、标签；历史经验最适合 Description 混合检索加 Content 全文读取；论文资料偏章节感知和术语过滤。
- 上下文阈值：有效窗口预留 2 万 token；50% 控制工具结果；60% 裁剪旧结果；75% 强制处理缓存热区；85% 全局摘要。
- 大结果处理：超过 30KB 先本地持久化，再返回预览和恢复路径。
- 权限控制：六种权限模式，包含计划、确认、自动分类、拒绝和快速实验场景。
- 安全核心指标：危险动作拦截率、误拦截率、绕过率、未读编辑拦截、外部修改拦截。
- read-before-edit 价值：防止盲改和基于过期上下文覆盖用户改动。
- Prompt Cache 边界：低水位尽量保持历史前缀稳定；高水位优先避免上下文溢出。

## 十二、面试时不要踩的坑

1. 不要说“比 Claude Code 强”。应说“面向企业私有研发知识和评测闭环做定向扩展”。
2. 不要把 87% 说成线上指标。应说“固定 30 组任务上的离线对照”。
3. 不要把 Recall@5 说成任务完成率。它只证明检索相关资料的能力。
4. 不要说经验会完全自动保存。应说“显式触发，自动提炼，程序校验”。
5. 不要说压缩的是 KV Cache。应说“应用层上下文治理”。
6. 不要把系统级完成率提升归因到单个模块。应说“整体提升，单模块需要消融证明”。
7. 不要只讲技术名词。每个模块都要落回业务价值：减少重复探索、降低上下文成本、控制修改风险、提高规范遵循。
