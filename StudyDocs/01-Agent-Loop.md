# 01 Agent Loop 核心循环

## 第一部分：总结介绍

Agent Loop 是 coding agent 的核心执行循环。普通聊天机器人通常只接收用户输入并生成文本，而 Agent Loop 会让模型在每一轮响应中决定是否需要调用工具。如果模型返回普通文本，说明它认为当前任务已经完成；如果模型返回 `tool_use`，宿主程序就负责执行工具，把执行结果包装成 `tool_result`，再作为新的消息放回上下文，继续调用模型。这个循环让模型从“只会说”变成“可以读文件、搜代码、执行命令、编辑文件”的执行型助手。

在 Python 版本里，主入口是 `/Users/8utterf1y/Desktop/agent项目/claude-mini/claude-code-from-scratch/python/mini_claude/agent.py:452` 的 `Agent.chat()`。它会在第一次聊天时懒加载 MCP 工具，然后根据后端选择 `_chat_openai()` 或 `_chat_anthropic()`。Anthropic 版本的主循环在 `/Users/8utterf1y/Desktop/agent项目/claude-mini/claude-code-from-scratch/python/mini_claude/agent.py:1487`。它先把用户消息加入 `_anthropic_messages`，然后进入 `while True`：调用模型、收集 `tool_use`、保存 assistant 回复、如果没有工具调用就结束；如果有工具调用，就权限检查、执行工具、处理大结果，然后把所有工具结果作为 `role: "user"` 的 `tool_result` 消息塞回历史，进入下一轮。

这个设计里有一个关键点：循环是否继续不是代码靠关键词判断，而是模型通过结构化工具调用决定。宿主程序不写“如果用户说读文件就读文件”的业务分支，而是把工具能力披露给模型，让模型选择工具。程序负责执行、权限、安全和状态维护。这样一来，Agent 的能力可以通过新增工具扩展，而不是不断写自然语言意图识别分支。

Python 代码里的异步写法也服务于这个循环。`async def chat(...) -> None` 表示这是一个异步函数，调用模型、连接 MCP、执行部分工具都可能等待 IO。`await` 表示等待这个异步操作完成后再继续。例如 `await self._mcp_manager.load_and_connect()` 保证 MCP 连接完成后再获取工具定义；`await coro` 保证真正的 `_chat_anthropic()` 或 `_chat_openai()` 循环跑完后再清理当前任务并保存会话。可以把 Python 的 coroutine 理解成 JavaScript 的 Promise：它代表未来会完成的异步结果。

工具返回结果也不是无限制塞进上下文。`_persist_large_result()` 在 `/Users/8utterf1y/Desktop/agent项目/claude-mini/claude-code-from-scratch/python/mini_claude/agent.py:1181` 负责处理大工具结果。如果结果不超过 30KB，就原样返回；如果超过 30KB，就把完整结果保存到 `~/.mini-claude/tool-results/`，只把文件路径和前 200 行预览放进 `tool_result`。这样既避免上下文被大日志撑爆，又不丢失完整信息，模型后续仍然可以用 `read_file` 读取保存下来的完整结果。

## 面试话术版本

这个项目的 Agent Loop 本质上是一个“模型决策、程序执行、结果回填”的循环。用户输入进入消息历史后，Agent 调用模型。如果模型只返回文本，当前轮结束；如果模型返回 `tool_use`，Agent 就执行对应工具，把结果包装成 `tool_result` 再放回消息历史，继续调用模型。Python 版本里这个逻辑主要在 `Agent._chat_anthropic()` 中实现。它不是靠手写规则判断用户意图，而是把工具 schema 发给模型，由模型决定何时调用工具，宿主程序负责权限、执行、安全和上下文管理。为了支持网络和 IO，外层使用 `async/await`；为了控制上下文，工具结果过大时会落盘，只把预览和路径回填给模型。

## 第二部分：面试问答与追问补充

### Q1：面试官问：你说的 Agent Loop 到底和普通聊天有什么本质区别？

普通聊天基本是“一次输入，一次文本输出”；Agent Loop 是“模型决定是否调用工具，程序执行工具，再把结果回给模型继续推理”的闭环。它让模型从只会生成文本，变成能读文件、搜代码、执行命令、编辑文件的执行型系统。

所以核心差异不在模型本身，而在宿主程序是否把外部能力、状态和工具结果接入了循环。

### Q2：面试官问：为什么一定要把工具结果再喂回模型？

因为工具是在宿主程序里执行的，模型本身并不知道执行结果。它只知道自己请求了 `read_file` 或 `run_shell`，但不知道读到了什么、命令是否失败、日志里有什么。

如果不把 `tool_result` 回填，模型下一步推理就会断掉，Agent Loop 会退化成“模型只会提要求，但拿不到环境反馈”。

### Q3：面试官问：Agent Loop 什么时候停止？

当模型这一轮不再返回工具调用时停止。也就是模型判断自己已经有足够信息，可以直接给用户最终回答。

这里停止条件不是程序写死的关键词规则，而是模型基于当前上下文自行决定“继续调用工具”还是“结束输出”。

### Q4：面试官问：为什么说 Agent Loop 的关键不是 if/else，而是结构化协议？

因为程序没有写“用户说修 bug 就先读文件，再跑测试”这种人工流程分支，而是把工具 schema 发给模型，由模型按任务自己选择工具。

程序只负责协议层事情：发送消息、接收 `tool_use`、执行工具、回填 `tool_result`、做权限和状态维护。这样新增能力时主要是加工具，不是重写意图分支。

### Q5：面试官问：Anthropic 为什么把工具结果放在 `role=user` 里？这不是很奇怪吗？

这是它的工具协议要求，不是业务语义上的“用户在说话”。Anthropic 的 assistant 消息里会产生 `tool_use`，宿主程序要在下一条 user 消息里回传对应的 `tool_result`。

所以这里的 `user` 更像协议容器，不是用户真实输入。面试时要区分“API 角色格式”和“业务语义”。

### Q6：面试官问：为什么要保存 assistant 的完整回复，而不是只保存可见文本？

因为 assistant 回复里不只有文本，还可能包含 `tool_use`、tool id、结构化参数。后续的 `tool_result` 必须和这些调用做严格配对。

如果只保存可见文本，就丢掉了协议状态。下一轮模型调用时，历史会变成不完整的对话，甚至被 API 拒绝。

### Q7：面试官问：Agent Loop 的核心状态是什么？

最核心的是消息历史，也就是 `_anthropic_messages` 和 `_openai_messages`。它们承载用户输入、assistant 回复、工具调用和工具结果，是模型每轮决策的直接依据。

除此之外，还有权限模式、token 统计、MCP 初始化状态、memory prefetch、experience journal、当前 task 等运行时状态。

### Q8：面试官问：为什么 MCP 工具要在第一次 `chat()` 时懒加载？

因为 MCP 初始化可能要启动子进程、建立连接、读取外部工具定义，成本不低。用户只是启动 CLI 或进入 REPL 时，不一定马上需要这些工具。

所以第一次真正聊天时再加载更合理，也避免子 Agent 初始化时重复建立主 Agent 的外部连接。

### Q9：面试官问：`async def` 和 `await` 在这个循环里解决什么问题？

Agent Loop 里大量操作都是 IO：模型请求、MCP 通信、web 请求、并发只读工具、memory side query。用 `async/await` 可以把这些等待阶段交给事件循环，不必把整个程序写成层层回调。

它的作用不是“让代码更高级”，而是让一个长任务里多个等待点可以被正确调度。

### Q10：面试官问：Python coroutine 和 JavaScript Promise 在这里怎么类比？

可以把 Python coroutine 理解成“还没执行完的异步任务描述”，JavaScript Promise 是“未来会完成的异步结果”。两者都通过 `await` 等待完成。

但在 Python 里，`async def` 返回的是 coroutine 对象，通常要交给事件循环驱动；这点和 JS 的 Promise 语义相近，但运行模型不同。

### Q11：面试官问：为什么 `Agent.chat()` 里要保存 `_current_task`？

这是为了中断控制。用户按 `Ctrl+C` 时，CLI 需要知道当前哪个 asyncio task 正在跑，然后取消它。

如果不保存这个引用，用户中断只能设置一个布尔值，无法快速打断正在等待的模型请求或工具任务。

### Q12：面试官问：如果预算超限，为什么还要给每个工具调用补一个结果？

因为协议要求每个 `tool_use` 都必须有对应 `tool_result`。即使因为预算原因不再执行工具，也不能把这些调用晾在那里。

所以项目会补一个“未执行”结果，保证历史仍然合法，下一轮如果继续使用这段历史，不会因为协议断裂失败。

### Q13：面试官问：`tool_result` 里是完整工具输出吗？

不一定。小结果会完整回填；大结果会先落盘，再把路径和预览回填。

这个设计说明 Agent Loop 不是机械传递结果，而是和上下文管理联动，控制哪些信息常驻上下文、哪些信息外部化。

### Q14：面试官问：为什么大结果要先落盘再截断？

因为如果先截断，完整信息就丢了。很多 shell 日志、测试堆栈、搜索结果后面还可能继续要看。

当前实现先把完整结果保存到 `~/.mini-claude/tool-results/`，再只给模型预览和路径，兼顾上下文成本和可恢复性。

### Q15：面试官问：Agent Loop 和权限系统是什么关系？

Agent Loop 负责把模型意图变成工具调用，但不会直接执行。真正执行前要先经过 permission gate。

所以可以把 Agent Loop 理解成主流程骨架，而权限系统是骨架上的执行闸门。

### Q16：面试官问：Agent Loop 和工具系统的边界怎么划分？

工具系统回答“有哪些工具、参数是什么、怎么执行”；Agent Loop 回答“什么时候调用模型、什么时候执行工具、结果怎么回填、何时停止”。

前者是能力定义层，后者是运行编排层。

### Q17：面试官问：Agent Loop 为什么适合做能力扩展？

因为新增能力时，只需要增加工具 schema 和执行器，再让模型在循环里按需调用即可。主循环本身一般不用改很多。

这比把每种需求都做成固定流程图更容易扩展，也更符合通用 coding agent 的目标。

### Q18：面试官问：这个项目的 Agent Loop 还缺什么生产级能力？

还缺更强的幂等控制、跨后端统一事件模型、工具调用审计、恢复时的运行时状态重建、对长任务更精细的上下文压缩，以及更严格的错误分类和熔断。

我会把当前实现描述成教学型但结构完整，不会夸成生产级 orchestrator。

### Q19：面试官问：如果模型一直重复调同一个失败工具怎么办？

当前系统至少会把失败结果明确回填给模型，权限系统也会阻止某些重复危险动作。更进一步可以加失败记忆、重复调用检测和策略熔断。

本质上，Agent Loop 不是只会继续循环，而是要把失败也作为状态输入，让模型知道应该换策略。

### Q20：面试官问：一句话总结你对 Agent Loop 的理解？

Agent Loop 本质上是一个“模型做决策、宿主执行动作、环境结果再回流给模型”的闭环状态机，它把大模型从单轮文本生成器变成了受控的执行型编程助手。
