# 02 工具系统

## 第一部分：总结介绍

工具系统是 Agent 能真正操作外部环境的基础。一个工具由三部分组成：工具名、给模型看的描述和参数 schema、真正执行的本地函数。模型只看到 schema，并根据 schema 生成结构化的工具调用；宿主程序收到调用后，解析工具名和参数，执行对应 Python 函数，再把字符串结果包装成 `tool_result` 回填给模型。

Python 版本的工具定义集中在 `/Users/8utterf1y/Desktop/agent项目/claude-mini/claude-code-from-scratch/python/mini_claude/tools.py:37` 的 `tool_definitions`。每个工具都是一个字典，包含 `name`、`description` 和 `input_schema`。例如 `read_file` 要求传入 `file_path`，`edit_file` 要求传入 `file_path`、`old_string`、`new_string`，`run_shell` 要求传入 `command` 和可选的 `timeout`。这些 schema 会在模型请求时通过 API 的 `tools` 字段发送出去。

工具真正发送给模型前会经过 `get_active_tool_definitions()` 过滤。普通工具默认披露完整 schema；带 `deferred: True` 的工具默认不披露，只有激活后才会发送完整 schema。当前 Python 版本里 `knowledge_search`、`enter_plan_mode`、`exit_plan_mode` 是 deferred 工具。系统提示会通过 `get_deferred_tool_names()` 告诉模型这些延迟工具可以用 `tool_search` 获取完整 schema。模型需要时调用 `tool_search`，匹配到的工具名会被加入 `_activated_tools`，下一轮请求时完整 schema 才会被发给模型。这就是文档里说的 ToolSearch 延迟加载机制，主要目的是减少工具 schema 对上下文 token 的消耗。

这里的延迟激活其实是一种“渐进式披露”。模型一开始并不会拿到所有工具的完整参数结构，只会拿到常驻工具的完整 schema，以及在 prompt 中看到一段提示：还有哪些 deferred 工具可以通过 `tool_search` 获取。这个提示来自 `/Users/8utterf1y/Desktop/agent项目/claude-mini/claude-code-from-scratch/python/mini_claude/prompt.py:229` 的 `get_deferred_tool_names()`。真正发送给模型的工具列表则来自 `/Users/8utterf1y/Desktop/agent项目/claude-mini/claude-code-from-scratch/python/mini_claude/tools.py:231` 的 `get_active_tool_definitions()`。这两个函数共同完成了“名字级可见、schema 级按需披露”的设计：prompt 让模型知道有这些能力存在，`tools` 字段只给模型当前可以直接调用的完整工具定义。

延迟激活的完整链路可以这样理解：第一轮调用模型时，`knowledge_search`、`enter_plan_mode`、`exit_plan_mode` 这些 deferred 工具不会出现在 API 的完整 `tools` schema 中，但 prompt 会告诉模型它们可通过 `tool_search` 获取。如果模型判断当前任务需要计划模式或知识库检索，它会先调用常驻工具 `tool_search`。`execute_tool()` 收到 `tool_search` 后，会在所有 `deferred=True` 的工具中按 query 匹配，把命中的工具名加入 `_activated_tools`，并把这些工具的 schema 作为工具结果返回。随后 Agent 把 `tool_search` 的结果作为 `tool_result` 回填给模型。下一轮模型请求时，`get_active_tool_definitions()` 会发现这些工具已经激活，于是把完整 schema 放入 API 的 `tools` 字段，模型这时才可以正式调用这些 deferred 工具。

这个机制要和 Agent Loop 一起看。`tool_search` 本身不是最终业务动作，而是一个“工具发现工具”。它第一次被调用时只是改变本地 `_activated_tools` 状态，并把 schema 信息返回给模型；真正调用被激活工具通常发生在下一轮 Agent Loop。这样做的好处是上下文成本可控：不常用的大工具 schema 不必每轮都发，但模型仍然有路径按需发现。代价是多了一次工具调用和一次模型往返，所以适合放那些不常用、schema 较大、场景较窄的工具，而不是 `read_file`、`grep_search` 这种高频基础工具。

工具调用的执行路径有两层。第一层是 `/Users/8utterf1y/Desktop/agent项目/claude-mini/claude-code-from-scratch/python/mini_claude/agent.py:1209` 的 `_execute_tool_call()`，它处理需要访问 Agent 状态的特殊工具，例如 `enter_plan_mode`、`exit_plan_mode`、`agent`、`skill`、`schedule_wakeup` 和 MCP 工具。第二层是 `/Users/8utterf1y/Desktop/agent项目/claude-mini/claude-code-from-scratch/python/mini_claude/tools.py:719` 的 `execute_tool()`，它处理普通本地工具，例如读写文件、搜索、执行 shell、网页抓取等。

工具执行前还有权限检查。`check_permission()` 会根据 permission mode、用户或项目配置、工具类型和风险等级返回 `allow`、`deny` 或 `confirm`。读工具默认允许；plan 模式下 shell 被禁止，写操作只允许写计划文件；`bypassPermissions` 默认放行但仍受 deny rule 限制；`acceptEdits` 会自动允许编辑类工具；危险 shell、新建文件、编辑不存在文件等情况可能需要用户确认。这个设计让模型不能绕过宿主程序直接执行高风险操作。

本章最重要的细节是 `edit_file` 的安全设计和 read-before-edit。`edit_file` 不做模糊编辑，而是要求 `old_string` 精确匹配，并且匹配位置必须唯一，否则拒绝修改，避免模型改错位置。`execute_tool()` 还会在 `read_file` 时记录文件的绝对路径和 mtime；后续 `write_file` 或 `edit_file` 修改已存在文件前，必须确认这个文件已经被读过，并且 mtime 没变。如果文件被用户或其他进程修改过，Agent 会要求重新读取，避免基于旧内容覆盖用户改动。

读写编辑文件是普通内置工具的典型流程。模型不会直接操作文件系统，而是先根据工具 schema 发出结构化调用，例如 `read_file({"file_path": "xxx.py"})`。Agent 收到 `tool_use` 后，先经过权限检查和 `_execute_tool_call()` 分发；因为 `read_file`、`write_file`、`edit_file` 不是特殊 Agent 工具，也不是 MCP 工具，所以最终会进入 `tools.py` 的 `execute_tool()`，再由它调用 `_read_file()`、`_write_file()` 或 `_edit_file()`。

`read_file` 会用 `Path(file_path).read_text()` 读取文件内容，并把每一行加上行号后返回。行号的作用是帮助模型和用户定位代码位置，尤其适合解释代码、定位 bug、描述修改点。同时，`execute_tool()` 会在读取成功后记录文件绝对路径和修改时间 `mtime`，保存在 Agent 的 `read_file_state` 里，为后续写入或编辑提供“我确实读过这个文件，并且知道当时版本”的依据。

`write_file` 接收 `file_path` 和 `content`，会自动创建父目录，然后把内容写入目标文件。它更适合创建新文件或整体覆盖文件；如果只是修改已有代码的一小段，通常更应该用 `edit_file`。写入完成后，工具会返回成功信息、总行数和前 30 行预览。如果写入的是已存在文件，`execute_tool()` 会先检查这个文件之前是否被读过，以及当前 `mtime` 是否和读取时一致，避免模型没看文件就盲写，或者覆盖用户刚刚改过的内容。

`edit_file` 使用精确字符串替换。模型必须提供 `old_string` 和 `new_string`，工具先读取原文件，查找 `old_string`。如果找不到，就返回错误；如果同一个 `old_string` 出现多次，也会拒绝编辑，因为无法确定模型要改哪一处。只有匹配到唯一位置时，才会把它替换成 `new_string`，并返回一段 diff 告诉模型具体改了什么。这个设计比按行号编辑更稳，因为行号可能随着上下文变化不准确，而精确字符串能保证改的是模型刚刚看过的那段内容。

### 面试话术版本

这个项目的工具系统把模型能力和本地执行解耦。工具通过 `tool_definitions` 声明名字、描述和参数 schema，再通过 API 的 `tools` 字段披露给模型。模型返回 `tool_use` 后，Agent 先做权限检查，再通过 `_execute_tool_call()` 处理特殊工具和 MCP 工具，普通工具交给 `tools.execute_tool()` 分发到具体函数。为了节省上下文，项目支持 `deferred` 工具：默认只在 system prompt 里告诉模型可通过 `tool_search` 激活，需要时才披露完整 schema。文件编辑方面，项目通过 `edit_file` 唯一匹配、read-before-edit 和 mtime 检查，避免盲写、误改和覆盖用户修改。

## 第二部分：面试问答与追问补充

### Q1：这个项目的工具系统整体怎么设计？

工具系统分为定义、披露、调用、权限检查和执行几个阶段。工具定义在 `tool_definitions`；调用模型时通过 `get_active_tool_definitions()` 把可用工具 schema 发给模型；模型返回 `tool_use`；Agent 做权限检查；特殊工具由 Agent 层处理，普通工具由 `execute_tool()` 分发到具体函数；结果包装成 `tool_result` 回填。

### Q2：一个工具包含哪些信息？

包含 `name`、`description` 和 `input_schema`。`name` 是模型调用时使用的工具名，`description` 告诉模型什么时候用这个工具，`input_schema` 定义参数结构和必填字段。

### Q3：为什么工具要用 JSON schema？

schema 是模型和宿主程序之间的结构化契约。模型根据 schema 生成合法参数，宿主程序根据 schema 预期解析参数。这样比自然语言输出稳定，也更容易校验和分发。

### Q4：工具是怎么被模型发现的？

普通工具会在每次模型请求时通过 API 的 `tools` 字段发送给模型。Anthropic 路径在 `_call_anthropic_stream()` 中设置 `"tools": get_active_tool_definitions(self.tools)`；OpenAI-compatible 路径会先转换成 OpenAI function calling 格式。

### Q5：什么是工具披露？

披露就是把工具 schema 发给模型。模型只有看到某个工具的 schema，才知道可以用这个工具以及参数怎么写。普通工具默认披露，deferred 工具默认不披露完整 schema。

### Q6：什么情况工具不会被披露？

带 `deferred: True` 且还没有被激活的工具不会被 `get_active_tool_definitions()` 返回，因此不会进入 API 的 `tools` 字段。当前 Python 版本中 `knowledge_search`、`enter_plan_mode`、`exit_plan_mode` 属于这类工具。

### Q7：模型怎么知道有 deferred 工具？

`build_dynamic_system_context()` 会调用 `get_deferred_tool_names()`，在 system prompt 里加入一段提示：哪些 deferred 工具可以通过 `tool_search` 获取完整 schema。

### Q8：`tool_search` 是怎么工作的？

`tool_search` 接收 query，在所有 deferred 工具里按工具名和描述匹配。匹配成功后，把工具名加入 `_activated_tools`，并返回这些工具的 schema。下一轮模型请求时，`get_active_tool_definitions()` 就会把它们包含进去。

### Q9：为什么需要 deferred tools？

工具很多时，每次都把完整 schema 发给模型会消耗大量上下文 token。deferred tools 让不常用工具按需加载，既保留扩展能力，又降低上下文成本。

### Q10：延迟激活工具的完整链路是什么？

第一轮请求时，deferred 工具不会进入完整 `tools` schema，但 prompt 会告诉模型这些工具名可以通过 `tool_search` 获取。模型需要时先调用 `tool_search`；`execute_tool()` 在 deferred 工具里匹配 query，把命中的工具加入 `_activated_tools` 并返回 schema；Agent 把这个结果作为 `tool_result` 回填；下一轮请求时，`get_active_tool_definitions()` 才会把已激活工具的完整 schema 发给模型。

### Q11：为什么说 deferred tools 是渐进式披露？

因为它不是一开始把所有能力完整暴露给模型，而是分层暴露：第一层只在 prompt 中暴露 deferred 工具名，让模型知道“有这个能力”；第二层通过 `tool_search` 返回完整 schema；第三层在下一轮 API 请求中把已激活工具加入 `tools` 字段，让模型可以正式调用。

### Q12：prompt 里定义 deferred 工具有什么作用？

prompt 里的 deferred section 让模型知道还有哪些工具可按需搜索。如果没有这段提示，模型只能看到常驻工具和 `tool_search`，但不知道应该搜索什么，也不知道系统里隐藏了哪些能力。

### Q13：为什么不直接把 deferred 工具完整 schema 全部放进 prompt？

因为这会失去 deferred 的意义。完整 schema 可能很长，每轮都塞进 prompt 会增加 token 成本，也会增加模型选择工具时的干扰。项目只在 prompt 里放工具名，把完整参数结构留给 `tool_search` 按需返回。

### Q14：为什么激活工具后通常要下一轮才能正式调用？

因为当前模型请求开始时，API 的 `tools` 字段已经固定了。`tool_search` 执行过程中虽然修改了本地 `_activated_tools`，但这不会改变当前这次模型请求已经发送出去的工具列表。Agent 把 `tool_search` 结果回填后，下一轮调用模型时才会重新计算 `get_active_tool_definitions()`，此时完整 schema 才会进入请求。

### Q15：哪些工具适合做成 deferred？

适合不高频、schema 较大、适用场景较窄的工具，例如知识库检索、计划模式切换、外部服务专用工具等。高频基础工具如 `read_file`、`grep_search`、`edit_file` 不适合 deferred，因为它们几乎每个 coding task 都可能用到，延迟激活反而增加往返成本。

### Q16：deferred tools 的代价是什么？

代价是多一次工具调用和一次模型循环。模型需要先发现工具，再在下一轮正式使用工具。因此它节省上下文 token，但可能增加少量延迟。是否使用 deferred 是 token 成本和交互轮次之间的取舍。

### Q17：`tool_search` 本身为什么不能 deferred？

因为 `tool_search` 是发现 deferred 工具的入口。如果它自己也 deferred，模型一开始就没有常驻工具可以用来激活隐藏工具，会形成自举问题。所以 `tool_search` 必须作为常驻工具披露。

### Q18：deferred 工具激活后会一直有效吗？

在当前进程内，激活状态保存在模块级 `_activated_tools` set 中。只要没有调用 `reset_activated_tools()`，已激活工具会继续被 `get_active_tool_definitions()` 包含。它不是写入持久化配置的永久状态。

### Q19：deferred 工具和权限系统是什么关系？

deferred 只控制 schema 是否披露，不代表权限放行。工具被激活并披露后，真正执行前仍然要经过 `check_permission()` 或 auto mode 分类器。也就是说，发现能力和允许执行是两件事。

### Q20：deferred 工具和 MCP 工具有什么关系？

它们解决的问题不同。deferred 是内置工具 schema 的按需披露机制；MCP 是外部工具的动态发现机制。MCP 工具会在第一次 chat 时由 MCP manager 加到 `self.tools`，如果某个 MCP 工具也带有 deferred 标记，同样会被 `get_active_tool_definitions()` 的过滤逻辑影响。

### Q21：`_execute_tool_call()` 和 `execute_tool()` 有什么区别？

`_execute_tool_call()` 是 Agent 层包装，能访问 Agent 状态，负责处理 plan mode、sub-agent、skill、schedule_wakeup 和 MCP 工具。`execute_tool()` 是普通工具分发器，负责读写文件、搜索、shell、web_fetch 等本地工具。

### Q22：为什么 `agent`、`skill` 不直接放在 `tools.execute_tool()` 里执行？

因为它们需要访问 Agent 实例状态。`agent` 要创建子 Agent，`skill` 要走 skill 执行流程，plan mode 要修改当前 Agent 的权限模式。这些都不是普通纯函数能完成的。

### Q23：MCP 工具怎么被发现和调用？

第一次 `chat()` 时，Agent 调用 `_mcp_manager.load_and_connect()`，再把 `get_tool_definitions()` 返回的工具追加到 `self.tools`。执行时如果 `_mcp_manager.is_mcp_tool(name)` 为真，就调用 `_mcp_manager.call_tool(name, inp)`。

### Q24：工具执行前为什么要做权限检查？

模型可能请求有副作用或危险的操作，例如执行 shell、写文件、编辑不存在文件。权限检查让宿主程序决定放行、拒绝或请求用户确认，防止模型直接执行高风险动作。

### Q25：`check_permission()` 有哪些返回结果？

返回 `{"action": "allow"}`、`{"action": "deny", "message": "..."}` 或 `{"action": "confirm", "message": "..."}`。Agent 根据结果决定执行、返回拒绝结果，或询问用户确认。

### Q26：permission mode 有哪些关键区别？

`default` 下读工具默认允许，风险操作可能确认；`plan` 下只允许读和写计划文件，shell 禁止；`acceptEdits` 自动允许编辑类工具；`bypassPermissions` 默认放行但 deny rule 仍优先；`dontAsk` 会自动拒绝需要确认的动作；`auto` 会交给分类器判断。

### Q27：为什么 deny rule 优先级最高？

deny rule 是用户或项目显式设置的安全边界，即使使用 bypass 模式也不能绕过。这样可以保证硬性禁止的工具或路径不会被模型执行。

### Q28：`read_file` 为什么加行号？

加行号方便模型和用户定位代码位置，尤其在解释代码或定位 bug 时有用。但编辑时使用的是真实文件内容中的 `old_string`，不是带行号的文本。

### Q29：`write_file` 做了哪些额外处理？

它会自动创建父目录，写入内容后返回行数和前 30 行预览。如果写的是 memory 目录里的 Markdown，还会尝试更新 memory index。

### Q30：`edit_file` 为什么要求 `old_string` 唯一？

如果 `old_string` 在文件中出现多次，模型可能改错位置。项目通过 `content.count(actual)` 检查唯一性，出现多次就拒绝编辑，让模型提供更精确的上下文。

### Q31：`edit_file` 的 quote normalization 是什么？

它会把智能引号和普通引号做归一化匹配，避免模型复制文本时因为中文输入法或富文本引号导致匹配失败。匹配成功后仍然使用文件里的真实字符串进行替换。

### Q32：什么是 read-before-edit？

Agent 在 `read_file` 时记录文件绝对路径和 mtime。后续修改已存在文件时，如果这个文件没被读过，就拒绝写入或编辑，要求模型先读文件。这样防止模型盲写。

### Q33：mtime 检查解决什么问题？

它防止 Agent 基于旧内容覆盖新修改。如果 Agent 读过文件后，用户或其他进程修改了文件，mtime 会变化，写入前检查失败，Agent 会要求重新读取。

### Q34：新文件为什么可以跳过 read-before-edit？

因为新文件不存在，没有旧内容可读，也不存在覆盖用户已有内容的问题。所以创建新文件可以不强制先读，但在默认权限下可能仍需要确认。

### Q35：模型是直接读写文件吗？

不是。模型只会根据工具 schema 生成结构化 `tool_use`，例如调用 `read_file` 或 `edit_file`。真正的文件系统操作由宿主程序执行：Agent 分发工具调用，`tools.py` 里的 Python 函数实际读取、写入或编辑文件。

### Q36：读文件时为什么要记录 mtime？

mtime 是文件最后修改时间。Agent 读文件时记录 mtime，后续编辑或写入前再比较当前 mtime。如果不一致，说明文件在 Agent 读取后被外部修改过，Agent 会要求重新读取，避免覆盖用户或其他进程的新改动。

### Q37：`write_file` 和 `edit_file` 应该怎么选择？

`write_file` 更适合创建新文件或整体生成文件；`edit_file` 更适合修改已有文件中的局部代码。对已有代码的小范围修改，用 `edit_file` 更安全，因为它要求旧字符串唯一匹配，并返回 diff。

### Q38：为什么 `edit_file` 不按行号编辑？

行号只适合定位和解释，不适合作为可靠编辑依据。上下文变化、插入删除、不同工具返回格式都可能让行号偏移。`edit_file` 使用精确 `old_string` 替换，可以确认要改的就是模型读过的真实内容。

### Q39：`edit_file` 返回 diff 有什么用？

diff 可以让模型知道刚才具体修改了哪些行，也方便用户审查。它同时也是下一轮模型推理的重要上下文，模型可以基于 diff 判断修改是否符合预期，是否还需要继续读文件或运行测试。

### Q40：`grep_search` 为什么先用系统 grep 再 fallback？

系统 `grep` 通常更快，适合大目录搜索。如果系统 grep 不可用、平台是 Windows，或命令执行失败，就用 Python 实现兜底，保证工具可用性。

### Q41：`run_shell` 有哪些风险控制？

它有 timeout，返回 stdout/stderr 和 exit code；执行前还会经过权限检查，危险命令例如 `rm`、`sudo`、`git reset`、`kill` 等会触发确认或拒绝。

### Q42：`web_fetch` 为什么只允许 http/https？

Python 的 `urllib` 可以打开 `file://` 等 scheme，如果不限制，web_fetch 可能变成本地文件读取漏洞。项目只允许 http/https，避免本地文件泄露。

### Q43：工具结果为什么统一返回字符串？

因为模型 API 的 `tool_result.content` 最容易接收文本结果。统一成字符串可以简化工具分发、错误处理和消息回填。

### Q44：工具返回错误时会抛异常吗？

大多数工具内部捕获异常并返回 `"Error: ..."` 字符串。这样 Agent Loop 不会因为一个工具失败直接崩掉，模型可以看到错误并调整下一步。

### Q45：什么是并发安全工具？

`CONCURRENCY_SAFE_TOOLS` 里是只读或低副作用工具，例如 `read_file`、`list_files`、`grep_search`、`web_fetch`、`knowledge_search`。这些工具可以更安全地并发执行。

### Q46：Anthropic streaming 下为什么可以提前执行工具？

当 stream 中某个 `tool_use` block 已经完整生成时，如果工具是并发安全且权限允许，Agent 可以用 `asyncio.create_task()` 先启动执行。这样工具执行可以和模型继续输出重叠，降低整体等待时间。

### Q47：`knowledge_search` 为什么是 deferred？

它面向外部导入知识库，不是每个代码任务都需要。把它设为 deferred 可以避免每次都发送复杂 schema；当任务需要外部文档检索时再通过 `tool_search` 激活。

### Q48：如何新增一个普通工具？

通常要做三步：在 `tool_definitions` 里添加工具名、描述和参数 schema；实现一个 `_xxx(inp)` 函数；在 `execute_tool()` 的 `handlers` 里注册工具名到函数的映射。如果工具有风险，还要补充权限规则。

### Q49：如何新增一个需要 Agent 状态的工具？

除了定义 schema，还要在 `Agent._execute_tool_call()` 中拦截处理，因为这类工具需要访问当前会话、权限模式、子 Agent、MCP manager 或其他 Agent 内部状态。

### Q50：这个工具系统和真实 Claude Code 相比简化在哪里？

这个项目用字典 schema 加函数分发实现核心机制，比较轻量。真实 Claude Code 的工具系统会有更复杂的工具契约、并发调度、权限确认、hook、UI 展示、结果压缩和错误恢复。但核心思想一致：模型只提出结构化调用，宿主负责执行和安全。

### Q51：面试时如何一句话总结工具系统？

工具系统把模型的意图转换成受控的本地执行：工具 schema 负责让模型知道能做什么，Agent 负责权限和分发，具体函数负责执行，结果再回填给模型继续推理。
