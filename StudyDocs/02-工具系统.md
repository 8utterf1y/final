# 02 工具系统

## 第一部分：总结介绍

工具系统是 Agent 能真正操作外部环境的基础。一个工具由三部分组成：工具名、给模型看的描述和参数 schema、真正执行的本地函数。模型只看到 schema，并根据 schema 生成结构化的工具调用；宿主程序收到调用后，解析工具名和参数，执行对应 Python 函数，再把字符串结果包装成 `tool_result` 回填给模型。

Python 版本的工具定义集中在 `/Users/8utterf1y/Desktop/agent项目/claude-mini/claude-code-from-scratch/python/mini_claude/tools.py:37` 的 `tool_definitions`。每个工具都是一个字典，包含 `name`、`description` 和 `input_schema`。例如 `read_file` 要求传入 `file_path`，`edit_file` 要求传入 `file_path`、`old_string`、`new_string`，`run_shell` 要求传入 `command` 和可选的 `timeout`。这些 schema 会在模型请求时通过 API 的 `tools` 字段发送出去。

工具真正发送给模型前会经过 `get_active_tool_definitions()` 过滤。普通工具默认披露完整 schema；带 `deferred: True` 的工具默认不披露，只有激活后才会发送完整 schema。当前 Python 版本里 `knowledge_search`、`enter_plan_mode`、`exit_plan_mode` 是 deferred 工具。系统提示会通过 `get_deferred_tool_names()` 告诉模型这些延迟工具可以用 `tool_search` 获取完整 schema。模型需要时调用 `tool_search`，匹配到的工具名会被加入 `_activated_tools`，下一轮请求时完整 schema 才会被发给模型。这就是文档里说的 ToolSearch 延迟加载机制，主要目的是减少工具 schema 对上下文 token 的消耗。

这里的延迟激活其实是一种“渐进式披露”。模型一开始并不会拿到所有工具的完整参数结构，只会拿到常驻工具的完整 schema，以及在 prompt 中看到一段提示：还有哪些 deferred 工具可以通过 `tool_search` 获取。这个提示来自 `/Users/8utterf1y/Desktop/agent项目/claude-mini/claude-code-from-scratch/python/mini_claude/prompt.py:229` 的 `get_deferred_tool_names()`。真正发送给模型的工具列表则来自 `/Users/8utterf1y/Desktop/agent项目/claude-mini/claude-code-from-scratch/python/mini_claude/tools.py:231` 的 `get_active_tool_definitions()`。这两个函数共同完成了“名字级可见、schema 级按需披露”的设计：prompt 让模型知道有这些能力存在，`tools` 字段只给模型当前可以直接调用的完整工具定义。

延迟激活的完整链路可以这样理解：第一轮调用模型时，`knowledge_search`、`enter_plan_mode`、`exit_plan_mode` 这些 deferred 工具不会出现在 API 的完整 `tools` schema 中，但 prompt 会告诉模型它们可通过 `tool_search` 获取。如果模型判断当前任务需要计划模式或知识库检索，它会先调用常驻工具 `tool_search`。`execute_tool()` 收到 `tool_search` 后，会在所有 `deferred=True` 的工具中按 query 匹配，把命中的工具名加入 `_activated_tools`，并把这些工具的 schema 作为工具结果返回。随后 Agent 把 `tool_search` 的结果作为 `tool_result` 回填给模型。下一轮模型请求时，`get_active_tool_definitions()` 会发现这些工具已经激活，于是把完整 schema 放入 API 的 `tools` 字段，模型这时才可以正式调用这些 deferred 工具。

这个机制要和 Agent Loop 一起看。`tool_search` 本身不是最终业务动作，而是一个“工具发现工具”。它第一次被调用时只是改变本地 `_activated_tools` 状态，并把 schema 信息返回给模型；真正调用被激活工具通常发生在下一轮 Agent Loop。这样做的好处是上下文成本可控：不常用的大工具 schema 不必每轮都发，但模型仍然有路径按需发现。代价是多了一次工具调用和一次模型往返，所以适合放那些不常用、schema 较大、场景较窄的工具，而不是 `read_file`、`grep_search` 这种高频基础工具。

工具调用的执行路径有两层。第一层是 `/Users/8utterf1y/Desktop/agent项目/claude-mini/claude-code-from-scratch/python/mini_claude/agent.py:1209` 的 `_execute_tool_call()`，它处理需要访问 Agent 状态的特殊工具，例如 `enter_plan_mode`、`exit_plan_mode`、`agent`、`skill`、`schedule_wakeup` 和 MCP 工具。第二层是 `/Users/8utterf1y/Desktop/agent项目/claude-mini/claude-code-from-scratch/python/mini_claude/tools.py:719` 的 `execute_tool()`，它处理普通本地工具，例如读写文件、搜索、执行 shell、网页抓取等。

工具执行前还有权限检查。`check_permission()` 会根据 permission mode、用户或项目配置、工具类型和风险等级返回 `allow`、`deny` 或 `confirm`。读工具默认允许；plan 模式下 shell 被禁止，写操作只允许写计划文件；`bypassPermissions` 默认放行但仍受 deny rule 限制；`acceptEdits` 会自动允许编辑类工具；危险 shell、新建文件、编辑不存在文件等情况可能需要用户确认。这个设计让模型不能绕过宿主程序直接执行高风险操作。

本章最重要的细节是 `edit_file` 的安全设计和 read-before-edit。`edit_file` 不做模糊编辑，而是要求 `old_string` 精确匹配，并且匹配位置必须唯一，否则拒绝修改，避免模型改错位置。`execute_tool()` 还会在 `read_file` 时记录文件的绝对路径和 mtime；后续 `write_file` 或 `edit_file` 修改已存在文件前，必须确认这个文件已经被读过，并且 mtime 没变。如果文件被用户或其他进程修改过，Agent 会要求重新读取，避免基于旧内容覆盖用户改动。

读写编辑文件是普通内置工具的典型流程。模型不会直接操作文件系统，而是先根据工具 schema 发出结构化调用，例如 `read_file({"file_path": "xxx.py"})`。Agent 收到 `tool_use` 后，先经过权限检查和 `_execute_tool_call()` 分发；因为 `read_file`、`write_file`、`edit_file` 不是特殊 Agent 工具，也不是 MCP 工具，所以最终会进入 `tools.py` 的 `execute_tool()`，再由它调用 `_read_file()`、`_write_file()` 或 `_edit_file()`。

`read_file` 会用 `Path(file_path).read_text()` 读取文件内容，并把每一行加上行号后返回。行号的作用是帮助模型和用户定位代码位置，尤其适合解释代码、定位 bug、描述修改点。同时，`execute_tool()` 会在读取成功后记录文件绝对路径和修改时间 `mtime`，保存在 Agent 的 `read_file_state` 里，为后续写入或编辑提供“我确实读过这个文件，并且知道当时版本”的依据。

`write_file` 接收 `file_path` 和 `content`，会自动创建父目录，然后把内容写入目标文件。它更适合创建新文件或整体覆盖文件；如果只是修改已有代码的一小段，通常更应该用 `edit_file`。写入完成后，工具会返回成功信息、总行数和前 30 行预览。如果写入的是已存在文件，`execute_tool()` 会先检查这个文件之前是否被读过，以及当前 `mtime` 是否和读取时一致，避免模型没看文件就盲写，或者覆盖用户刚刚改过的内容。

`edit_file` 使用精确字符串替换。模型必须提供 `old_string` 和 `new_string`，工具先读取原文件，查找 `old_string`。如果找不到，就返回错误；如果同一个 `old_string` 出现多次，也会拒绝编辑，因为无法确定模型要改哪一处。只有匹配到唯一位置时，才会把它替换成 `new_string`，并返回一段 diff 告诉模型具体改了什么。这个设计比按行号编辑更稳，因为行号可能随着上下文变化不准确，而精确字符串能保证改的是模型刚刚看过的那段内容。

### 面试话术版本

这个项目的工具系统把模型能力和本地执行解耦。工具通过 `tool_definitions` 声明名字、描述和参数 schema，再通过 API 的 `tools` 字段披露给模型。模型返回 `tool_use` 后，Agent 先做权限检查，再通过 `_execute_tool_call()` 处理特殊工具和 MCP 工具，普通工具交给 `tools.execute_tool()` 分发到具体函数。为了节省上下文，项目支持 `deferred` 工具：默认只在 system prompt 里告诉模型可通过 `tool_search` 激活，需要时才披露完整 schema。文件编辑方面，项目通过 `edit_file` 唯一匹配、read-before-edit 和 mtime 检查，避免盲写、误改和覆盖用户修改。

## 第二部分：面试问答与追问补充

### Q1：面试官问：工具系统最核心的设计点是什么？

核心是把“模型知道能做什么”和“程序真正怎么执行”解耦。模型只看到工具 schema，根据 schema 生成结构化 `tool_use`；宿主程序负责权限检查、参数分发、实际执行和结果回填。

这样工具系统既能扩展能力，又不会让模型直接碰文件系统、shell 或外部服务。

### Q2：面试官问：为什么工具一定要用结构化 schema，而不是让模型直接输出命令文本？

因为 schema 是模型和宿主之间的明确契约。工具名、参数类型、必填字段都固定下来后，分发和校验都更稳定。

如果让模型自由输出命令文本，宿主程序就很难可靠判断意图、提取参数和做安全控制，错误率也会更高。

### Q3：面试官问：工具 schema 和 System Prompt 的分工是什么？

System Prompt 负责告诉模型“什么时候该用什么工具、有哪些行为原则”；schema 负责定义“这个工具叫什么、参数怎么传、哪些字段必填”。

只在 Prompt 里提到工具，不代表模型获得了可调用契约；只给 schema，不告诉模型使用策略，模型也可能乱用工具。

### Q4：面试官问：什么是工具披露？为什么它重要？

工具披露就是把工具 schema 发送给模型。模型只有看到 schema，才知道当前这轮能直接调用哪些工具。

披露控制很重要，因为工具越多，上下文固定成本越大；而且有些工具不适合一开始就完整暴露。

### Q5：面试官问：为什么要做 deferred tools？

因为不是所有工具都值得常驻上下文。像 `knowledge_search`、plan mode 切换这类低频工具，如果每轮都附带完整 schema，会浪费 token。

deferred tools 让这些能力按需激活，减少固定上下文体积。这本质上是“能力可扩展”和“上下文成本可控”之间的折中。

### Q6：面试官问：deferred tools 的完整链路是什么？

第一轮请求时，deferred 工具不会进入 `tools` 字段，只在 Prompt 中暴露名字，告诉模型可以通过 `tool_search` 获取。模型需要时先调用 `tool_search`，本地把命中的工具名加入 `_activated_tools`，并把对应 schema 作为结果返回。

下一轮请求开始时，`get_active_tool_definitions()` 才会把这些已激活工具的完整 schema 真正加入 API 请求，模型这时才能正式调用它们。

### Q7：面试官问：为什么激活后通常要下一轮才能真正调用？

因为本轮模型请求发出去时，`tools` 字段已经定死了。`tool_search` 改的是本地状态，不能回头修改这次已经提交给模型的 schema 集合。

所以延迟激活天然意味着至少多一次工具调用和一次模型轮转。

### Q8：面试官问：为什么说 deferred tool 是一种渐进式披露？

因为它不是一次把所有细节暴露给模型，而是分层暴露。第一层是 Prompt 里的名字级提示，第二层是 `tool_search` 返回 schema 文本，第三层才是下一轮 API 请求里真正可调用的完整工具。

这种设计很适合大量低频工具或大 schema 工具。

### Q9：面试官问：`tool_search` 为什么不能也是 deferred？

因为它是激活 deferred 工具的入口。如果它自己也隐藏起来，模型就没有办法发现隐藏工具，会形成自举问题。

所以 `tool_search` 必须是常驻能力。

### Q10：面试官问：哪些工具适合 deferred，哪些不适合？

适合的是低频、schema 大、场景窄的工具，比如知识库检索、计划模式切换、特定外部服务工具。不适合的是高频基础工具，比如 `read_file`、`grep_search`、`edit_file`。

判断标准不是“这个工具复杂不复杂”，而是“它是否值得每轮都占上下文预算”。

### Q11：面试官问：deferred tool 的代价是什么？

代价是多一次搜索和一轮模型往返，整体延迟会上升一点。如果一个工具高频使用，这个代价可能比节省的 token 还大。

所以 deferred 不是越多越好，而是要结合任务分布和上下文成本做选择。

### Q12：面试官问：工具系统和 Agent Loop 的边界怎么划分？

工具系统负责定义工具、披露 schema、分发执行和返回结果；Agent Loop 负责调用模型、接收 `tool_use`、决定何时继续下一轮。

可以理解为工具系统是“能力层”，Agent Loop 是“编排层”。

### Q13：面试官问：为什么 `_execute_tool_call()` 和 `execute_tool()` 要分两层？

因为有些工具只是普通纯函数，例如读写文件、grep、web_fetch；但有些工具需要访问 Agent 状态，比如 `agent`、`skill`、plan mode、`schedule_wakeup`、MCP 工具。

前者适合留在 `tools.py` 做纯工具执行，后者必须在 Agent 层处理。这个分层能减少普通工具对 Agent 内部状态的耦合。

### Q14：面试官问：为什么 `agent`、`skill`、plan mode 不能直接走普通工具执行器？

因为它们会修改 Agent 运行状态。`agent` 要创建子 Agent，`skill` 要读取并执行 skill prompt，plan mode 要切换当前 permission mode 和 system prompt。

这些都不是单纯输入输出的工具函数，而是调度行为。

### Q15：面试官问：MCP 工具和普通工具的发现流程有什么不同？

普通工具是编译期就写在 `tool_definitions` 里的；MCP 工具是在第一次 `chat()` 时，由 MCP manager 连接外部 server 后动态发现，再追加到 `self.tools`。

也就是说，普通工具是内置能力，MCP 工具是运行时接入能力。

### Q16：面试官问：MCP 工具和普通工具的调用流程一样吗？

前半段一样：都先由模型生成 `tool_use`，都先走 Agent 的权限入口。不同的是执行阶段：普通工具进 `execute_tool()`，MCP 工具转发给 `_mcp_manager.call_tool()`。

所以它们共享 Agent Loop 和权限框架，但执行落点不同。

### Q17：面试官问：工具执行前为什么必须做权限检查？

因为模型提出的只是请求，不代表一定允许执行。像 shell、写文件、外部请求都可能有副作用，必须由宿主程序基于 permission mode、deny rule 和风险判断来决定。

工具系统如果没有 permission gate，本质上就把执行权直接交给模型了。

### Q18：面试官问：为什么 deny rule 优先级这么高？

因为 deny 是用户或项目显式声明的硬边界，不能被默认策略或便捷模式覆盖。这样才能表达“允许大类动作，但禁止危险子集”。

这也是为什么即使在 `bypassPermissions` 下，显式 deny 仍然生效。

### Q19：面试官问：`read_file` 为什么要返回带行号的内容？

因为行号更适合解释代码、定位问题和让模型引用具体位置。用户问“第 42 行为什么报错”时，模型更容易对齐上下文。

但编辑并不依赖行号，而是依赖真实文件内容中的 `old_string`，避免行号漂移导致误改。

### Q20：面试官问：为什么 `edit_file` 要求 `old_string` 唯一匹配？

因为多处匹配会导致修改目标不确定。要求唯一匹配可以确保模型改的是自己刚读过的那一段，而不是文件里另一处相似文本。

这是一种比按行号编辑更稳的局部编辑策略。

### Q21：面试官问：`edit_file` 为什么不直接按行号改？

行号适合定位，不适合作为可靠编辑基准。文件在读写之间可能已经变化，插入删除后行号会偏移，模型也可能引用的是带编号的显示文本。

精确字符串替换虽然也有局限，但至少能和当前文件真实内容做一致性校验。

### Q22：面试官问：什么是 read-before-edit？为什么重要？

就是 Agent 先记录哪些文件被 `read_file` 读过，后续修改已存在文件时，如果没读过就拒绝。这样可以防止模型对未读文件盲写。

对 coding task 来说，这个约束非常有价值，因为它强迫修改建立在当前真实代码之上。

### Q23：面试官问：mtime 检查解决什么问题？

它解决的是“读过，但文件后来变了”的问题。用户、另一个进程或者格式化器都可能在 Agent 读取后改文件。

如果 mtime 不一致，Agent 要求重新读取，相当于轻量版乐观锁。

### Q24：面试官问：新文件为什么可以不走 read-before-edit？

因为新文件不存在，没有旧内容可读，也不存在覆盖用户已有修改的问题。所以创建新文件不强制先读。

但这并不意味着创建新文件一定安全，在默认权限下它仍可能触发确认。

### Q25：面试官问：`write_file` 和 `edit_file` 应该怎么选？

`write_file` 更适合新建文件或整体重写；`edit_file` 更适合已有文件中的局部修改。对已有代码的小改动，用 `edit_file` 更安全，因为它能验证旧内容和返回 diff。

这个选择本质上是在“生成整文件”和“精确局部变更”之间做区分。

### Q26：面试官问：为什么 `edit_file` 返回 diff？

diff 不只是给用户看，也是给模型看。模型下一轮可以基于 diff 判断修改是否符合预期，是否还需要继续编辑或运行测试。

它相当于把“我改了什么”结构化回流给了 Agent Loop。

### Q27：面试官问：为什么工具结果统一返回字符串？

字符串最容易被 `tool_result.content` 承载，也最容易被不同 provider 的协议兼容。统一成文本能降低分发和回填复杂度。

代价是强类型信息少一些，所以复杂结构通常要自己序列化成 JSON 字符串。

### Q28：面试官问：工具失败为什么大多返回 `"Error: ..."`，而不是直接抛异常？

因为工具失败通常是模型需要感知的环境反馈，不一定是整个 Agent 崩溃条件。把错误文本回填给模型，模型可以调整下一步策略。

如果直接抛异常，中断的是整个循环，而不是单个工具调用。

### Q29：面试官问：`grep_search` 为什么优先系统 grep，再做 Python fallback？

因为系统 grep 或 rg 通常更快，尤其在大仓库里性能优势明显。Python fallback 是可用性兜底，保证跨平台和无依赖场景也能工作。

这是典型的“先用最快的系统能力，再用纯 Python 保底”。

### Q30：面试官问：`run_shell` 在工具系统里为什么风险最高？

因为它的能力最泛，几乎等于把操作系统命令执行暴露给模型。它既可能读取状态，也可能删除文件、推送代码、访问网络。

所以它一定要和权限系统、危险命令检测、timeout、输出截断一起看，不能把它当普通工具。

### Q31：面试官问：`web_fetch` 为什么只允许 `http/https`？

因为不限制 scheme 的话，`urllib` 可能支持 `file://` 之类本地路径读取，等于变相绕过文件工具和权限边界。

只允许 `http/https` 是最小必要能力控制。

### Q32：面试官问：什么叫并发安全工具？

就是那些通常没有共享状态写入、可重复执行成本低、并发运行不容易互相破坏的工具，比如读文件、列目录、代码搜索、某些只读检索。

但并发安全不等于绝对无副作用，像 `web_fetch` 就可能有网络侧影响。

### Q33：面试官问：为什么 Anthropic streaming 可以提前执行部分工具？

因为它能在单个 `tool_use` block 完整结束时就知道工具名和完整参数。如果工具并发安全且权限允许，就可以先 `create_task()` 启动执行，让工具 IO 和模型后续生成重叠。

这是工具系统和流式系统结合后的性能优化。

### Q34：面试官问：`knowledge_search` 为什么特别适合做 deferred？

因为它不是每个 coding task 都需要，而且 schema 相对复杂、返回结果也长。把它常驻会增加上下文负担。

当问题确实涉及外部资料或经验库时，再通过 `tool_search` 激活更合理。

### Q35：面试官问：如果我要新增一个工具，应该怎么判断放 Agent 层还是普通工具层？

如果工具只是纯输入输出、无需访问会话状态，优先放普通工具层；如果它要改 permission mode、操作 sub-agent、依赖 MCP manager、访问当前 turn 状态，就应该放 Agent 层。

判断标准是它是不是一个“纯执行器”，还是一个“运行时调度动作”。

### Q36：面试官问：这个工具系统和真实 Claude Code 相比，简化在哪里？

当前实现已经覆盖了 schema、deferred、权限、MCP、并发和文件保护这些核心骨架，但仍是轻量实现。真实系统通常会有更细的 capability policy、UI 展示、审计日志、hook、幂等控制、错误恢复和 provider 兼容层。

我会把它说成“结构完整的教学版”，而不是完整生产工具平台。

### Q37：面试官问：一句话总结这个工具系统？

这个工具系统把模型的工具意图转成受控执行：schema 负责能力披露，Agent 负责权限和分发，普通工具或 MCP 负责实际执行，结果再回流给模型继续推理。
