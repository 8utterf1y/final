# 代码-设计文档一致性审查插件面试问答：真实面试官追问版

> 适配简历项目：**开发代码-设计文档一致性审查工具：调取内部需求文档和 MR 变更信息，基于 Git Diff、AST/Tree-sitter 构建符号索引与双向调用链，形成需求-变更-代码关联的证据上下文；设计证据驱动的多阶段审查引擎，引导大模型依次完成初判、反向质疑、定向取证与结论收敛，实现对需求实现情况的判定与证据追溯。**
>
> 面试表达口径：这是实习期间参与公司内部研发提效方向时做的 **代码审查插件**，已经在部门内接入公司内部 Agent / OpenCode 类工具，用于 MR 检视时辅助提出需求实现一致性方面的检视意见。它不是独立 Agent 产品，也不是个人 demo。它的价值在于补强公司原有 AI 审查工具在复杂 MR 和长设计文档场景下的稳定性、证据性和可审计性。

## 一、STAR 项目总述

### 1. 面试官：请先自然介绍一下这个项目。

面试官您好，我在实习期间做的是一个面向部门内部 MR 检视场景的代码-设计文档一致性审查插件。我们部门主要是 ICT 新通话相关的 C++ 业务开发，代码链路比较长，设计文档里经常会写状态流转、接口行为、异常处理、配置开关、日志上报等要求。MR 检视时，reviewer 不只是看代码风格，还要判断这次变更有没有真正符合设计文档。

公司内部原来已经有一些 AI 辅助审查能力，但是面对复杂 MR 或者长设计文档时，稳定性不够好。主要问题是模型容易只看当前 diff，缺少跨函数上下文；文档和代码一起塞进去后注意力容易分散；单轮回答容易把初步怀疑当成结论；另外输出往往是自然语言建议，缺少证据追溯，reviewer 很难快速复核。

所以我做的这个插件重点不是再做一个普通 AI review，而是把“需求文档、MR 变更、代码实现和证据链”组织起来。插件会通过内部 MCP 与平台接口获取 MR 信息和设计文档，Runtime 锁定 base/head SHA，并准备 detached analysis worktree。之后再用 AST/Tree-sitter 构建符号索引和双向调用链，把变更函数的上下游上下文组织成 evidence pack。模型不是一次性回答，而是按 L3 快速审查和 L4 初判、反向质疑、定向取证、结论收敛的流程输出结构化 finding。

这个插件已经在部门内部 Agent / OpenCode 类工具中用于 MR 检视辅助提意见，定位是 reviewer 的辅助工具，不是替代人工合并决策。它的价值是让 AI 审查在复杂、多文件、跨函数的代码-设计文档一致性场景下更稳定，而且每条结论都能追溯到需求条目、MR diff 和源码证据。

### 1A. 面试官：请用 STAR 法介绍一下这个项目。

**S，背景**：我实习所在方向是 ICT 新通话相关的 C++ 开发和研发效率工具建设。部门本身有大量 C++ 业务代码和设计文档，MR 审查时不仅要看代码质量，还要确认代码实现是否符合设计文档里的业务约束。公司内部已经有一些基于大模型的审查能力，但在复杂 MR、跨函数逻辑、多文件改动和较长设计文档场景下，结果不够稳定。

**T，任务**：我的任务不是重新做一个独立 Agent，而是做一个接入内部 Agent / OpenCode 类平台的审查插件，重点解决原有工具的几个问题：跨函数上下文扩展不足、模型直接读长文档和大 diff 时注意力分散、单轮回答容易误判、输出不可审计、以及审查结论缺少可追溯证据。

**A，行动**：我把审查链路拆成两部分。确定性的部分由插件 runtime 完成，包括通过内部 MCP 与平台接口获取 MR 信息和设计文档，锁定 base/head SHA、准备 analysis worktree，再根据 base/head 计算 Git Diff、用 AST/Tree-sitter 构建符号索引、从变更函数出发做 callers/callees 双向调用链扩展，并把需求条目、diff、源码片段和调用链缺口组织成 evidence pack。模型判断部分则通过受控工具调用和多阶段流程完成，先做 L3 快速审查，再在复杂或不确定场景进入 L4 的初判、反向质疑、定向取证和结论收敛。

**R，结果**：最后插件能够把“需求文档、MR 变更、相关代码、证据 ID、阶段判断”串成一条可追溯链路。输出不再只是自然语言建议，而是结构化 finding，包括对应需求、代码证据、严重级别、变更归因和不确定原因。这个插件已经在部门内用于 MR 检视时辅助提出审查意见，帮助 reviewer 更快定位需求实现遗漏、跨函数影响和证据不足点。

### 2. 面试官：这个项目属于什么类型的项目？

它属于企业内部研发效能和 AI 辅助代码审查方向的插件项目。更准确地说，它不是一个通用聊天 Agent，也不是传统静态扫描工具，而是部署在公司内部 Agent 平台里的 **需求-代码一致性审查插件**。

它的输入来自两个方向：变更侧来自内部 MR 平台，需求侧来自内部需求文档系统。插件会通过内部 MCP 与平台接口获取 MR 元信息、变更范围、设计文档 ID、文档版本和验收项，再把 MR 变更、需求文档和本地代码索引结合起来，帮助大模型更稳定地完成需求实现检查。离线调试时也可以保留本地 base/head 和文本文档作为兜底输入，但正式链路不依赖模型猜测文档来源。

### 3. 面试官：你们部门是做什么的？为什么你实习既做 C++ 又做 AI 工具？

可以这样回答：我实习所在方向主要是 ICT 新通话相关业务，核心代码以 C++ 为主，日常研发会涉及业务逻辑开发、问题定位、MR 提交和设计文档评审。AI 工具这部分不是脱离业务的研究项目，而是围绕团队真实研发流程做提效，尤其是 MR 审查和需求实现一致性检查。

所以我既接触 C++ 业务代码，也参与了内部审查插件建设。这个组合反而是合理的：如果不了解业务代码和评审痛点，很难判断 AI 审查到底需要哪些上下文；如果只懂模型不懂工程，也很难把插件部署到真实研发链路里。

比较稳妥的回答是：这是实习期间在导师和团队同事指导下完成的内部工具方向工作。我主要负责其中审查插件的核心链路设计和实现，包括 MR/diff 输入如何进入审查、需求文档如何解析成 claim、代码索引和调用链证据如何构建、多阶段审查流程如何组织，以及最终结构化报告如何输出。

### 5. 面试官：这个插件部署了吗？效果怎么样？

已经在部门内部部署，用在 MR 检视时辅助 reviewer 提出需求实现一致性方面的检视意见。它不是作为强制门禁直接卡 MR，而是作为检视辅助：对高置信问题给出结构化 finding，对证据不足的地方标记 uncertain，并附上对应需求、diff、源码证据和不确定原因，方便 reviewer 快速复核。

效果上，相比原来一次性把设计文档和 MR diff 交给模型，插件在复杂 MR 上更稳定，尤其是跨函数上下文、证据可追溯和误报控制这几块有明显改善。我们会用历史 MR 和对应设计文档做对比测试：基线是原有单轮审查或直接喂文档加 diff；改进版是索引驱动 evidence pack 加 L3/L4 多阶段审查。对比指标不是只看“模型说得像不像”，而是看高置信 finding 的误报率、需求遗漏召回情况、证据引用有效率、uncertain 是否合理、以及 reviewer 是否采纳。

## 二、背景痛点与对应方案

### 6. 面试官：为什么要做这个插件？原有工具有什么问题？

主要背景是公司内部已经有大模型辅助审查能力，但在复杂代码-设计文档一致性审查上有几个明显短板。

第一是 **跨函数扩上下文缺失**。原有工具更多看当前 diff 或模型自己检索到的片段，但需求实现经常跨多个函数，比如入口校验在上游，状态变更在当前函数，下游还要写库、发事件、打日志。只看 diff 行容易漏掉业务路径。

第二是 **模型幻觉和不可追溯**。模型可能说“代码没有实现某个需求”，但无法稳定指出是哪条需求、哪个 diff、哪段源码支持这个判断。reviewer 很难复核，也很难把结果接入 MR 流程。

第三是 **注意力分散**。需求文档长、MR 文件多时，把所有内容一次性塞给模型，模型容易关注表面相似内容，忽略关键异常分支、配置开关或调用路径。

第四是 **单轮回答不可靠**。一致性审查不是一次判断就够，初判发现的问题可能被替代实现、配置条件、历史代码或非适用需求推翻。没有反向质疑和补证阶段，误报会比较高。

我的方案就是围绕这些痛点拆解：用索引驱动的跨函数上下文解决上下文缺失；用 evidence_id 和全程留痕解决不可审计；用有界 evidence pack 解决注意力分散；用 L3 + L4 多阶段链路解决漏语义、弱泛化和单轮不可靠。

### 7. 面试官：跨函数上下文缺失具体怎么解决？

我没有让模型自己随便搜索代码，而是让 runtime 先对仓库建立符号索引。它会基于 AST/Tree-sitter 提取函数、类、方法、起止行、签名和调用边。MR diff 解析后，会把变更 hunk 映射到具体符号，比如某个改动落在哪个函数里。

然后从这些变更符号出发，做双向调用链扩展。向上查 callers，确认变更逻辑从哪些入口可达；向下查 callees，确认是否调用了正确的下游逻辑，比如持久化、鉴权、状态变更、日志、通知等。这样 evidence pack 不是只有 diff，而是包含变更函数的上下游上下文。

这个设计解决的是“模型看不到关键上下文”的问题。它不是简单扩大上下文窗口，而是有方向、有预算地扩展和本次 MR 相关的代码路径。

### 8. 面试官：模型幻觉和不可审计怎么解决？

我用证据策略解决。每次审查会创建一个 case，runtime 把需求 claim、diff 片段、源码片段、调用边和阶段结果都持久化下来。每条 diff 或源码证据都会生成 evidence_id，模型最终输出 finding 时必须引用这些 evidence_id。

这样如果模型说某个需求没有实现，reviewer 可以看到它基于哪条需求、哪段 diff、哪个函数、哪几行源码做判断。runtime 也会校验模型引用的 evidence_id 是否真实存在、是否属于当前 case、是否支持对应 claim。

所以这里不是单纯要求模型“请不要幻觉”，而是把模型输出变成可以被程序校验和人工复核的结构化结果。

### 9. 面试官：注意力分散怎么解决？

注意力分散的根源是上下文太大、噪声太多。我的处理方式不是把更多内容塞给模型，而是先在 runtime 里做范围收敛。

第一，用 MR 的 base/head 和 path filters 限定本次审查范围。第二，用需求文档结构提取可审查 claim，而不是把整篇文档全部塞进去。第三，用 Git Diff 找到变更 seed，再通过调用链有界扩展，只返回和变更相关的上下游源码。第四，把解析失败、预算触顶这些情况显式标为 gap，避免模型强行脑补。

这样模型面对的是“少量但结构化的证据包”，不是一堆长文本。它更容易把注意力放在需求条目和相关代码之间的关系上。

### 10. 面试官：单轮回答不可靠怎么解决？

我把一次性回答拆成 L3 + L4 多阶段链路。L3 先做快速审查，把每条需求 claim 判成 consistent、inconsistent、uncertain 或 not_applicable。它的目标是筛风险，不是定案。

如果 L3 出现 inconsistent 或 uncertain，auto 模式会进入 L4。L4 分四步：initial 初判先提出候选问题；challenge 反向质疑，主动找能推翻初判的证据，比如替代实现、配置开关、调用不可达、需求不适用；investigate 定向取证，只围绕 gap_id 沿 callers/callees 补上下文；converge 最后收敛，去误报、合并根因、定级和归因。

这套流程针对的是漏语义、弱泛化和单轮不可靠。它让模型先提出问题，再自己挑战问题，再补证，最后才给结论。

## 三、内部 MR 与需求文档接入

### 11. 面试官：公司内部 MR 信息怎么调取？

用户不需要手动复制 diff。插件会通过内部 MCP 与 MR 平台接口获取 MR 的 base/head、分支、仓库、状态、变更文件、作者和关联需求链接，并锁定完整 head SHA。Runtime 拿到这些结构化信息后，会在 analysis worktree 里计算 Git Diff，并把 diff hunk 映射到符号索引。离线或回归测试场景可以显式传本地 repo、base/head 和 paths，但正式 MR 检视链路以内部平台数据为准。

审查插件拿到这些信息后，不直接让模型读，而是把 base/head、path filters 和 repo 传给 runtime。runtime 再在本地仓库执行 Git Diff，得到具体 hunk。这样做比直接调用平台 diff 文本更稳，因为本地还能结合当前源码索引，把 diff 行映射到函数或类。

### 12. 面试官：如何根据 MR 定位 diff？

核心是 base/head。MR 平台会给出目标分支基线和当前提交，runtime 用 `git diff base...head -- path_filters` 计算差异。解析 diff 时会记录每个 hunk 的文件路径、old_start、new_start、行数、change_type 和 diff_text。

接着用 new_start 去符号表里找覆盖该行的最小函数或方法，把它作为 change seed。如果 diff 没有落在已解析符号里，也会保留文件级 diff 证据，不会直接丢弃。这样无论是函数级还是文件级变更，都能进入后续审查。

### 13. 面试官：需求文档怎么连接到 MR？

公司内部通常有固定规范，比如 MR 描述里会挂需求单号或设计文档链接，分支名或 commit message 也可能包含需求 id。插件会通过内部 MCP 与平台接口读取 MR 关联的设计文档，拿到文档 ID、版本、章节结构、表格字段和验收项，再由 Runtime 规范化成 claim。这样 MR 和需求文档的关联来自平台字段和权限校验，不靠模型猜。

这里我会强调：MR 和需求的关联不靠模型猜。模型可以辅助理解需求语义，但“这个 MR 对应哪份设计文档”由平台字段、链接、需求 id 或用户显式输入决定。如果没有关联文档，插件会返回 blocked，提示补充需求链接，而不是假装完成审查。

### 14. 面试官：公司内部需求文档有固定结构，你怎么解析？

内部需求文档有固定模板，比如背景、需求目标、功能说明、接口变更、状态流转、异常处理、权限控制、配置项、验收标准和影响范围。解析时插件会优先使用文档 MCP 返回的结构化信息，比如文档 id、版本、章节 id、标题路径、表格字段、列表项和验收项。

然后把真正可落到代码实现的内容提取成 claim，比如接口字段是否新增、错误码是否处理、某状态下是否触发通知、是否支持幂等、是否有灰度配置、异常分支是否打日志。背景介绍、价值描述这类不适合直接代码验证的内容，可以标为 not_applicable。

同时，工具保留了对 Markdown 的标题、列表和段落级抽取能力，主要用于离线回归、文档导出和兜底解析。在部门内部链路里，会优先使用文档 MCP 返回的结构化章节信息，尤其关注表格、接口字段和验收标准。

### 15. 面试官：如果 MR 没有关联需求文档怎么办？

这类情况不能强行审查。插件会返回明确的 blocked 原因，比如“MR 未关联需求文档”或“未识别到需求 id”。因为没有需求输入时，工具只能做普通代码 review，不能做代码-设计文档一致性审查。

部门流程里提供了降级路径：如果用户手动补充文档链接，可以继续审查；如果没有文档，只输出“无法进行一致性判断”，不要编造需求。这也是工程落地里很重要的边界。

## 四、审查插件架构与职责边界

### 16. 面试官：这个项目为什么不是 Agent，而是插件？

准确说，它是部署在 OpenCode 类 Agent 平台里的审查插件。平台或主 Agent 负责接收用户请求和展示结果；这个插件负责提供 `spec-review` 命令、审查工具集和 runtime。插件已经包含内部 MR 解析、设计文档调取、安全发布预览、真实发布前 head 复验、SARIF 和 Fix MR 相关工具，但它本身不是一个从零实现的独立 Agent 系统。

不过插件内部会利用平台的大模型能力完成多阶段审查推理。也就是说，项目形态是插件，运行方式是“插件提供受控工具 + 平台模型执行审查流程”。面试时我会避免把它说成自己做了一个完整 Agent 产品，而是强调我做的是企业内部 Agent 生态中的审查插件和证据运行时。

### 17. 面试官：插件内部各部分怎么分工？

可以分成四层。

第一层是平台接入层，负责注册 `/spec-review` 命令、工具 schema 和审查提示词，让公司内部 Agent 平台能发现并调用插件。

第二层是数据接入层，负责通过内部 MCP 与平台接口获取 MR 信息和设计文档，锁定 MR base/head，并把需求文档版本、章节和验收项规范化成 Runtime 可处理的 claim。离线调试入口可以复用同一套结构，但正式链路以内部平台数据为准。

第三层是 runtime 证据层，负责 Git Diff、文档 claim 抽取、AST/Tree-sitter 索引、调用链 BFS、evidence_id、状态持久化和报告生成。

第四层是模型审查层，负责基于 evidence pack 做 L3/L4 判断，但它不能自由读取仓库，只能使用插件提供的受控工具。

### 18. 面试官：为什么要把 LLM 和 runtime 分开？

因为二者擅长的事情不一样。runtime 适合做确定性工作，比如路径校验、diff 解析、符号索引、数据库持久化、并发锁和证据 ID。LLM 适合做语义判断，比如需求表达和代码行为是否一致、某个异常分支是否满足设计意图、证据不足时应该怎么归因。

如果所有事情都交给模型，会有幻觉、不可复现和权限风险；如果所有事情都用规则写死，又很难理解自然语言需求和复杂业务语义。所以分层之后，runtime 提供可靠证据边界，模型在边界内做判断。

### 19. 面试官：为什么限制模型只能用插件工具取证？

这是为了保证所有结论都有证据闭环。如果模型能自由 shell、grep、read，它可能绕过 evidence pack 直接读文件，最后输出的依据不在 case 记录里，reviewer 和系统都无法复核。

所以插件要把模型的取证路径收敛到 `start/context/submit/next/finish` 这类工具。start 创建 case，context 生成证据包，submit 保存阶段结果，next 推进状态，finish 生成报告。这样每一步都能留痕。

## 五、证据上下文构建

### 20. 面试官：需求-变更-代码关联是怎么落地的？

它不是单点匹配，而是一条证据链。

首先，需求文档被解析成 claim，每个 claim 保留文档来源、章节和原文。其次，MR base/head 被解析成 diff hunk，每个 hunk 保留文件、行号和 diff_text。然后，AST/Tree-sitter 索引把代码变成符号表和调用边，diff hunk 可以映射到具体函数或方法。最后，从这些变更符号沿 callers/callees 扩展，把相关源码片段组织进 evidence pack。

最终模型看到的是：某条需求 claim、这次 MR 改了哪些代码、这些改动属于哪些函数、上下游调用关系是什么、有哪些源码和 diff 证据、还有哪些证据缺口。

### 21. 面试官：为什么不用关键词匹配需求和代码？

关键词只能处理表面相似，不能理解实现路径。需求里可能写“失败重试”，代码里函数叫 `scheduleRetry`；需求写“通知用户”，代码里可能是发消息队列事件；需求写“幂等”，代码里可能是检查 request id 或状态机版本号。单纯关键词很容易漏召回或误召回。

所以我用 Git Diff 和符号索引先确定本次变更代码，再用模型在 evidence pack 中做语义判断。模型可以理解“不同说法表达同一行为”，但它不能自由扩散，必须基于 runtime 提供的证据。

### 22. 面试官：AST/Tree-sitter 在这里具体解决什么？

AST/Tree-sitter 解决代码结构化问题。它把源码里的函数、类、方法、起止行、签名和调用关系提取出来，使 diff hunk 可以映射到具体符号，也使跨函数上下文扩展可以在符号图上进行。

对 C++ 场景来说，Tree-sitter 可以作为轻量语法解析基础，先提取函数定义、方法定义和调用引用。生产环境如果要更准，可以结合 clangd/LSP 或编译数据库补强类型解析、重载、多态和宏展开。面试时要承认：Tree-sitter 是轻量语法索引，不等于完整 C++ 语义分析。

### 23. 面试官：为什么需要双向调用链？

因为需求实现既要看入口可达性，也要看下游副作用。callers 解决“这个变更会从哪些业务入口触发”，callees 解决“这个变更最终有没有执行需求要求的动作”。

比如新通话业务里，一个状态切换需求可能要求在特定通话状态下更新媒体能力、上报事件并写日志。只看当前 diff 行可能看不到这些动作是否完整；向下查 callees 可以看到是否调用了上报或状态更新函数，向上查 callers 可以看到它是否只在测试路径触发，还是从真实业务流程可达。

### 24. 面试官：调用图不准怎么办？

调用图只作为导航线索，不作为最终证明。静态调用图在 C++ 里会遇到宏、模板、重载、虚函数、多态、回调、异步事件和跨进程调用等问题，所以边上要有解析状态和置信度。解析不出来就标记 unresolved 或 ambiguous，不能说“没找到调用所以一定没实现”。

当前部门落地里，Tree-sitter 负责基础结构索引；对 C++ 宏、模板、重载、虚函数、多态、异步回调这类复杂场景，会结合代码搜索、人工 review 经验和必要的运行证据补证。最终 inconsistent 必须同时满足：需求可验证、代码证据明确、替代路径检查过、和本次 MR 有可辩护关系。

### 25. 面试官：evidence pack 和普通上下文有什么区别？

普通上下文可能只是一堆文本片段，模型读完后很难说明每个结论来自哪里。evidence pack 是结构化的：它包含 claim、change summary、graph、evidence、gaps。每条 evidence 都有 id、类型、路径、行号、内容和元数据。

这样模型输出可以规范化，比如每个 finding 都要引用 evidence_ids。runtime 会校验这些 id 是否存在、是否属于当前 case 和 claim，reviewer 也能按 id 回看原始证据。这就是 evidence pack 比普通上下文更适合企业审查的原因。

## 六、L3 + L4 多阶段审查链路

### 26. 面试官：为什么要设计 L3 + L4，而不是一次性回答？

因为一次性回答在复杂审查中容易漏语义、弱泛化和误报。L3 的作用是快速初筛，让模型用小证据包判断哪些需求已经明显一致、哪些不适用、哪些疑似不一致或证据不足。这样简单场景不必进入重流程。

L4 面向复杂或不确定场景。它要求模型经历初判、反向质疑、定向取证和收敛。这个过程把“发现问题”和“确认问题”拆开，避免模型第一次看到表面差异就下最终结论。

### 27. 面试官：L4 四个阶段分别解决什么问题？

initial 初判解决“候选问题是什么”。模型要说明需求期望、当前代码观察、候选差异和未证实前提。

challenge 反向质疑解决“这个候选问题可能为什么是误报”。它要检查需求是否适用、调用路径是否可达、是否有替代实现、是否有配置开关、是否是历史遗留或非本次 MR 引入。

investigate 定向取证解决“缺什么证据就补什么证据”。它不是重新全仓搜索，也不是简单再拿一页 context，而是围绕 gap_id 调用 `spec_review_investigate`，每轮选择一个 action，例如查 callers、callees、符号、diff 或源码范围，并把 observation 和预算消耗落库。

converge 结论收敛解决“最终如何对 reviewer 负责”。它要去误报、合并重复根因、给严重级别、给变更归因，并明确 evidence_ids。

### 28. 面试官：反向质疑为什么重要？

因为 AI 审查最危险的不是漏说几句，而是把不充分证据包装成确定结论。反向质疑阶段强制模型站在反方检查自己的初判，比如是不是需求条目不适用于这个 MR、是不是另一个模块已经实现、是不是调用路径根本不可达、是不是配置开关关闭、是不是本次 MR 只是暴露了历史问题。

这一步本质上是在降低误报。它让模型先承认自己的判断可能错，再列出需要补充的证据缺口。后面的定向取证就是围绕这些缺口展开。

### 29. 面试官：这是不是只是 prompt 工程？

不是。prompt 只是描述阶段目标，真正保证流程可靠的是插件 runtime 的状态机。每个 case 有当前 stage，每个阶段结果写入 stage_runs，submit 时校验阶段是否匹配，next 时校验当前阶段是否已经提交，finish 时校验是否到达 ready_to_finish。

所以多阶段不是一段长 prompt，而是有状态、可恢复、可审计的工作流。模型不按顺序走，runtime 会拒绝。

### 30. 面试官：如果证据不足，插件会怎么输出？

证据不足时应该输出 uncertain，而不是强行 inconsistent。比如调用链解析不到、需求太抽象、MR 未覆盖关键路径、或者存在多个可能替代实现但没法确认，就要在 finding 里写清 uncertainty reason。

这在生产上很重要。uncertain 不是失败，而是告诉 reviewer “这里需要人工确认或补充动态证据”。比模型自信地给错结论更有价值。

## 七、结构化输出、失败处理与留痕

### 31. 面试官：最终输出是否结构化？

是的。面向人的输出是 Markdown 报告，面向平台消费的是 JSON。每个 finding 包含 claim_id、需求原文或章节、verdict、severity、attribution、reasoning、evidence_ids、uncertainty_reason 和 suggested_action。

这样支持回写 MR 评论，也能进入质量看板或后续评测。插件提供发布预览、MR review、commit status/check-run 和 SARIF 输出；真实发布前要求用户确认 locked head SHA，默认 dryRun，避免把旧结论发到已经变化的 MR 上。比如高置信 inconsistent 作为强提醒，uncertain 作为人工关注项，not_applicable 可以折叠展示。

### 32. 面试官：失败重试机制怎么设计？

我会把错误分成四类。

retryable 是临时错误，比如内部 MCP/平台接口短暂失败、网络超时、git fetch 暂时失败，生产环境中的内部 MR/文档平台接口短暂失败也属于这一类，可以做指数退避，最多重试 2 到 3 次。

recoverable 是可恢复流程错误，比如模型调用了错误阶段、重复 submit、case 状态不清楚，可以先调用 status 恢复当前状态，再继续。

blocked 是缺少必要输入，比如 MR 没有关联需求文档、repo 不存在、没有 base/head，也没有 path 或 fullRepo，这类需要用户或平台补充信息。

fatal 是无法继续的错误，比如数据库版本不兼容、仓库路径非法、Git diff 无法计算且无法恢复。这里要明确失败原因并停止，不能让模型继续编。

### 33. 面试官：如何解决不可审计问题？

三个层面。第一，输入留痕：保存 MR id、base/head、需求文档 id、文档版本和审查范围。第二，证据留痕：保存 diff evidence、source evidence、调用边和 evidence_id。第三，过程留痕：保存每个阶段的 stage result，包括 L3 初筛、L4 初判、质疑、取证和收敛。

这样审查报告不是一个黑盒结论，而是一条可以复盘的链路。后续如果 reviewer 标记误报，也能回看是文档解析错、diff seed 错、调用链缺失，还是模型判断错。

### 34. 面试官：输出怎么接入 MR 页面？

当前 内部 MR 模式下，插件可以先生成 publish preview，预览 MR review、行内评论、检查状态和 SARIF；用户确认 locked head SHA 后，才允许真实发布。展示上不会把所有中间推理都贴到 MR 里，而是按 finding 聚合：先展示结论、严重级别、对应需求、代码位置和建议动作；证据详情可以折叠展开。对于内部 MR 平台，可以复用同样的结构化 payload 做适配。

如果 finding 是 uncertain，会明确写出不确定原因，比如“调用链解析到预算上限”或“需求条目缺少验收标准”。这样 reviewer 能快速决定是要求作者补充实现、补充测试，还是补充需求说明。

## 八、效果验证与对比测试

### 35. 面试官：你怎么证明这个插件比原有工具好？

我会用历史 MR 做对比测试，而不是只拿单次 demo 证明。选择一批有明确设计文档和人工 review 结论的 MR，固定模型、固定输入范围，对比原有单轮审查和新插件审查。

指标可以分为四类：第一，准确性指标，比如 finding precision、需求遗漏召回、误报率；第二，证据指标，比如每个 finding 是否有有效 evidence_id，证据是否支持结论；第三，流程指标，比如 uncertain 是否合理、L4 是否消除了 L3 误报；第四，效率指标，比如平均审查耗时、工具调用次数、reviewer 采纳率。

这样能回答“好在哪里”：不是模型说得更像，而是证据更完整、误报更可控、复杂 MR 下稳定性更好。

### 36. 面试官：如果面试官追问效果数据，你怎么回答？

我会区分“部门内已投入使用”和“全公司强门禁指标”。这个插件已经在部门 MR 检视中辅助提意见，但我不会把它包装成已经有全公司规模化门禁效果。效果回答要落到部门使用反馈和对比测试口径上：复杂 MR 下跨函数上下文是否补齐、模型结论是否可追溯、多阶段是否减少误报、输出是否能被 reviewer 理解和采纳。

如果面试官追问量化，我会说我们用历史 MR 和对应设计文档做对比，基线是原有单轮审查，新方案是 evidence pack 加 L3/L4。部门使用过程中会持续记录 reviewer 采纳、误报标记、作者修改行为和审查耗时变化。这样既说明已经投入使用，也不会虚构不属于实习阶段的全量指标。

### 37. 面试官：怎么证明 L4 反向质疑有效？

可以统计 L3 产生的候选 inconsistent/uncertain 中，有多少在 L4 challenge 后被推翻或降级，有多少通过 investigate 补齐证据后变成高置信 finding。理想情况不是 finding 越多越好，而是最终 finding 更少、更准、证据更充分。

具体可以人工标注一批 L3 候选，比较 L4 前后的误报率。如果反向质疑能识别出需求不适用、替代实现存在、调用不可达、非本次 MR 引入这些误报来源，就说明它有效。

### 38. 面试官：怎么验证证据策略有效？

可以看证据引用有效率：模型输出的 evidence_ids 是否真实存在、是否属于当前 case、是否和对应 claim 有关、是否真的支持 reasoning。还可以看 reviewer 复核成本：有 evidence_id 的 finding 是否更容易被采纳或驳回。

如果没有证据策略，模型输出只能靠人工重新查；有证据策略后，reviewer 可以直接从 finding 跳到需求条目、diff hunk 和源码片段，这就是可审计性的提升。

## 九、真实项目情景追问

### 39. 面试官：这是实际项目还是你自己包装出来的虚拟项目？

这是实习期间围绕部门真实研发流程做的实际工具项目，不是脱离业务的虚拟项目。它的使用场景来自部门日常 MR 检视：开发提交 MR 后，reviewer 需要对照设计文档判断实现是否完整，尤其是状态流转、异常分支、配置开关、日志上报和跨函数调用这些点。

我不会把它说成全公司统一平台或者已经替代人工 review。更准确的说法是：它是部门内部 Agent / OpenCode 类工具中的审查插件，已经用于 MR 检视时辅助提出需求实现一致性意见。它服务的是实际研发流程，输入是部门 MR 和设计文档，输出面向 reviewer 复核。

### 40. 面试官：你们部门具体是做什么的？

我实习所在方向主要是 ICT 新通话相关业务，核心工作还是通信业务能力和 C++ 工程开发。日常会涉及通话状态管理、媒体能力协同、信令或业务流程处理、配置开关、日志与事件上报等模块。这类系统代码链路比较长，很多需求不是改一个函数就结束，而是牵涉入口条件、状态流转、下游调用和异常处理。

所以部门的 MR 检视不只是看代码能不能编译，也要看实现是否符合设计文档。比如设计文档里写了某个状态下要触发特定处理、异常时要降级或上报、某个配置开关下行为不同，这些都需要 reviewer 结合文档和代码链路去判断。

### 41. 面试官：部门为什么会做 AI 开发？这和业务有什么关系？

部门做 AI 工具不是为了单独做一个 AI 产品，而是为了提升内部研发效率。通信业务代码复杂、模块多、设计文档多，MR 检视和问题定位本身就很耗费经验。AI 辅助工具可以帮助 reviewer 更快整理上下文、发现疑似遗漏、定位相关代码和生成结构化检视意见。

这个项目正是从这个业务痛点出发的。原有 AI 审查工具在简单 MR 上可以提供一些帮助，但遇到跨函数、多文件、长设计文档时容易不稳定。所以我们做这个插件，是把部门 reviewer 的审查经验工程化：先把 MR 和文档结构化，再用索引和调用链补上下文，最后让模型基于证据输出意见。

### 42. 面试官：你为什么一边做 C++ 开发，一边做 AI 工具？会不会和岗位不匹配？

我觉得这是匹配的，因为这个 AI 工具服务的就是 C++ 研发流程。只做模型或 prompt，不了解部门 C++ 代码结构，很难知道 MR 检视到底缺什么上下文；只做 C++ 业务开发，不做工具化，也很难把重复的审查经验沉淀下来。

我在实习中接触 C++ 业务开发，所以能理解哪些信息对 review 有价值，比如调用入口、状态机分支、配置条件、异常路径和日志上报。基于这些业务理解，再去做审查插件，就不是泛泛地让模型读代码，而是把真实 reviewer 会看的证据组织出来。所以 C++ 开发经验和 AI 工具建设在这个项目里是互相支撑的。

### 43. 面试官：你是 C++ 开发实习生，为什么会做这个 AI 审查插件？

因为这个插件服务的就是 C++ 业务开发流程。新通话这类业务代码链路长、模块多，MR 审查经常需要对照设计文档确认状态流转、异常分支、配置开关和跨函数调用。团队已有 AI 审查工具在简单 diff 上有帮助，但复杂 C++ MR 容易上下文不够。

所以我的工作不是脱离岗位做 AI 玩具，而是围绕 C++ 研发流程做工具化补强。C++ 业务理解帮助我知道哪些上下文对 review 重要，AI 插件实现则把这些 review 经验固化到工具里。

### 44. 面试官：你具体写了哪些代码？不是只写 prompt 吧？

不是只写 prompt。我的工作包括插件接入层、工具 schema、runtime 调用桥接、Git Diff 解析、文档 claim 抽取、符号索引、调用链扩展、状态机、SQLite 持久化、文件锁和报告生成。

prompt 只是其中一层，用来约束模型在每个阶段应该如何审查。真正保证流程可控的是代码里的 runtime 状态机和证据系统，比如 case_id、stage_runs、evidence_id、next_action、范围校验和重复提交校验。

### 45. 面试官：你们几个人做？你的贡献怎么证明？

可以回答：这是团队内部研发提效方向的工作，不是我一个人决定业务场景。导师和同事提供业务痛点、平台接入方式和 review 反馈，我主要承担审查插件核心链路的设计和实现。我的贡献可以从模块边界说明：MR/diff 输入如何转成 change seed、需求文档如何转成 claim、AST/Tree-sitter 如何生成符号和调用边、证据包如何组织、多阶段审查状态机如何推进、报告如何结构化输出。

面试时不要只说“我参与了”，要能把自己负责的链路讲清楚。能讲清楚输入、状态、输出和失败边界，就是贡献证明。

### 46. 面试官：如果公司已有审查工具，你这个插件的增量价值是什么？

增量价值主要有三点。第一，跨函数上下文从模型自由检索变成索引驱动扩展，能覆盖变更函数的上下游路径。第二，审查流程从单轮回答变成 L3/L4 多阶段，能显式处理初判、质疑、补证和收敛。第三，输出从自然语言建议变成带 evidence_id 的结构化 finding，方便 reviewer 复核和平台留痕。

也就是说，我不是重复做一个审查入口，而是在原有工具不稳定的复杂场景上补强证据、流程和可审计性。

### 47. 面试官：既然已经部门内使用，你最担心什么？

最担心误报被过度信任。因为需求一致性判断涉及语义和上下文，所以部门内使用时它的定位是辅助 reviewer 提检视意见，而不是替代人工判断或直接阻塞 MR。输出时要按置信度和证据充分程度展示，高置信问题作为重点提醒，uncertain 作为人工关注项。

技术上要持续补充输出校验、权限审计、文档版本锁定、MR 评论回写、失败重试和反馈回流。这样即使工具判断错，也能被 reviewer 纠正，并沉淀到后续评测集里。

### 48. 面试官：如果 MR 很大，几十个文件，怎么处理？

不会把几十个文件全部塞给模型。先用 MR 变更文件和 path filter 做范围收敛，再把 diff hunk 映射到符号 seed。上下文扩展时设置 maxNodes 和预算，优先扩展高相关的 callers/callees。超出预算时记录 budget_limit gap，而不是继续扩大。

如果 MR 过大，还可以按需求章节、变更模块或入口路径拆分成多个 case。这样每次审查都有明确范围，模型不会在一个超大上下文里分散注意力。

### 49. 面试官：如果内部需求文档和代码实现不一致，但需求文档本身过期怎么办？

这类情况不能简单判代码错。报告里要体现文档版本和更新时间，如果发现需求和现有接口或历史行为冲突，可以输出需求风险或 uncertain，建议确认设计文档是否过期。

插件通过内部 MCP 与平台接口获取设计文档版本，并在 case 中保存文档来源、版本和内容摘要，能保证同一次 case 的文档来源可追溯。MR 要关联到具体文档版本，而不是永远读取最新版，否则审查结果可能因为文档后续修改而不可复现。

### 50. 面试官：这个插件和普通静态分析工具有什么区别？

静态分析工具主要基于代码规则，比如空指针、资源泄漏、复杂度、规范问题。这个插件的核心输入还有设计文档，它要判断自然语言需求和本次 MR 代码行为是否一致。

所以它需要模型做语义判断，但又不能让模型自由发挥；因此要用 Git Diff、AST/Tree-sitter、调用链和 evidence_id 给模型提供可控证据。这是静态分析和 LLM 审查结合的地方。

## 十、现场回答模板与避坑

### 项目一句话

这是我实习期间围绕公司内部 C++ 研发流程做的代码-设计文档一致性审查插件，部署形态是 OpenCode 类平台插件，用于 MR 检视时辅助提需求实现一致性意见。插件会通过内部 MCP 与平台接口获取 MR 信息和设计文档，再用 Git Diff、AST/Tree-sitter、符号索引和双向调用链构建 evidence pack，最后用 L3/L4 多阶段审查输出可追溯 finding，并支持发布预览、检查状态和 SARIF 集成。

### STAR 简短版

背景是原有 AI 审查工具在复杂 MR 和长设计文档场景下存在跨函数上下文不足、模型幻觉、注意力分散、单轮回答不稳定和不可审计的问题。我的任务是做一个内部审查插件补强这条链路。做法是用 MR 元信息和 Git Diff 锚定变更，用 AST/Tree-sitter 建符号索引和双向调用链，用 evidence_id 和 SQLite 留痕保证可追溯，再用 L3 + L4 多阶段审查降低误报。结果是输出从泛泛自然语言建议变成结构化、可复核的需求实现审查 finding。

### 被质疑“是不是个人小项目”时

不是个人小项目的口径。它的部署形态是公司内部 Agent 平台插件，输入来自公司 MR 平台和需求文档系统，场景来自 C++ 业务 MR 审查痛点，输出面向 reviewer 和 MR 流程。实习阶段我负责核心审查链路和 runtime，导师和团队提供业务场景、平台规范和评审反馈。

### 被质疑“是不是只写 prompt”时

不是。prompt 只是阶段行为约束，真正的工程工作在插件和 runtime：MR/diff 范围解析、文档 claim 抽取、AST/Tree-sitter 符号索引、调用链上下文扩展、evidence_id 生成、状态机推进、失败处理、SQLite 留痕和报告输出。

### 被质疑“效果怎么证明”时

我不会只用主观 demo 证明，而是用历史 MR 和设计文档做对比测试。基线是原有单轮审查或直接喂文档加 diff，新方案是 evidence pack 加 L3/L4。指标看误报率、需求遗漏召回、证据引用有效率、uncertain 合理性、reviewer 采纳率和平均审查耗时。

### 不要踩的坑

不要把它说成独立 Agent 产品，要说是部署在内部 Agent 平台里的审查插件。不要说它能完全替代人工 review，要说它是 reviewer 辅助和证据组织工具。不要把 Tree-sitter 说成完整 C++ 语义分析，要承认静态调用图边界。不要虚构全公司强门禁指标，要区分部门内已使用、历史 MR 对比测试和后续可持续统计的线上反馈指标。不要只讲 prompt，要强调索引、证据、状态机和留痕。
