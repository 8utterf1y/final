# 大仓库索引性能与工程落地面试追问

## 第一部分：总结介绍

这个插件的索引链路发生在 `spec_review_start` 阶段。子 Agent 首次调用 `spec_review_start` 后，TypeScript 层会启动 Python Runtime，Runtime 进入 `workflow.py` 的 `start_case`，第一步就是调用 `build_or_update_index(connection, repo)`。也就是说，审查不是先让模型读 diff，而是先在本地构建一个面向审查的静态索引快照，再基于 Git Diff、需求 claim 和调用链生成 evidence pack。

从代码实现看，索引入口在 `runtime/spec_review_runtime/indexer.py`。它先读取数据库里最新一条 `index_snapshots`，然后扫描仓库源码文件，支持的后缀包括 `.py`、`.go`、`.rs`、`.java`、`.js`、`.ts`、`.tsx`、`.c`、`.cpp` 等。扫描时会跳过 `.git`、`.spec-review`、`node_modules`、`.venv`、`dist`、`build`、`target`、`vendor` 等目录。这个跳过策略很关键，因为大仓库里真正拖慢索引的通常不是业务源码，而是依赖目录、构建产物和生成文件。

当前实现每次 `start_case` 都会创建一个新的 snapshot，但不是每次都全量重新解析。`build_or_update_index` 会把当前文件的 sha256 和上一 snapshot 的 `file_versions` 对比。如果文件内容没变，就调用 `_reuse_file_facts`，把上一 snapshot 对应文件的 symbols 和 edges 复制到新 snapshot；如果文件变了，才重新解析该文件。这就是当前实现的增量复用机制。它不是 watchman 那种实时增量索引，也不是语言服务器级别的精细增量 AST 更新，而是基于文件哈希的 snapshot 级增量复用。

性能上要分首轮冷启动和后续热启动。首轮冷启动必须扫描所有支持语言源码，并对每个文件读取、hash、解析、写入 SQLite。对于小型仓库，例如几百个源码文件、几万行代码，通常是秒级。对于中型仓库，例如几千个源码文件、几十万行代码，冷启动常见是十几秒到一两分钟，取决于磁盘、语言、Tree-sitter parser 是否可用、SQLite 写入速度以及调用边解析成本。对于大型 monorepo，如果有几万文件、百万级以上代码行，单进程全仓冷索引可能进入数分钟级，甚至更久。这个项目通过跳过依赖目录、支持增量复用和允许 `paths` 限制审查范围来控制成本，但当前代码的 `_source_files(repo)` 仍然会扫描整个仓库下所有支持后缀文件，并不是只索引 `paths`。

后续热启动会快很多，但也不是零成本。因为当前实现仍会遍历源码文件、读取文件内容并计算 sha256，用这个 digest 判断是否复用。未变文件不重新 AST/Tree-sitter 解析，只复制上一 snapshot 的符号和边，所以 CPU 解析成本能省掉，但文件系统扫描、读文件、hash 和 SQLite 复制仍然存在。工程上可以这样表达：首次索引成本主要来自解析和写库；后续索引成本主要来自文件遍历、hash 校验和复制事实。对于日常 MR 审查，如果变更只涉及少量文件，热启动通常应该稳定在秒级到十几秒级；如果仓库非常大，瓶颈会转移到全仓扫描和 hash。

索引是否能重复使用，答案是能，但当前是“上一 snapshot 级别复用”，不是跨任意历史版本的智能缓存。数据库表里有 `index_snapshots`、`file_versions`、`symbols` 和 `edges`。每次新建 snapshot 时，未变化文件会从上一 snapshot 复制 symbols/edges。这个设计的优点是简单、可解释、容易恢复；缺点是 snapshot 会持续增长，长时间使用后需要 GC 策略，例如只保留最近 N 个 snapshot，或按 revision 保留被报告引用的 snapshot。

如果索引过程中中断，当前实现不会留下可被误用的半成品 snapshot。`build_or_update_index` 在写入前执行 `BEGIN IMMEDIATE`，过程中如果抛异常，会 rollback。只有完整索引完成后才 commit。因此，如果在索引期间进程崩溃，下一次重新开始时看不到未提交的半成品 snapshot，只能复用上一次已经成功 commit 的 snapshot。这个行为对正确性是好的：宁可重做一部分索引，也不能让 evidence pack 基于不完整符号表生成错误结论。

如果中断发生在索引已经 commit 之后、case 还没完全创建之前，要看 `start_case` 的事务边界。当前 `build_or_update_index` 内部自己 commit 一次，随后 `start_case` 再写 review case、diff seeds 和 claims，最后再 commit。也就是说索引快照可能已经成功保存，即使后续 case 创建失败，下次启动仍能复用这个 snapshot 的文件事实。这个取舍偏向复用性能，但会产生没有 case 引用的 snapshot，生产环境需要周期性清理。

并发上，整个 Python CLI 在进入数据库之前会先拿仓库级 `runtime.lock`。这个锁用的是 `fcntl.flock` 的内核锁，不是靠锁文件是否存在判断。进程异常退出后，内核会释放锁，锁文件保留只用于诊断。这样能避免两个审查同时构建同一仓库索引、同时写 SQLite 导致损坏或 `database is locked`。SQLite 自身也开启了 WAL 和 `busy_timeout=5000`，但这里真正的串行化主力是仓库级锁。

准确性上，索引不是“代码理解”的全部，它只是构建审查证据的底座。当前实现对 Python 有标准库 AST fallback；对其他语言，如果 Tree-sitter 模块没有随发行包提供，会标记 `tree_sitter_pending` 和 `backend_unavailable`，不会伪装成已经完成语义索引。这个边界很重要：生产回答里不能把“没索引到调用边”说成“没有调用”。对于动态派发、反射、依赖注入、框架路由、跨服务调用，静态索引都可能不完整，因此 evidence pack 会把 unresolved 或 ambiguous edge 作为 gap 暴露给 Agent，Agent 应该输出 uncertain 或进入 L4 定向取证。

从实际落地看，大仓库索引要关注的不是单一“快不快”，而是首轮冷启动时间、热启动时间、变更文件命中率、索引复用率、索引失败率、解析覆盖率、证据召回率和审查误报率之间的平衡。一个生产可用的实现通常不会要求每次 MR 都全仓冷索引，而是会结合 MR paths、文件哈希缓存、后台预热、snapshot GC、语言 parser 分包、索引任务进度展示和超时降级策略。当前项目已经有增量复用和范围控制意识，但还可以进一步把 `paths` 下推到索引阶段，减少超大仓库场景下的全仓扫描成本。

## 面试话术版本

大仓库索引的性能我会按冷启动和热启动拆开看。这个工具在 `spec_review_start` 阶段会先构建或更新本地索引，当前实现会扫描仓库里支持语言的源码文件，跳过 `.git`、`node_modules`、`dist`、`build`、`vendor` 这类目录。首轮冷启动需要读取、hash、解析并写入 SQLite，所以小仓库通常秒级，中型仓库可能十几秒到一两分钟，大型 monorepo 如果是全仓冷索引就可能到数分钟级。

后续启动会快很多，因为它不是每次都重新解析所有文件。Runtime 会读取上一 snapshot 的 `file_versions`，对当前文件重新算 sha256；如果文件没变，就直接复用上一 snapshot 的 symbols 和 call edges；只有变更文件才重新解析。这样日常 MR 场景下，如果改动很小，主要成本会从 AST/Tree-sitter 解析变成文件遍历、hash 校验和少量 SQLite 复制，通常能控制在秒级到十几秒级。不过当前代码仍会扫描整个仓库，并没有把 `paths` 下推到索引阶段，所以超大仓库热启动仍可能受文件系统遍历影响。

中断恢复方面，索引构建在数据库事务里执行。如果构建过程中失败，会 rollback，不会留下半成品 snapshot 被后续审查误用。如果索引已经 commit，但后续 case 创建失败，下次仍然可以复用这个成功的 snapshot，这对性能有利，但生产环境要做 snapshot GC，清理没有 case 引用的旧快照。并发方面，Runtime 在连接和写库前会先拿仓库级 `fcntl` 文件锁，同一仓库内写操作串行化，避免两个审查任务同时写 SQLite。

我不会把静态索引说成完全准确的代码理解。它解决的是把 MR diff 关联到符号、调用边和源码证据，为 Agent 提供可追溯 evidence pack。对于反射、动态派发、依赖注入、框架路由和跨服务调用，静态调用图会有边界，所以 unresolved 或 ambiguous edge 会作为 gap 暴露出来，后续 L4 取证阶段围绕这些 gap 补证。生产化时我会重点看索引复用率、解析覆盖率、冷/热启动耗时、证据召回率、误报率和 uncertain 占比，而不是只看索引耗时一个指标。

## 第二部分：面试问答与追问补充

Q：大仓库索引会不会很慢？具体慢在哪里？

A：会，尤其是第一次冷启动。慢主要慢在四个地方：全仓文件遍历、读取文件并计算 sha256、AST/Tree-sitter 解析、symbols/edges 写入 SQLite。当前实现已经跳过依赖和构建目录，但 `_source_files(repo)` 仍然会扫描整个仓库支持语言文件，所以大型 monorepo 的冷索引可能是数分钟级。这个成本可以接受在首次使用或后台预热里，但不适合每次 MR 都全量冷跑。

Q：常见场景的索引速度大概是什么量级？

A：小仓库几百个源码文件通常是秒级；中型仓库几千个源码文件、几十万行代码，冷启动常见十几秒到一两分钟；大型 monorepo 如果有几万源码文件，冷启动可能到数分钟级。热启动通常会明显下降，因为未变化文件复用上一 snapshot 的符号和边，日常小 MR 更常见是秒级到十几秒级。这里的数值不是固定 SLA，实际取决于磁盘、文件数量、语言 parser、SQLite 写入和仓库目录结构。

Q：索引之后能不能重复使用？

A：能。当前实现每次创建新的 index snapshot，但会对比上一 snapshot 的文件 sha256。文件没变就复用上一 snapshot 的 symbols 和 edges，文件变了才重新解析。这是一种简单可靠的文件级增量复用，适合 MR 审查这种“多数文件不变，少量文件变化”的场景。

Q：它是增量索引吗？

A：是文件级增量，不是 AST 节点级增量。它不会像 IDE 或语言服务器那样对单个函数做精细增量更新，而是以文件 sha256 为粒度判断是否复用。这个取舍实现简单、稳定、容易审计，也足够覆盖 MR 审查的大多数场景。代价是大文件只改一行，也要重解析整个文件。

Q：如果索引后中断，重新开始还能用吗？

A：如果索引已经 commit，就能复用；如果索引过程中中断，事务会 rollback，不会复用半成品。`build_or_update_index` 使用 `BEGIN IMMEDIATE`，异常时 rollback，成功后 commit。所以恢复策略是：只复用完整成功的 snapshot，宁可重做，也不基于半成品索引生成证据。

Q：如果索引已经成功，但 case 创建失败，会不会浪费？

A：会留下一个没有被 case 引用的 snapshot，但这不影响正确性。下次启动还能用它作为上一 snapshot 做复用。生产环境需要 snapshot GC，比如保留最近 N 个 snapshot，或者保留仍被报告引用的 snapshot，清掉孤儿快照和过旧快照。

Q：为什么当前每次 start 都要新建 snapshot，而不是直接复用旧 snapshot？

A：因为审查需要绑定到一个明确的代码状态。即使文件没变，也要有一个新的 snapshot_id 表示本次审查看到的仓库 revision 和文件集合。这样 case、evidence、symbols 都能绑定到同一个快照，报告可追溯。未变化文件通过复制 facts 降低成本。

Q：如果仓库很大，为什么不只索引 MR 改动路径？

A：只索引 MR 路径会快，但会损失调用链上下文。需求一致性问题经常出现在调用方入口、权限校验、异常处理或下游副作用里，只看改动文件容易漏判。当前实现选择全仓索引，再用 diff seed 和调用图做有界上下文扩展。生产化可以做折中：默认索引 MR paths 和相邻依赖，必要时再后台扩展全仓索引，或者把 `paths` 下推为候选扫描范围加可配置扩展深度。

Q：`paths` 参数现在能减少索引成本吗？

A：当前主要减少审查范围和 change seeds，不明显减少索引扫描成本。`start_case` 先调用 `build_or_update_index(connection, repo)`，之后才 `resolve_change_scope(..., paths)`。所以从代码顺序看，`paths` 没有下推到索引入口。这个是生产化优化点：大仓库里应该让 paths 影响索引候选文件，至少支持 partial index 或 staged index。

Q：怎么避免索引 `node_modules`、构建产物和虚拟环境？

A：当前 `_source_files` 里有 `SKIP_DIRS`，会跳过 `.git`、`.spec-review`、`node_modules`、`.venv`、`venv`、`__pycache__`、`dist`、`build`、`target`、`vendor`。这个策略对 JavaScript、Python、Rust、Go 项目都很关键，否则依赖目录会把索引时间和证据噪音放大。

Q：SQLite 能承受大仓库索引吗？

A：对单机本地工具来说可以承受中小规模到一部分大仓库场景，因为它是本地嵌入式、部署简单、读写延迟低。当前还用了 WAL 和 busy timeout，并通过仓库级锁串行化写入。但如果是公司级服务、多用户并发、超大 monorepo，就应该拆成服务端索引，或者把索引和 case 状态分库，甚至引入专门的代码搜索/图存储。

Q：并发跑两个审查会不会把索引搞坏？

A：同一仓库不会并发写。Python CLI 一进来就拿 `.spec-review/runtime.lock`，用的是 `fcntl.flock` 内核锁。拿不到锁会等待，超时后返回带锁持有者信息的错误。SQLite 还有 WAL 和 busy timeout，但主要并发保护是仓库级排他锁。

Q：中断后锁文件还在，会不会导致永久锁死？

A：不会。这个实现不是靠锁文件存在判断，而是靠内核文件锁。进程退出或崩溃后，内核锁会释放；锁文件保留只是为了记录 pid 和 acquired_at，方便超时诊断。真正的锁状态由 `fcntl.flock` 决定。

Q：索引的准确性怎么保证？

A：准确性不是绝对保证，而是通过结构化证据和不确定性标注控制风险。Python 文件可以用标准库 AST 抽取函数、类和调用；其他语言优先用 Tree-sitter 查询。如果 parser 不可用，当前实现会记录 `backend_unavailable`，不会假装已经完成语义索引。调用边如果无法唯一解析，会标成 unresolved 或 ambiguous，并作为 gap 给到 Agent。

Q：如果调用图不准，审查结论还可靠吗？

A：调用图在这个系统里是导航线索，不是单独定案证据。prompt 也要求不能只靠调用图证明行为。最终 inconsistent 必须引用具体 diff/source evidence_id，并且在 L4 收敛时检查替代路径、适用性和变更归因。所以调用图不准时，正确处理应该是产生 gap 或 uncertain，而不是强行下结论。

Q：为什么要保存 snapshot，而不是每次 context 现查文件？

A：snapshot 让本次审查的证据有固定代码基准。否则审查过程中用户继续改代码，context 每次读到的源码可能不一致。当前实现虽然源码片段读取时仍来自工作区文件，但 symbols/edges 和 case 绑定到 snapshot_id。生产化应进一步把源码片段也绑定到 Git blob 或缓存内容，避免工作区变化影响证据。

Q：如果用户在索引后又改了代码，会发生什么？

A：当前 case 已经绑定到 start 时创建的 snapshot 和 head_revision，但后续 `_source_for_symbol` 读取源码片段时是从工作区路径读文件。这意味着如果用户在审查过程中修改了文件，source evidence 可能和索引时的符号行号不完全一致。这是当前实现的一个边界。生产化应该从 Git object、临时 checkout 或索引时保存的 content slice 读取证据，保证 case 内证据不可变。

Q：怎么衡量索引复用是否有效？

A：看 `index_snapshots` 里的 `files_total`、`files_parsed`、`files_reused`。复用率可以定义成 `files_reused / files_total`。日常 MR 场景下，复用率应该很高，通常大多数文件都应该 reused。如果复用率长期很低，要排查是否有生成文件频繁变化、换行或格式化导致 hash 抖动、工作区 revision 不稳定，或者 snapshot GC 策略过于激进。

Q：怎么衡量索引质量？

A：看 parser 覆盖率、parse_status 分布、symbols 数量、edges 数量、unresolved/ambiguous edge 占比，以及最终 evidence pack 对历史缺陷的召回能力。只看索引耗时没有意义，索引很快但边都 unresolved，Agent 只能输出 uncertain；索引很全但耗时过长，也不适合 MR 阻塞式审查。

Q：如果要生产化优化大仓库性能，优先做什么？

A：优先做五件事。第一，把 `paths` 下推到索引阶段，支持局部索引和按需扩展。第二，引入后台预热，在 MR 创建或更新时提前构建 snapshot。第三，做 snapshot GC，控制 SQLite 体积。第四，按语言拆 parser 能力和超时策略，避免单个异常文件拖垮整次审查。第五，记录索引指标，包括 cold start、hot start、files_parsed、files_reused、parse failures 和 graph gap ratio。

Q：为什么不用向量库做代码检索，反而自己建符号索引？

A：向量检索适合语义召回，但不擅长提供精确调用关系和可审计证据边界。这个场景要回答的是“MR 是否实现了需求”，关键是变更点、符号、调用方、下游影响和 evidence_id。符号索引和调用图能把 diff 映射到代码结构，向量检索可以作为补充，比如召回相关文档或相似实现，但不能替代结构化索引。

Q：为什么不用语言服务器 LSP？

A：LSP 的语义能力更强，尤其是跨文件跳转和类型解析，但部署复杂度更高，不同语言需要不同 server，项目依赖环境也可能很重。这个插件定位是可直接投放到 OpenCode 的本地工具，所以先选择 AST/Tree-sitter 这种轻量、无常驻服务的方案。生产化如果面向少数核心语言，可以接入 LSP 作为增强后端。

Q：如果 MR 很小，为什么还要构建索引？

A：因为小 diff 不等于影响范围小。一个小改动可能改变权限、重试、幂等、异常处理或入口参数，影响在调用方和下游。索引的作用是把 diff seed 放回代码结构和调用链里，而不是只看 patch 文本。不过为了性能，生产化可以对纯文档、纯测试或极小低风险变更走 fast path。

Q：如果索引失败，审查应该继续吗？

A：要看失败类型。如果是 repo 不存在、范围不明确、数据库损坏这类基础错误，应该直接阻断。如果是部分语言 parser 不可用或个别文件 syntax error，可以降级继续，但必须把 parse_status 和 backend_unavailable 暴露给 Agent，让结论变成 uncertain 或进入 L4 补证，不能伪装成完整审查。

Q：这个实现对 MR 平台的落地还缺什么？

A：当前代码用本地 Git diff 和本地需求文档路径，生产落地还要接 MR 平台 API 和文档系统 API。MR 侧要拿 base/head、changed files、review comments、commit metadata；文档侧要拿文档版本、章节锚点和权限校验。否则报告虽然能本地生成，但还没有形成平台化闭环，比如自动评论到 MR、阻断合并、统计历史质量指标。

Q：索引数据会不会泄露敏感代码？

A：当前索引都写在业务仓库本地 `.spec-review/index.sqlite`，没有网络上传，这对本地插件是合适的。但它确实会持久化源码片段 evidence 和符号信息，所以应该把 `.spec-review/` 加入 `.gitignore`，并在生产环境加密或设置访问权限。如果接入服务端，还要做租户隔离、最小权限和数据保留策略。

Q：怎么设计超时和降级策略？

A：索引阶段应该有文件级、语言级和整体 case 级超时。超过阈值时，不应该直接失败所有审查，而是生成部分索引并标注 coverage，比如哪些路径已解析、哪些路径超时。对高风险 MR 可以要求 deep 模式继续补证，对低风险 MR 可以输出 uncertain 或需要人工复核。关键是不能把超时当成“没有问题”。

Q：如果 SQLite 越来越大怎么办？

A：需要 snapshot GC 和报告保留策略。索引 snapshot 可以只保留最近 N 个，或者保留仍被 active case、recent report 引用的 snapshot。evidence 内容可以按 case 生命周期归档，老报告只保留 markdown/json 和 evidence 摘要。还可以把索引 facts 和审查 case 状态拆成两个数据库，便于独立清理和备份。

Q：怎样回答“这个方案能不能支撑公司级大规模使用”？

A：当前形态适合本地插件和团队级落地，优势是部署简单、权限边界清楚、无服务依赖、可追溯。公司级大规模使用需要升级为混合架构：本地 Agent 负责交互和审查编排，服务端负责预热索引、MR 元数据、文档版本、指标统计和缓存共享。否则每个开发者本地重复冷索引大型 monorepo，成本会比较高。
