## 2. 文档目的

本文档定义员工费用报销从提交到付款的业务规则、系统行为、异常处理和验收标准。读者不需要熟悉 RFC 或特定技术标准，应能通过场景、规则和示例理解预期行为。

本文档同时作为：

- 产品、开发、测试和安全团队的共同交付基线。
- 代码变更审查时的需求依据。
- 自动化一致性审查的可追溯需求源。

## 3. 背景与目标

公司现有费用报销流程存在重复提交、审批权限不清、付款失败后处置不一致和状态追溯困难等问题。新服务的目标是：

1. 保证同一提交请求不会创建多张报销单。
2. 保证报销申请人不能审批自己的申请。
3. 根据金额采用一级或两级审批。
4. 对短暂性付款故障进行有界重试，不放大永久性故障。
5. 在付款开始前允许申请人取消，并防止已取消单据被后台任务付款。
6. 对每次成功状态转换留下不含敏感内容的审计记录。

## 4. 范围

### 4.1 本期范围

- 员工提交单币种报销申请。
- 经理审批。
- 财务对大额申请二次审批。
- 申请人在付款前取消。
- 后台付款任务与有界重试。
- 状态变化审计。

### 4.2 非本期范围

- 发票 OCR 和真伪验证。
- 税务计算。
- 多币种换算。
- 会计凭证生成。
- 与外部银行的对账。

非范围功能的不存在不应被判定为需求缺失。

## 5. 角色与权限

| 角色 | 代码 | 允许的操作 |
|---|---|---|
| 员工 | EMPLOYEE | 提交报销；查看自己的报销；在付款开始前取消自己的报销 |
| 经理 | MANAGER | 对他人的待经理审批报销进行通过或驳回 |
| 财务 | FINANCE | 对他人的待财务审批报销进行通过或驳回 |
| 付款任务 | SYSTEM | 领取已审批单据并调用付款网关；不代表人工审批者 |

权限判断以服务端传入的已认证 Actor 为准，不接受请求体中自报的角色。

## 6. 名词说明

| 名词 | 说明 |
|---|---|
| 请求幂等键 | 客户端为一次业务提交生成的唯一 `request_id` |
| 总尝试次数 | 首次调用加所有重试调用的总和 |
| 短暂性失败 | 超时、限流、网关暂时不可用等稍后再试可能恢复的失败 |
| 永久性失败 | 账户无效、币种不支持等重试不会改变结果的失败 |
| 付款开始 | 后台任务原子地将状态从 `APPROVED` 改为 `PAYING` 的时点 |

## 7. 整体业务流程

```text
员工提交
    ↓
PENDING_MANAGER
    ├─ 驳回 → REJECTED
    ├─ 取消 → CANCELLED
    └─ 经理通过
          ├─ 金额 <= 1000.00 → APPROVED
          └─ 金额 > 1000.00  → PENDING_FINANCE
                                     ├─ 驳回 → REJECTED
                                     ├─ 取消 → CANCELLED
                                     └─ 财务通过 → APPROVED

APPROVED
    ├─ 取消抢占成功 → CANCELLED
    └─ 付款任务抢占成功 → PAYING
                                      ├─ 成功 → PAID
                                      └─ 失败/重试耗尽 → PAYMENT_FAILED
```

`APPROVED -> CANCELLED` 与 `APPROVED -> PAYING` 是互斥竞争，任意时刻只能有一方成功。

## 8. 功能需求

### FR-01 报销提交幂等性

#### 业务场景

客户端在网络超时后可能使用同一 `request_id` 重复提交。系统必须防止因重试生成多张报销单。

#### 处理规则

1. `request_id` 在同一申请人范围内唯一。
2. 首次合法请求创建一张报销单并返回其 ID。
3. 同一申请人使用同一 `request_id` 再次请求时，必须返回原报销单，不能创建新单据。
4. “查询已有单据”与“创建新单据”必须处于同一原子临界区，并发请求不得各自创建。
5. 不同申请人可以使用相同的 `request_id`。

#### 验收标准

- 串行重复调用 10 次，返回的 expense ID 唯一。
- 并发重复调用 20 次，最终仓库中只有一张对应单据。
- 两个不同员工使用相同 `request_id`，各自生成一张单据。

### FR-02 审批权限与职责分离

#### 业务场景

为避免自批和越权审批，系统需要同时验证审批人角色和申请人身份。

#### 处理规则

1. 经理审批仅允许 `MANAGER` 角色执行。
2. 财务审批仅允许 `FINANCE` 角执行。
3. 无论行为人兼任什么角色，只要 `actor.user_id == expense.requester_id`，审批必须被拒绝。
4. 被拒绝的审批不得改变状态，不得产生“审批成功”审计记录。
5. 审批操作只能作用于对应待审状态；重复审批或跨级审批必须被拒绝。

#### 验收标准

- 员工、无角色用户不能审批。
- 具有 `MANAGER` 或 `FINANCE` 角色的申请人仍不能自批。
- 合法的他人审批可以推进状态。

### FR-03 金额分级审批

#### 规则

1. 审批阈值为 `1000.00 CNY`。
2. 金额小于或等于 `1000.00`时，经理通过后直接进入 `APPROVED`。
3. 金额大于 `1000.00`时，经理通过后进入 `PENDING_FINANCE`，必须由财务再次通过才能进入 `APPROVED`。
4. 阈值比较使用十进制金额，不允许使用二进制浮点近似值改变边界结果。
5. 本期仅支持 `CNY`；其他币种在提交时拒绝。

#### 边界示例

| 金额 | 经理通过后状态 |
|---:|---|
| 999.99 | APPROVED |
| 1000.00 | APPROVED |
| 1000.01 | PENDING_FINANCE |

### FR-04 付款前取消与竞争保护

#### 业务场景

申请人可能在付款任务扫描到单据的同时发起取消。仅检查 API 路径的状态不足以防止后台已读取的旧快照继续付款。

#### 处理规则

1. 只有报销申请人可以取消自己的单据。
2. `PENDING_MANAGER`、`PENDING_FINANCE` 和 `APPROVED` 允许转换为 `CANCELLED`。
3. `PAYING`、`PAID`、`REJECTED`、`CANCELLED` 和 `PAYMENT_FAILED` 不允许取消。
4. 付款任务必须使用仓库提供的原子 `claim_for_payment` 操作，仅当当前持久化状态仍为 `APPROVED` 时才可改为 `PAYING`。
5. 付款任务不得依赖早先读取的对象快照直接开始付款。
6. 取消和付款抢占并发发生时，只允许一个状态转换成功。

#### 验收标准

- 已取消单据不调用付款网关。
- 竞争测试的最终状态只能是 `CANCELLED` 或从 `PAYING` 继续完成的付款结果，不能出现“状态是 CANCELLED 但网关已扣款”。

### FR-05 付款重试策略

#### 处理规则

1. 付款网关每次调用必须使用 `expense_id` 作为网关幂等键。
2. 成功时立即停止，将单据转为 `PAID`并记录网关交易号。
3. 只有 `TransientPaymentError` 可以重试。
4. `PermanentPaymentError` 不得重试，首次失败后立即进入 `PAYMENT_FAILED`。
5. 短暂性失败的总尝试次数上限为 3，即首次调用加最多两次重试。
6. 两次重试前的等待时间依次为 1 秒、2 秒，不要在最后一次失败后再等待。
7. 3 次短暂性失败全部发生后，状态转为 `PAYMENT_FAILED`。

#### 验收矩阵

| 网关结果序列 | 调用次数 | 等待序列 | 最终状态 |
|---|---:|---|---|
| success | 1 | [] | PAID |
| transient, success | 2 | [1] | PAID |
| transient, transient, success | 3 | [1, 2] | PAID |
| transient × 3 | 3 | [1, 2] | PAYMENT_FAILED |
| permanent | 1 | [] | PAYMENT_FAILED |

### FR-06 状态变化审计

#### 处理规则

1. 每一次成功状态转换必须产生一条审计事件。
2. 审计事件至少包含：`expense_id`、`actor_id`、`action`、`from_status`、`to_status`、`occurred_at`。
3. 系统后台付款操作的 `actor_id` 固定为 `SYSTEM`。
4. 未通过权限或状态检查的操作不能产生成功转换事件。
5. 审计事件不得包含报销事由原文、银行账户、身份证件、凭证附件内容等敏感信息。

#### 验收标准

- 从提交到成功付款的每个状态都可按时间追溯。
- 驳回、取消和付款失败均有对应记录。
- 审计记录的 metadata 中不出现 `purpose`、`bank_account` 或原始请求体。

## 9. 数据模型

### 9.1 Expense

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| id | string/UUID | 是 | 报销单唯一标识 |
| requester_id | string | 是 | 申请人 ID |
| request_id | string | 是 | 客户端幂等键 |
| amount | decimal(12,2) | 是 | 正数金额 |
| currency | string | 是 | 本期固定 CNY |
| purpose | string | 是 | 1–500 字符，业务敏感字段 |
| status | enum | 是 | 当前状态 |
| payment_reference | string/null | 否 | 付款成功后的网关交易号 |
| version | integer | 是 | 并发更新版本 |

### 9.2 数据约束

- `(requester_id, request_id)` 必须有唯一约束或等价的原子唯一性保证。
- `amount > 0`，最多两位小数。
- `payment_reference` 只能在 `PAID` 状态下非空。
- 状态更新必须通过带期望旧状态的条件更新、行锁或其他等价原子机制完成。

## 10. 服务接口契约

### 10.1 提交报销

```text
submit_expense(actor, request_id, amount, currency, purpose) -> Expense
```

- actor 必须是已认证用户。
- `request_id` 不能为空。
- `amount` 必须是大于 0 的 Decimal。
- 币种不是 CNY 时返回参数错误。

### 10.2 审批

```text
approve_manager(actor, expense_id) -> Expense
approve_finance(actor, expense_id) -> Expense
reject(actor, expense_id, reason_code) -> Expense
```

`reason_code` 是非敏感枚举代码，不在审计中写入自由文本理由。

### 10.3 取消

```text
cancel(actor, expense_id) -> Expense
```

取消失败时应返回权限错误或状态冲突，不得静默成功。

### 10.4 后台付款

```text
PayoutWorker.process(expense_id) -> PaymentOutcome
```

- 单据不是 `APPROVED` 时返回 `SKIPPED`。
- 成功返回 `PAID`。
- 永久性失败或重试耗尽返回 `FAILED`。

## 11. 异常处理

| 异常 | 场景 | 是否可重试 |
|---|---|---|
| ValidationError | 参数、金额或币种不合法 | 否，修正请求后重新提交 |
| AuthorizationError | 角色不允许或申请人自批 | 否 |
| StateConflictError | 当前状态不允许该操作 | 重新读取后由业务决定 |
| TransientPaymentError | 网关短暂性故障 | 是，受 FR-05 限制 |
| PermanentPaymentError | 网关永久性拒绝 | 否 |

## 12. 非功能性需求

### NFR-01 安全

- 权限校验在服务端执行。
- 日志和审计事件不记录报销事由原文。
- 错误信息不暴露仓库内部结构或付款网关密钥。

### NFR-02 并发一致性

- 幂等创建、取消和付款抢占均必须具有原子性。
- 系统不依赖单进程或 Python GIL 作为业务正确性保证。

### NFR-03 可测试性

- 付款网关、时钟/等待器和审计接收器必须可替换，单元测试不进行真实等待或外部付款。
- 并发幂等和取消/付款竞争必须有自动化测试。

### NFR-04 性能基线

- 不含外部付款网关时，提交、审批和取消操作的服务端 P95 处理时间应小于 200ms。
- 不为达成性能基线牺牲 FR-01 和 FR-04 的原子性。

## 13. 可观测性

服务至少暴露以下计数指标：

- `expense_submissions_total`
- `expense_approval_denied_total`
- `expense_cancellations_total`
- `payment_attempts_total`
- `payment_transient_failures_total`
- `payment_permanent_failures_total`
- `payment_failures_total`

指标可以带有限枚举标签，不能使用 `expense_id`、`requester_id` 或 `purpose` 作为高基数标签。

## 14. 验收与追溯矩阵

| 需求 | 关键实现证据 | 必要测试 |
|---|---|---|
| FR-01 | 原子 create-or-get；复合唯一性 | 串行重复、20 线程并发重复、不同用户同 key |
| FR-02 | 角色检查；requester/actor 不等检查 | 越权、自批、正常他人审批 |
| FR-03 | Decimal 阈值比较；两级状态转换 | 999.99、1000.00、1000.01 |
| FR-04 | 条件状态更新；worker 调用 claim | 先取消后 worker、取消/claim 竞争 |
| FR-05 | 异常分类；尝试上限；1/2 秒序列 | 验收矩阵的 5 组序列 |
| FR-06 | 统一 transition audit；敏感字段排除 | 全状态轨迹、拒绝不记成功、敏感词扫描 |

## 15. 发布准入条件

1. FR-01 至 FR-06 的必要测试全部通过。
2. 不存在已知的自批、已取消付款或重复单据风险。
3. 重试策略的次数和等待序列经自动化测试确认。
4. 审计数据通过敏感信息检查。
5. 代码审查报告对未能证明的路径明确标记为不确定，不得将“未找到”直接当作“未实现”。
