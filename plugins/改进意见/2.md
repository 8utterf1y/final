一、结构：不是"52 例"，而是 52 条规则 × 3 变体 = 156 个用例
每个用例（如 ALP-001/01_mul_overflow）是一个完整的最小 C/C++ 工程（CMakeLists + include/ + src/），附 3 个文件：

文件	作用
expected.json	人工标注的 ground truth：rule_id、severity、精确 file_path:line_start:line_end、evidence_chain（证据链）、fix_hint（修复提示）、distractors（干扰项）、negative_assertions（负断言）、case_type
README.md	用例说明（Rule/Variant/Description + 构建命令）
源码	植入缺陷的最小工程，可真实编译运行
case_type 分布：144 个 positive（有真缺陷）+ 12 个 negative（CTX-001~004，代码合法但含"陷阱"防误报）。

二、15 个类别及含义（按每条规则首个变体的描述归纳）
前缀	类别（推断全名）	代表缺陷
ALP	Arithmetic 算数运算	乘法溢出致分配过小、无符号减法绕回、除零、死循环
API	API 误用	(void) 吞关键返回值、未校验 channel 范围即索引
CON	Concurrency 并发	lock 中途 return 未 unlock、锁序相反致死锁
CQT	Code Quality 代码质量	宏拼写错误 CONIFG、冗余 memcpy 覆盖、缺 cstdint
CTX	Cross-function Context 跨函数上下文	专测上下文注入：注释伪代码/过期文档/跨文件同名函数，多半是 negative
EXC	Exception 异常(C++)	noexcept 抛异常致 terminate、new 后分支未 delete
FMT	Format 格式化	%d 配 size_t、外部 payload 直接作格式串
IMP	Implementation 一致性	实现丢 const、malloc 返回未检查、参数缺 const
LER	Log/Error Report 日志	日志引用错变量、Upload 日志写 Download、恒打印 success
LGC	Logic 逻辑	switch 缺 default 分支、状态非法跃迁、参数写反、off-by-one
RES	Resource 内存/资源	越界拷贝(UAF/泄漏/空指针/静态对象 free/错误路径锁泄漏)
TYP	Type 类型	const 强转写入、size_t→uint32 截断、void** 传参、void 返错误码
UND	Undefined Behavior 未定义行为	void* 指针算术
UNI	Uninitialized 未初始化	声明未初始化即读、结构体部分字段初始化
USF	Unsafe Function 不安全函数	非线程安全 localtime、memcpy_s 返回值 <0 判断
严重级分档：critical（ALP/RES/UND/FMT-002 等）、major（API/CON/LGC/EXC/IMP 等）、minor（CQT/LER/CTX 等）。

三、如何评价（关键点：当前没有自动化评分脚本）
我全仓搜索过，没有任何 Python 脚本引用 benchmark——它由一次 commit（98808d1 add benchmark，1497 文件/4.4 万行）静态导入，只有标注、没有 runner/评分器。评价方式目前是：

选一个 case（如 ALP-001-01），对其工程跑 cpp-review review，得到 findings。
与 expected.json 精确比对（而非模糊人工判读）：
维度	匹配标准
命中(Recall 分子)	报告的 rule_id + 文件路径 + 行号 ∈ expected_findings（行号允许 ±N 行容差是可选项）
证据链(可加分)	findings 的证据链能否逐条对上 evidence_chain（文件:行:内容）
误报(Precision 惩罚)	报了 distractors[].should_not_trigger 里的 rule_id，或在 negative 用例上报出任何 thing
修复建议	fix_hint 方向是否符合
聚合：52 条规则可算逐规则命中率（Recall）、误报率（distractor 命中数 → Precision/特异度），12 个 negative 用例专测"会不会被陷阱骗到"。
结论：期望答案是人工构造 + 可脚本化的精确比对——ground truth 已标注到「文件:行号 + 证据链」级，理论上能全自动打分（写个脚本跑 156 个工程、对 expected.json 算 P/R），只是这个打分器还没写进仓库。若需要，我可以帮你写一个 benchmark/run_eval.py：遍历所有变体 → 调 cpp-review → 与 expected.json 精确比对 → 输出按类别/规则聚合的 Recall/Precision 报告。要做吗？
