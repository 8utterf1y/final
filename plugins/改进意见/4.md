⚔️ 两项目 L4 过程实现对比
一、总体架构差异（根本区别）
维度	cpp_review (AI_for_code_review)	spec-review (插件)
驱动模式	🔒 确定性自动流水线（进程内执行）	🤖 Agent 驱动的交互式状态机
执行主体	Python 进程内 l4.py 自动串联	OpenCode Agent 调用 spec_review_* 工具逐步推进
阶段数	4 段：Actor→Critic→ReAct→Refiner	4 段：initial→challenge→investigate→converge
阶段间通信	内存中变量直接传递	SQLite stage_runs 表 + 工具往返
是否可人工干预	❌ 一次跑完	✅ 每阶段可暂停/查看/续推
---
二、阶段设计逐段对比
① 初判阶段
维度	cpp_review Actor	spec-review l4_initial
输入范围	全函数 + 全部规则（all_in_one）或单规则（per_rule）	仅 L3 判定 inconsistent/uncertain 的 claims
上下文	双向 BFS 调用链 + 级联裁剪	有界 BFS（20 nodes）+ 符号排名
输出字段	findings + doubts	期望/观察/候选差异/归因假设/证据/未证实前提
触发条件	无条件执行	_needs_deep_review() 条件升级（auto 模式）
> spec-review 胜：L3 全 consistent 时直接跳过 L4（ready_to_finish），大幅节省 token。cpp_review 的 L3/L4 是用户显式选择，无自动降级。
② 质疑阶段
维度	cpp_review Critic	spec-review l4_challenge
角色	站在开发者侧过滤误报	逐项尝试推翻初判
检查清单	10 项证据链检查	9 项：适用性/路径可达性/别名/替代实现/防护条件/配置/生成代码/外部行为/归因
输出	questions[]（带 tool + arguments）	按优先级排序的证据缺口 gaps[]
特殊机制	drop 指令 + 白名单校验	无（gap 直接驱动下阶段）
> 不相上下：cpp_review 的"drop 转 recheck"机制更细（防止 Critic 误杀），spec-review 的检查项更全面（含配置/生成代码/外部行为）。
③ 取证阶段（核心差异最大）
维度	cpp_review ReAct 循环	spec-review l4_investigate
执行者	LLM 自身在进程内发起工具调用（native tool_calling）	Agent 调用 spec_review_context 工具
工具	5 个（symbol_lookup/find_callers/find_callees/read_file_region/search_symbol_usage）	1 个工具 4 个方向（callers/callees/both + maxNodes）
循环控制	明确上限 max_react_rounds(2) + done 信号 + 观测预算(12000 tokens)	Agent 自主决定（提示词建议 max_tool_rounds: 64，无硬预算）
重试	首轮无工具调用 → 强制重试 1 次	无（依赖 Agent 判断）
上下文增量	working_memory 逐步追加观测	prior_stage_results 自动注入前序结果
最大节点	无硬限制（受预算裁剪）	60 nodes（investigate 专属）
> cpp_review 胜在"可控"：ReAct 循环有观测预算（react_observation_max）、轮次上限、done 信号、重试机制，token 消耗可预测。spec-review 依赖 Agent 自律，max_tool_rounds: 64 只是建议值，无硬性预算控制——一个"激进"的 Agent 可能无限取证。
>
> spec-review 胜在"灵活"：Agent 可以根据证据缺口自主决定查 caller 还是 callee、查多少节点；cpp_review 的 ReAct 受限于模型原生 tool_calling 能力（GLM/vLLM 偶发失败时靠 prompted 兜底）。
④ 收敛阶段
维度	cpp_review Refiner	spec-review l4_converge
输入	Actor findings + Critic questions + working_memory	全部前序阶段结果（自动注入）
决策规则	观测推翻→删 / 强化→留 / 无法证实→删 / 新发现→加	去误报 + 合并重复 + 定级
产出	findings（refined=True）	结论 + severity + 归因
补丁	❌ 无	✅ suggested_patch（证据充分时）
归因	❌ 无	✅ introduced/exposed/pre_existing/unattributed
> spec-review 胜：收敛阶段的归因机制（introduced/exposed/pre_existing/unattributed）是 cpp_review 完全没有的——这对"这次变更引入了什么问题 vs 历史遗留问题"的研判至关重要。suggested_patch 也是 cpp_review 缺失的。

三、过程质量保障机制对比
机制	cpp_review	spec-review	胜者
证据行号校验	✅ check_evidence_line_consistency() 锚点比对	❌ 无硬校验	cpp_review
证据归属校验	❌ 无	✅ evidence_id→claim_id 一一对应，跨 claim 复用被拒	spec-review
覆盖率门控	❌ 无	✅ 缺 claim 或多余 claim 都拒绝提交	spec-review
阶段推进门控	无（自动串联）	✅ 未 submit 不能 advance	spec-review
截断检测	✅ finish_reason=length → doubt + 不写缓存	❌ 无	cpp_review
缓存防毒化	✅ 截断/错误不写缓存	❌ 无缓存（每轮重跑）	cpp_review
结果缓存复用	✅ cache_entries（7 元组键）	❌ 无	cpp_review
规则驱动	✅ 25 条 YAML 规则注入 prompt	❌ 依赖 Agent 泛化	cpp_review
LLM 重试/降级	✅ Tenacity + 主备切换	❌ 无（依赖 Agent）	cpp_review
并发安全	RLock + 单进程	✅ 文件锁 + 进程级序列化	spec-review
可审计性	✅ llm_calls 表全量留痕	✅ stage_runs 表阶段留痕	持平
预算控制	✅ 级联裁剪 + 观测预算（硬）	⚠️ max_nodes 硬限但无 token 预算	cpp_review

四、Token 消耗对比
场景：10 个候选问题需深审
cpp_review（每个函数独立跑 L4）：
  Actor(1 次 LLM) + Critic(1 次) + ReAct(≤2 轮 × 1 次) + Refiner(1 次)
  ≈ 4-5 次 LLM 调用/函数，全程自动，token 可预测 ✅
spec-review（Agent 驱动，10 claims）：
  initial(≤4 页 context + 1 次提交) 
  + challenge(同上) + investigate(每个 gap 都可能查 60 nodes) + converge
  ≈ 4 阶段 × (N 次 context + 1 次 LLM)，但 LLM 调用次数由 Agent 自主决定，
  token 消耗不可控 ⚠️
---
五、适用场景与结论
cpp_review 的 L4 更适合：
1. 无人值守批量检视 — 全仓/多函数自动跑，确定性流水线不依赖 Agent 智能
2. 结果可复现 — 缓存机制保证相同输入→相同输出
3. Token 预算敏感 — 级联裁剪 + 观测预算是硬约束
4. C/C++ 专项 — 规则库 + 证据行号锚点针对 C/C++ 优化
spec-review 的 L4 更适合：
1. 需求-代码一致性检视 — claims 来自需求文档，L4 验证"代码是否满足需求"
2. 需要人工研判介入 — 每阶段可暂停查看，适合专家逐步研判
3. PR 集成发布 — 归因 + suggested_patch + PR Review 发布
4. Agent 协同场景 — 已嵌入 OpenCode，Agent 可实时查询
🏆 综合结论
> 没有绝对的"更好"，取决于目标。但就"L4 过程实现"的工程成熟度而言：
>
> 可靠性/可控性：cpp_review 胜 — ReAct 循环有轮次上限、观测预算、done 信号、重试、截断检测、缓存防毒化，是一套闭环可控的工程实现；spec-review 把流程控制权交给 Agent，质量波动取决于 Agent 自律。
>
> 过程严谨性/结果价值：spec-review 胜 — 阶段门控、证据归属校验、覆盖率门控、归因、suggested_patch 这些"过程质量保证"和"结果深化"机制是 cpp_review 没有的。
>
> 理想形态是两者融合：
> > spec-review 的流程骨架（门控 + 归因 + 校验）
>         +
> cpp_review 的执行内核（预算控制 + 缓存 + 重试降级）
>

两个项目 L4 过程实现对比
0. 先厘清：两边的"L4"不是同一个概念
主仓 cpp_review 的 L4	插件 spec-review 的 L4
本质	单个函数上跑「多角色流水线」（代码层确定性编排）	单个案例上跑「四阶段状态机」（LLM 自我驱动 + 运行时门禁）
输入	一个函数 + 全部规则	L3 判定为 inconsistent/uncertain 的候选 claim 子集（workflow.py:292-309）
校验主体	代码层（行号/白名单/截断…以 prompt + 代码双重兜底）	运行时层（claim/evidence 归属 + 覆盖率门禁硬拒绝）
LLM 调用	每阶段独立角色、独立 prompt	同一个子 Agent 在四阶段内自问自答
1. 阶段结构对比（可映射但不等价）
cpp_review L4	spec-review L4	对应但关键差异
Actor（l4_actor.j2 = L3）产出 findings+ doubts，可短路	l4_initial：陈述期望/行为/差异/归因假设/证据/未证实前提	主仓 Actor 直接产出可落库 finding；插件 initial 只形成"候选问题与假设"，必须走完四阶段才算数
Critic（l4_critic.j2，独立角色）逐条审 findings，产出带 tool+arguments 的 questions	l4_challenge：同一 Agent 尝试推翻自己初判，输出证据缺口（gap_id）	最大哲学分歧：主仓是"质疑者与被质疑者分离"，Critic 的 prompt 明确"怀疑即降级、别信 Actor"；插件是同体挑战，缺独立批判视角
ReAct（l4_react.j2）模型 propose tool_calls → Python 真执行（execute_tool→cpp-ctx）→ observation 追加 working_memory → 循环（默认 2 轮）	l4_investigate：按 gap_id 调 spec_review_context，选 callers/callees 方向分页取证据	主仓是真 ReAct（提-执-看三拍循环）；插件是单向受控检索（预打包证据包 + 固定 BFS 方向），没有"模型提需求→运行时执行→回填"的循环
Refiner（l4_refiner.j2）综合三者终判，去误报/补证据/提 confidence	l4_converge：去误报、合并重复、定级、归因、可附 suggested_patch	均为终判，但主仓 Refiner 有硬门槛（confidence≥0.7、白名单、禁推测词），插件靠 agent 自觉 + 运行时只验格式
2. 核心差异点
2.1 编排与信任模型（本质区别）
cpp_review：Python pipeline 顺序调用，**信任靠"角色分离+层层校验+降级兜底"**。Actor 敢报、Critic 泼冷水、Refiner 终裁，每层 prompt 独立设计（l4.py:465-528 Critic 含 11 条证据链清单 + drop 保护 _filter_invalid_drops 把合法 rule_id 的 drop 降级为 recheck）。
spec-review：状态机只往前走（每阶段提交一次，submit_stage+advance），**信任靠"运行时门禁"**：claim_id 格式、verdict 枚举、evidence 必须属于本 claim（跨 claim 复用硬拒，workflow.py:329-345）、consistent/inconsistent 必须有证据、expected/actual 覆盖率精确匹配（workflow.py:348-354）。语义正误完全押注在单个 agent 的自我一致性上。
2.2 取证模型
cpp_review 是真 ReAct：l4_react.j2 + l4.py:569-744 每轮模型调 5 个工具（symbol_lookup/find_callers/find_callees/read_file_region/search_symbol_usage），Python 真实执行并把 observation 拼回 working_memory 供下一轮，有 observation token 预算（默认 12000）、首轮无 tool_calls 强提示 retry、done 信号早停。
**spec-review 是"分页取证"**：context() 按 claim 返回预构造证据包（build_context_packs），investigate 只决定 direction/maxNodes。max_tool_rounds=64 定义了但从未被执行（workflow.py:94）——没有真正的工具执行循环，gap 的"取证"深度取决于索引预抽取质量。
2.3 失败降级
cpp_review：以"不丢"为原则。critic/reffner transport 失败或不可解析 → 一律 fallback 到 Actor findings（l4.py:499-510, 800-849）；per_rule 单规则失败跳过并 partial_error 不缓存；截断+0 findings 不写缓存防毒化（l4.py:929-933）。
spec-review：以"不脏"为原则。没有降级路径——校验失败就把结果拒收，同一个 agent 重写重提；运行时状态机严格执行"每阶段一次、不得跳过/覆盖"（workflow.py:191 唯一约束）。坏处：模型反复不过门禁会空转；好处：产出纪律严。
2.4 校验强项（互补）
cpp_review	spec-review
行号/坐标	check_evidence_line_consistency 逐条反查 + prompt 行号锚点	evidence 走稳定 evidence_id 引用，行号由索引保证
rule_id 合法性	白名单注入 prompt，白名单外 drop/剔除	无规则概念，claim_id 由运行时生成，天然可信
覆盖完整性	无（能发现多少是多少）	强门禁：missing/extra 都拒（防漏防幻觉双杀）
证据归属	无 claim 概念	强校验：evidence→claim 一一对应，禁跨声明复用
2.5 缓存与可复现
cpp_review：函数级 LLM 结果缓存（cache_key = body+ctx fingerprint+model+prompt+rule 版本，l4.py:207-215），命中整条 L4 跳过，可复现可回溯。
spec-review：只有索引快照按文件哈希增量复用（ind_ex 复用前次 snapshot），LLM 结论无缓存——每次审查都重新烧 token；这是选择"检查当前 PR"语义的代价。
3. 各自的优劣与可互相借鉴点
cpp_review 强在：多角色防偏置、真 ReAct 深度取证、失败降级不丢结论、LLM 层缓存。
短板：无覆盖门禁（可能整函数漏报而不自知）、无 claim/证据归属校验（幻觉 finding 只能靠 prompt 约束）、每函数独立跑成本高。

spec-review 强在：运行时硬门禁（覆盖率/归属/枚举全验，主仓最缺的）、单 Agent 四阶段编排轻量、分页上下文预算清晰。
短板：无独立质疑者（challenge 自问自答）、取证是单向检索非真 ReAct、校验失败只能原地重写无降级、无 conclusion 缓存。

借鉴建议：

插件给 l4_investigate 引入"propose-执行-回填"真工具循环（复用主仓 ReAct 预算+retry 模式），让 gap 取证真正可迭代；
主仓可把插件的覆盖率门禁移植为最小形态（如函数级"至少产出 findings 或 doubts，否则标 uncertain"）；
插件 l4_challenge 可考虑把前一轮结论交给"独立 Critic prompt"复核一轮再进 converge，或至少把 challenge 的推翻理由硬性字段化；
主仓的 fallback 哲学（失败回退 Actor 不丢结论）可让插件在状态机加"阶段结果不可解析 → 自动用前一阶段结果降级"路径。
